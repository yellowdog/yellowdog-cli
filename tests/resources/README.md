# The Resource Specification Corpus

This directory is the single source of resource specifications used by `tests/test_resource_specs.py`, `tests/test_resource_property_coverage.py` and `tests/test_system_resources.py` — one Jsonnet file per resource type, loaded through the CLI's own loader (`load_resource_specifications()`) rather than duplicated as a second set of fixtures. Extending coverage for a resource type means editing the corpus, not the test files that read it.

## Minimal and Maximal

Most files define a `Min` specification carrying only the properties the SDK dataclass marks required, and a `Max` one carrying every other settable property. The minimal variant proves nothing optional is secretly required by the CLI's creation path; the maximal variant is what `test_resource_property_coverage.py`'s gate measures against — every settable property of every SDK model in scope must appear in some maximal (or minimal) specification, or be excluded in `resource_models.py` with a stated reason. A few files (`credentials.jsonnet`, `allowances.jsonnet`) repeat the Min/Max pair once per polymorphic subtype rather than once for the whole file, because coverage is tracked per concrete SDK class, not per corpus file.

## Variables

Every environment-specific value — an AWS region, an Azure resource group, a GCP project — is a `{{variable}}` resolved from `test-config.toml`'s `[common.variables]` table (or from `[common]`'s own `namespace`/`tag`), never hard-coded in a `.jsonnet` file. Every resource's own name carries `{{run_id}}` (via `lib/base.libsonnet`'s `name()` helper), so two runs against the same account never collide on a name. Pointing the corpus at real infrastructure is therefore an edit to `test-config.toml` alone: replace a dummy value there and every specification that references it picks up the change with no edit to any `.jsonnet` file.

## Credentials

Credentials come from the environment, and only from there:

```shell
export YD_KEY=... YD_SECRET=...      # and YD_URL, for a non-default platform
```

`test-config.toml` carries no key, secret or URL, and imports none from anywhere else — it names no credential property at all, which is precisely what hands the decision to the environment: an explicitly selected `-c` file outranks environment variables only for the properties it actually defines (see `CLAUDE.md`'s Configuration section). This is a deliberate constraint rather than an omission. It keeps the tracked configuration free of any reference to a personal file, so nothing in the repository has to be edited to switch accounts; it means a run that authenticates as the wrong account has one place to look rather than an indirection to unwind; and it is the same pair of variables every other platform-touching test in the suite already uses, so `--run-system` has a single prerequisite across the board. Setting a key or secret in `test-config.toml`, or reintroducing an `importCommon` that supplies one, would defeat all three.

## What the Live Layer Cannot Create Standalone

Three specifications — `requirement-templates.jsonnet`'s `staticMin` and `dynamicMin`, and `configured-worker-pools.jsonnet`'s `poolMin` — cannot be created as standalone resources against the real platform. `create_compute_requirement_template()` and `create_configured_worker_pool()` (`create.py`) read `namespace` out of the resource dict with a bare `resource[PROP_NAMESPACE]` subscript before any SDK model is ever built, which is stricter than the model itself, where `namespace` is optional. `resource_live.KNOWN_PARTIAL_FAILURES`/`KNOWN_PARTIAL_FAILURE_NAMES` document this explicitly, and `test_system_resources.py` asserts these three specifications, and only these three, fail creation within their files — every other specification in the same file is still expected to succeed, since `create_resources()` continues past one resource's failure rather than aborting the file.

`credentials.jsonnet` and `namespace.jsonnet` are never created by the live layer at all (`resource_corpus.OFFLINE_ONLY`): real provider credentials are out of scope for this suite, and the shared namespace is created once per test account by a session-scoped fixture rather than as a per-test resource.

## Adding a Property to a Resource Type Already Covered

You do not have to notice the property: the gate notices it for you. `resource_models.settable_properties()` reads `dataclasses.fields()` on the installed SDK model, so a property the SDK gained in an upgrade is demanded the moment that version is installed, and `pytest tests/test_resource_property_coverage.py` fails naming it and the class it belongs to. Upgrading the SDK and running that one test file is therefore how you find out what a new SDK release added to the settable surface.

1. Add it to the `Max` local for that class, in the file that covers it — for a compute source, `source-templates.jsonnet`. That is usually the whole change.
2. Add it to the `Min` local as well **only if the SDK marks it required** (no default). The minimal variants exist to prove nothing optional is secretly required, so putting an optional property there defeats their purpose.
3. Run `pytest tests/test_resource_specs.py tests/test_resource_property_coverage.py`. The gate closes, and the offline layer additionally asserts the property survives into the SDK model *with the value the specification sent* — a property that arrives under the right name with a mangled value is the regression this suite exists to catch, so presence alone is not enough.
4. Run the live case for that file, for example `pytest --run-system "tests/test_system_resources.py::test_resource_lifecycle[sources]"`, and triage anything the platform says using the table below.

Four rules for the value, each of which has produced a real failure here rather than being hypothetical. Anything environment-specific — a subnet, image, region, ARN, project — belongs in `test-config.toml` as a `{{variable}}` and never inline. An enum-typed property must use a real member of that enum: an invalid value is stored as `None` in silence, so the specification looks thorough while exercising nothing. A property whose type is a nested model needs that model's real field names, because a wrongly-shaped object silently yields a default instead of an error, and it needs a `type` key only where that nested class is genuinely polymorphic — most are not. And once a nested model is reachable, the gate starts demanding *its* settable properties too, so expect the failure list to grow by more than the one property you added.

If the live run objects, choose the registry by what you observed, never by what would make the run pass:

| What the platform did | Where it goes |
|---|---|
| Rejected creation outright (`... must be null`) | `resource_models.SERVER_ASSIGNED_COVERAGE`, and remove the property from the corpus — no specification can carry it |
| Returned its own value in place of yours | `resource_models.SERVER_ASSIGNED_COVERAGE` (see the read-gate obligation in step 8 below) |
| Nothing — `create.py` pops the property before building a model | `resource_models.NOT_SETTABLE`, citing the pop |
| Accepted it, then never echoed it back | `resource_live.LIVE_ONLY_EXCLUSIONS_BY_CLASS`, keeping the property in the corpus so the offline gate still covers it |
| Something that genuinely cannot be exercised here | `resource_models.NOT_TESTED`, with the reason |

The distinction that matters most is between the second and fourth rows: a genuinely platform-assigned property **comes back**, which is exactly why `provider`, `traits` and `id` are what close the read gate. A property that is accepted and then neither stored nor returned is a platform bug worth reporting, not a property to stop demanding — and excluding it on the write side would hide it permanently, in both layers at once. Four separate review rounds during this suite's construction found exclusions resting on a plausible argument rather than an observation, each one hiding real coverage; when the evidence does not settle it, leave the property in the gate.

## Adding a New Resource Type

1. Add a `<type>.jsonnet` file (or extend an existing one, if the new type is a variant of something already covered — e.g. another Allowance subtype). Follow the existing files' shape: import `lib/base.libsonnet` for `name()`/`namespace`/`sourceTemplate()`, define a `Min` local with only the required properties and a `Max` local layering in every other settable one, and end the file with the list of resources to emit.
2. Add an entry to `resource_models.MODEL_FOR_RESOURCE` (`tests/resource_models.py`) naming the SDK model class `create.py` builds for the new resource type — a fixed class name, `None` if `create.py` calls the client (or a plain constructor) directly with no model object involved, or `resource_models.DYNAMIC` if the class name is read out of the specification itself (a `type`/`source.type`/`credential.type` property), in which case also add every concrete class it can resolve to into `resource_models.DYNAMIC_MODELS`.
3. **Teach `resource_models.build_models()` about the new type, if `create.py` does anything to a specification before building its model.** This is the step to get wrong: `build_models()` mirrors `create.py` rather than calling it, and every divergence between the two is a test that passes while the CLI fails (or the reverse). A type needs its own branch if `create.py` pops a discriminator (`type`, `source.type`, `credential.type`), builds more than one model (a `ComputeSourceTemplate` builds the source *and* the wrapper), pre-processes a value (an Allowance's natural-language dates go through `dateparser`, and an unparseable one must raise the way `create_allowance()` does), or carries a property that belongs to no model at all and must be popped rather than compared (a `Credential`'s `keyringName`, an `Application`'s `groups`/`keyrings`). A type that needs none of that needs no branch: the fallthrough builds one model from `MODEL_FOR_RESOURCE`.
4. Add an entry to `test_system_resources.ENTITY_TYPE_FOR_RESOURCE` mapping the resource type to the `yd-list`/`yd-remove` entity type it becomes — unless the new file belongs in `resource_corpus.OFFLINE_ONLY`, in which case it never reaches the live layer and needs no entry there.
5. Run `pytest tests/test_resource_specs.py`. Beyond the model-building checks, this dry-runs every specification through `create.py`'s own `create_resources()` dispatch. If a specification cannot be created at all (and the live layer documents it in `resource_live.KNOWN_PARTIAL_FAILURE_NAMES`), and the dry run reaches the failure offline, name it in `test_resource_specs._DRY_RUN_EXPECTED_FAILURES` too.
6. Run `pytest tests/test_resource_property_coverage.py`. The write-side coverage gate will name any settable property of the new model that no specification exercises yet; add it to the `Max` local, or — only with a reason citing `create.py`'s own behaviour or live-probe evidence — exclude it in `resource_models.NOT_SETTABLE`, `resource_models.NOT_TESTED`, or (for a genuinely platform-assigned property) `resource_models.SERVER_ASSIGNED_COVERAGE`. Do not exclude on a hunch: an excluded property is invisible to the gate forever.
7. Then the live layer (`pytest --run-system tests/test_system_resources.py`), where a handful of registries may need the new type. Each is a one-line entry, and each has a comment saying what it is for: `resource_corpus.OFFLINE_ONLY` (the live layer must never create this file); `resource_live.SECRET_EMITTING` (creation prints a secret, so no failure message may quote the command's output); `resource_live.NO_YDID_ENTITY_TYPES`/`NO_YDID_KEY_FIELD` (the entity has no YellowDog ID, so it is matched by a plain field instead); `resource_live.LIVE_ONLY_EXCLUSIONS` (a property `yd-show` structurally cannot echo) or `LIVE_ONLY_EXCLUSIONS_BY_CLASS` (the same, but only for one polymorphic class — always prefer this one where the property name exists on sibling classes that behave correctly); `test_system_resources._identity()` (the new type is named by none of `name`/`description`/`namespace`); `test_system_resources._remove_args()` (`yd-remove` needs an extra flag, as an Allowance needs `-M`); and `test_system_resources._record_read_gate_evidence()` (the new type nests or discriminates the classes `SERVER_ASSIGNED_COVERAGE` names, which the read gate cannot see otherwise).
8. A property added to `SERVER_ASSIGNED_COVERAGE` is also picked up by the live layer's read gate (`test_system_resources.test_every_server_assigned_property_came_back_in_a_live_run`), which then demands the property either actually come back from a live `yd-show` for that class at least once, or be waived by a `test_system_resources.READ_GATE_EXCLUSIONS` entry recording what was observed instead — so an exclusion made on the write side needs live evidence, not just an offline model-building shortcut, before `--run-system` will pass. Most of the waived pairs belong to a compute source that never provisions a real instance. A waiver is not permanent either: if the platform starts returning a waived property, the read gate reports the exclusion as stale and asks for it to be deleted.
