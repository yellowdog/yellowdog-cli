# Tests

Tests are run using [pytest](https://docs.pytest.org/).

The unit tests need no configuration at all: `conftest.py` loads the configuration as the run starts, and the common section's missing key or secret would stop it, so it substitutes a dummy key and secret where none can be found, and reports that in the pytest header. Anything already working is left alone, and no substitution is made under `--run-system`, which takes real credentials of its own; `--run-live` gives `yd` its credentials itself, so a dummy set may still stand in for the CLI's own configuration.

## Quick Start

Set up as [Getting Started](../DEVELOPMENT.md#getting-started) describes, which installs the `dev` extra (pytest and its plugins) with the rest; the unit tests need nothing else. Then pick the row for what you want to test:

| To test | Run | Needs |
|---|---|---|
| Everything offline, as before a commit | `make test` | Nothing |
| One file, or tests matching a name | `pytest -v tests/test_ydid_utils.py`, `pytest -v -k test_variable` | Nothing |
| Every supported Python (3.10 to 3.15) | `make tox` | `uv` |
| Commander's GUI | `pytest -v -n 8 tests/test_commander_*.py` | The `commander` extra and Qt's runtime libraries; skipped without them |
| The MCP server | `pytest -v tests/test_mcp_*.py` | The `mcp` extra for `test_mcp_server.py`; skipped without it |
| A command's options, after changing them on purpose | `pytest tests/test_parser_snapshots.py --update-parser-snapshots` | Nothing |
| Types | `make pyright` | Nothing |
| Which lines the unit tests reach | `make coverage` (detail in `htmlcov/index.html`) | Nothing |
| The tests that crash a child interpreter, on macOS | `pytest -v --run-crash-tests` | Nothing (they run anyway elsewhere) |
| Resource specifications against the Platform | `pytest -v --run-system tests/test_system_resources.py` | `[platform]` in `~/.config/yellowdog/system-tests.toml`, copied from [`live/system-tests.example.toml`](live/system-tests.example.toml) |
| Every system test | `pytest -v --run-system` | The same |
| The live tests' configuration, offline | `make live_config` | A filled-in `system-tests.toml` |
| Failure handling, Work Requirement control and Task listing, live but with no compute | `pytest -v --run-live tests/live/test_live_failures.py tests/live/test_live_work_control.py tests/live/test_live_listing.py` | The same; a few minutes |
| One provider's chain, live | `pytest -v --run-live tests/live/test_live_providers.py -k aws` (or `azure`, `gcp`, `oci`) | That provider's section; real compute, about 20 minutes |
| The whole live suite, every configured provider | `pytest -v --run-live -n 4 tests/live/` | Every provider's section; real compute, about 30 minutes |
| What a dead live run left behind, and clearing it | `python tests/live/sweep.py --dry-run`, then without `--dry-run` | A filled-in `system-tests.toml` |

The live tests provision real cloud instances and cost money: run them when you mean to. A live run tears down everything it made, and the sweep catches what a killed run left.

## Namespaces

The unit tests reach no Platform. The tests that do work in two fixed namespaces, which exist in the account for good, since the Platform never deletes a namespace that has been populated:

| Namespace | Used by | What is in it |
|---|---|---|
| `yd-cli-system-tests` | The live suite (`--run-live`; `tests/live/harness/run.py`'s `NAMESPACE`) and the resource system tests (`--run-system`; `tests/resources/test-config.toml`) | A live run's resources, work and compute, named `ydst-<yymmddhhmm>-<4 base36>-…` and tagged with that run ID, removed by its teardown or the sweep; the resource tests' specifications, named `yd-test-<run>-…` and tagged `yd-cli-tests`, removed as each test ends. Each suite selects only its own, by name and tag |
| `yd-cli-tests` | The failure tests' limited Application (`LIMITED_NAMESPACE`), which may read Work Requirements there and nowhere else | Nothing: the control case lists its Work Requirements and expects none, so no test puts work in it |

Keyrings, Applications, Groups, Allowances and Attribute Definitions are not in a namespace: the live suite tells its own apart by name and by a description naming `yd-cli-system-tests`, and the resource tests by name. `test_dryrun_system.py` lists with an empty namespace and tag (every namespace) under `--dry-run`, and `test_system_error_handling.py`'s input fails before anything is created, so neither leaves anything behind.

## Test Categories

Three categories of test exist, controlled by pytest flags:

| Flag | Marker | Description |
|---|---|---|
| *(none)* | — | Unit tests; no platform connectivity, configuration file or credentials required |
| `--run-system` | `system` | System tests (resource CRUD, error handling, dry-run listings); requires credentials |
| `--run-live` | `live` | The [live system tests](#live-system-tests---run-live-provisions-real-cloud-instances) under `tests/live/`: everything a run needs created from their own configuration, real compute provisioned, everything torn down; never part of `make test` or `tox` |
| `--run-crash-tests` | `crashes` | Not a category: on macOS, runs the tests that crash a child interpreter on purpose, which are skipped there without it because each crash puts up the system's "quit unexpectedly" dialog (Homebrew's Python runs as `Python.app`). Elsewhere they always run |
| `--update-parser-snapshots` | — | Not a category: regenerates `parser_snapshots.json` for `test_parser_snapshots.py`, which then passes, rather than running any extra tests. Regenerate on the oldest supported interpreter, or check the test on one, because a newer argparse can derive values differently |

Around 700 of the unit tests are [Commander GUI tests](#commander-gui-tests). They are controlled by no flag, but they skip where PyQt6 or Qt's runtime libraries are unavailable, so a run without them reports fewer passes and more skips rather than any failure.

`test_dryruns.py` and `test_demos.py` hold the maintainer's own checks against a separate repository, skipped unless enabled; nothing in development needs them. `test_demos.py`'s `TestDemoCommandHarness` is unmarked and so runs in the standard suite: it exercises two shell idioms (`_timed` and `_with_cleanup`) with stub commands, provisioning nothing, and the two of them that time a command out skip where there is no coreutils `timeout` (standard on Linux; Homebrew's `coreutils` on macOS).

### Live System Tests (`--run-live`, provisions real cloud instances)

`tests/live/` sets up everything a run needs with `yd resource create`, provisions on each configured provider, and tears it all down, depending on nothing outside the repository or already on the Platform but its two fixed namespaces (`harness/run.py`'s `NAMESPACE`, `yd-cli-system-tests`, and the failure tests' `LIMITED_NAMESPACE`, `yd-cli-tests`; never configured, see [Namespaces](#namespaces)), which it creates if missing and never removes. Its configuration is its own, never `config.toml`: `YDST_CONFIG`, else `~/.config/yellowdog/system-tests.toml`, with every key overridable as `YDST_<SECTION>_<KEY>` — see [DEVELOPMENT.md](../DEVELOPMENT.md#live-system-tests). Everything a run makes is named `ydst-<yymmddhhmm>-<4 base36>-...` and tagged with that run ID, so runs may overlap, and `python tests/live/sweep.py [--older-than HOURS] [--run RUN_ID ...] [--dry-run]` tears down runs that died. The run is set up once, by xdist's controller (or, without `-n`, by the first live test), and torn down when every worker has finished. A whole-suite session ends with the coverage gate, which fails on any CLI verb neither exercised nor listed, with its reason, in `harness/coverage.py`'s `NOT_EXERCISED` (after a failed test it names them and fails nothing more, since a scenario stopped part-way leaves its later verbs unrun); and every `yd` call fails if its output holds a configured secret. The files whose rows begin "Live" (and `test_live_marker.py`'s one test) run only with `--run-live`; every other file runs offline in the default suite.

## Prerequisites for Platform Tests

`--run-system` and `--run-live` take the Platform's credentials from one place: `[platform]` in the live system tests' configuration, `~/.config/yellowdog/system-tests.toml` (or the file `YDST_CONFIG` names), each key overridable as `YDST_PLATFORM_KEY`, `YDST_PLATFORM_SECRET` and `YDST_PLATFORM_URL`:

```toml
[platform]
key = "..."
secret = "..."
url = "..."   # optional, defaults to production
```

Under `--run-system`, `conftest.py` sets `YD_KEY`, `YD_SECRET` and `YD_URL` from it before anything runs, in place of the shell's, so every `yd` a test starts uses them; a missing key or secret stops the session. A configuration file of your own is never read for them.

## Parallel Execution

The tests support parallel execution via `pytest-xdist`:

```shell
pytest -v -n 4                         # 4 workers, unit tests only
pytest -v --run-live -n 4 tests/live/  # the live suite: its groups in parallel
```

Tests sharing state that no worker can isolate are kept on one worker with `@pytest.mark.xdist_group`, which `--dist loadgroup` in `pyproject.toml`'s `addopts` honours (and ignores without `-n`): `test_commander_file_preview.py`, whose real Qt file dialogs share the sidebar width Qt keeps in the user's own settings, is one group. `test_system_resources.py` is another, `live_resources`: it compares every resource of a type before and after, and its read gate reads what its own lifecycle tests recorded in that process. The live system tests are grouped the same way, one `ydst-*` group per provider's chain and per scenario, so the groups run in parallel and each one's steps in order on one worker.
