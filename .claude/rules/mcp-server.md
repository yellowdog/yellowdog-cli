## MCP Server

`yd-mcp` is an MCP server over the CLI, in `yellowdog_cli/mcp/`, offered by the optional `mcp` extra (`mcp>=2.2`). It is a thin peer of Commander: **every tool call runs a `yd-*` command as a child process with `--json`**, exactly as Commander runs a command in response to a button, so that behaviour, configuration precedence, output shapes and exit codes are the CLI's by construction rather than a second implementation of them. Nothing in the package imports the SDK, `wrapper.py`, `args.py` or `printing.py`: `args.py`'s `ARGS_PARSER` is a registered command's command line, and `yd-mcp` is not one, and `printing.py`'s output goes to a terminal a stdio server does not have. `tools.py` and `runner.py` import nothing from the `mcp` package either, so the tool catalogue and the child-process runner are tested without the extra installed; `server.py` is the one module that imports `mcp`, and `launcher.py` imports it only after `check_mcp_imports()` (`utils/check_imports.py`) passes, so `--help` and the missing-extra message work without it, as Commander's do without Qt.

The tool catalogue (`tools.py`) is built from the command registry, not hand-written: `build_tools()` makes one `ToolSpec` per command whose `ToolKind` (`command_registry.py`) is not `NONE` — `READ_ONLY`, `ACTING` or `DESTRUCTIVE`, carried to the client as `readOnlyHint`/`destructiveHint` (`destructiveHint` false for `ACTING`, against the protocol's destructive default), with `openWorldHint` on every tool — from `all_options()` less those `mcp_excluded()` names (`MCP_EXCLUDED_OPTIONS`, by name for every command, and `MCP_EXCLUDED_SPECIFICATION_FILES`, the specification-file flags by command, since `--worker-pool` and `--compute-requirement` are also `yd-nodeaction`'s and `yd-resize`'s own non-file options), mapped mechanically to JSON Schema (`_property_schema()`, `_item_schema()`). **A new command states its `ToolKind` when it is added to the registry**, since the field has no default; **a new option is placed on purpose**, either given a schema entry or excluded, and `tests/test_mcp_tools.py` holds every option of every tool command to one or the other. `yd-cloudwizard`, `yd-format-json`, `yd-jsonnet2json` and `yd-help` are `ToolKind.NONE` and so absent from the catalogue. The action commands whose targets may be left out, acting then on everything in scope, are in `SCOPE_TARGETS` (`tools.py`, the command and its targets positional): their tools take an `all_in_scope` boolean, and `_validate()` refuses a call with neither targets nor `all_in_scope`, or with both, since `--yes` would otherwise turn an omission into an action on everything; a test holds every acting or destructive tool with an optional `nargs='*'` positional (bar a `tool_required` one) to the table.

`fixed_args()` prepends what every tool call needs ahead of its own arguments, gated per command on the option actually being present: `-c <file>`/`--nc`, `--nf`, `--json` (added even for `yd-version`, whose parser is its own and not in the registry), `--quiet` for `SELF_PRINTING_COMMANDS` (`yd-show` and `yd-variables`, which print their own document through `print_json()` with no `--json` option, so without it the wrapper's `Done` follows the document and `Run.document` is `None`, as Commander's `_yd_variables_command()` found), `--yes`, then the launch-time namespace, tag and variables, each joined as `--flag=value` as a tool's own are, so a tool's own `namespace`/`tag`/`variable` argument comes later on the command line and wins; a launch `-v` is held at launch to `VARIABLE_NAME_PATTERN` and `RESERVED_VARIABLE_NAMES` (`variable_syntax.py`), since `variable_substitution` cannot be imported there. `command_argv()` runs the command as `python -m <module>` under the server's own interpreter, the module from `command_registry.command_module()` (the console script's entry point, which Commander's `host.cli_program()` shares), not the `yd-*` console scripts, since a desktop client launches the server with a minimal `PATH` that may not hold them. `to_argv()` emits every value-taking option as one `--long-flag=value` entry (`_joined()`; an `append` option repeats it, a `--sort` (its `type` in `SORT_KEY_TYPES`), offered as a list of its keys, joins them with commas, a boolean stays its bare flag), and **that form is load-bearing for security, not style**: as two entries, a value that looks like a flag (`namespace="--show-secrets"`) is taken by argparse as that flag on a `nargs="?"` option such as `--namespace` or `--tag`, which switched on exactly the options `MCP_EXCLUDED_OPTIONS` withholds — `yd_variables` reported the secret in full — so never tidy it back into `[flag, value]`; for the same reason `_property_schema()` refuses a non-positional option with `nargs` of `*` or `+`, whose values one entry could not carry. It emits `--` ahead of the positionals, so a positional starting with `-` (a glob, a remote path) is never read as an option. The five specification-taking tools (`yd_submit`, `yd_provision`, `yd_instantiate`, `yd_create`, `yd_remove`) accept a path or the specification inline; an inline one is written as JSON to a uniquely named `.yd-mcp-*.json` file in the working directory, created exclusively and readable by the owner only (`tempfile.NamedTemporaryFile`, so O_EXCL and 0600: a predictable name written with `write_text()` followed a symlink pre-placed there and was world-readable) — the config file's directory, so relative `taskDataFile`/`userDataFile` references resolve as they would from a file the user wrote there — and removed after the run whatever its outcome.

`runner.run()` runs one command line with `subprocess.Popen` (`stdin=DEVNULL`, so an unanswered prompt fails fast rather than hanging), in a process group of its own (a new session on POSIX, `CREATE_NEW_PROCESS_GROUP` on Windows), with `PYTHONIOENCODING=utf-8` (`CHILD_ENVIRONMENT`), and a `timeout_seconds` bound (every tool has one, default 300, `yd_follow`'s 60); at the bound the whole group is interrupted (`_interrupted()`: SIGINT by `os.killpg()`, as a terminal's Ctrl-C reaches the foreground group, so the wrappers flush the `--json` records of what was done — killed outright, a stopped call lost its whole document — and what the command started stops too rather than running on through the grace period; not on Windows, whose CTRL_BREAK_EVENT Python does not make a KeyboardInterrupt), given `INTERRUPT_SECONDS` to go, and then killed whatever it did (`os.killpg()`, or `taskkill /T /F`), the pipes drained for at most `DRAIN_SECONDS` — killing the command alone left a data client command's rclone transferring after the stop, and on Windows held the pipes so the stop never returned — and the result is a stopped `Run` carrying what the child had already written, not an exception; output is decoded as UTF-8 with `errors="replace"`, since a strict decode raised `UnicodeDecodeError` out of `call_tool()` and the SDK answered a stray byte with a JSON-RPC internal error. `server.py`'s `_result_of()` turns a `Run` into a `CallToolResult`: an exit 0, a stopped run, or an exit 1 whose document holds a record with `outcome`/`action` of `failed` (the CLI's own per-item rule, `results.any_failed()`) is a success, `structuredContent` being `{"result", "exitCode", "stopped"}` (plus `"stderr"` when stopped); every other non-zero exit, or no parseable document at all, is `isError` with `{"result", "exitCode", "stderr"}` and, as text, the command's stderr followed by the document as compact JSON when there is one (`_error_text()`: `yd_doctor`'s failing checks and `yd_wait`'s failed Work Requirement exit 1 with the document alone, and said only 'exited 1 with no output' before); an unknown tool name, an argument `timeout_of()` or `_validate()` rejects, an `OSError` writing an inline specification or starting the child, or any other exception raised inside `call_tool()` (its last-resort `except Exception`, which logs the traceback to stderr) is a tool error too, with `exitCode` 2, never a protocol-level error, so the agent sees the message and can retry. Stdout is the transport (`stdio_server()`), so nothing the server prints for itself may go there; it logs its own start and, per call, the command line (the module and its arguments, without the interpreter) and the child's exit code to stderr at `INFO`, which is why the fixed `-v` arguments, and a call's own `variable` argument, make a secret-holding variable visible in the server's own log. On POSIX the first SIGINT or SIGTERM ends the process at once (`_stop_on_signal()`, an `anyio.open_signal_receiver()` task beside `server.run()`): it logs `stopped (<signal>)`, flushes the log (`logging.shutdown()`) and calls `os._exit(0)` because cancelling the task group cannot finish — the SDK's stdin reader blocks in `readline()` in an anyio worker thread that a cancel waits for and interpreter exit joins, as does a tool call in progress — which is why one Ctrl-C used to be absorbed and a second one printed a traceback. A command still running is left to finish on its own. On Windows, which has no signal receiver, `run_server()` catches `KeyboardInterrupt` instead.

Tests are `tests/test_mcp_tools.py`, `tests/test_mcp_runner.py`, `tests/test_mcp_launcher.py` (all Qt-free, SDK-free and `mcp`-free) and `tests/test_mcp_server.py`, which drives the real `Server` through the SDK's own `ClientSession` over in-memory streams and is skipped without the extra (`tests/mcp_guard.py`'s `require_mcp()`, in the style of `qt_guard.py`'s `require_qt()`). `yellowdog_cli/mcp/README.md`, shipped as package data, documents the server for its users; `tests/test_mcp_readme.py` holds it to declaring every tool and keeping its table of contents current.

Phase 2 (a `streamable-http` transport, per-session credentials) is left open rather than built: `run()` already takes an `environment` parameter that phase 1 fills with the server's own `os.environ` and phase 2 would fill per session instead, and no tool exposes `--key`, `--secret`, `--url` or `--config`, so a session's credentials can only ever come from that parameter.

## Modules

```
├── mcp/                         # yd-mcp: the MCP server over the yd-* commands (see MCP Server above)
│   ├── __init__.py
│   ├── launcher.py              # Entry point: argparse into a ServerSettings, the missing-extra guard, then the server; mcp-free, SDK-free, Qt-free
│   ├── __main__.py              # 'python -m yellowdog_cli.mcp'
│   ├── tools.py                 # The tool catalogue from the command registry: ToolSpec, build_tools(), fixed_args(), to_argv() (a call's arguments to the child's command line, inline specifications included); imports nothing from mcp
│   ├── runner.py                # run(): one command line as a child process with a bound, returning a Run (document, stderr, exit code, stopped); parse_event_documents() for yd-follow's stream; imports nothing from mcp
│   ├── server.py                # The mcp.server.lowlevel.Server: on_list_tools/on_call_tool over tools.py and runner.py, the stdio transport; the one module in the package that imports mcp
│   └── README.md                # User-facing documentation for the server, shipped as package data
```
