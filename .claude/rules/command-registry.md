## Command Registry

Every `yd-*` command's options are defined once in `utils/command_registry.py`, as data. `CLIParser` builds argparse with `build_parser()`: the command's own options first, in the order argparse will print them, so the option order in a `Command` is load-bearing for `--help`, then the kind's common set (`COMMON_OPTIONS`, the docs' Universal Options) in an argument group of their own (`COMMON_OPTIONS_TITLE`), which the usage line shows as one `[universal options]` (`_usage()`, argparse's own line for the command's options alone, so its wrapping is argparse's). A shared option is one module constant (`NAMESPACE`, `FOLLOW`, `DRY_RUN`, ...) and a command whose wording differs uses `CONSTANT.variant(help=...)`, which keeps the option's identity (an `Option`'s `kwargs` are a read-only copy, since a shared constant changed in place would change every command taking it); `Command.has()` and `option_named()` both compare by that identity, and `option_named()` is what the README checker relies on to look a flag up. Four options are separate constants rather than `variant()`s, because a `variant()` merges keyword arguments onto the base rather than replacing them and cannot change the `flags` tuple, so it can narrow a keyword's value but never drop one or remove an alias: `DRY_RUN_JSON` and `ACTIONS_JSON` (each a bare `--json` with no `-J`, unlike the shared `JSON`; `ACTIONS_JSON` is the base of `TRANSFERS_JSON`, `RESOURCES_JSON`, `CREATE_JSON` and `ENTITY_JSON`), `RESIZE_COMPUTE_REQUIREMENT` (a flag with no `type`, unlike `COMPUTE_REQUIREMENT`'s) and `NODE_ACTION_STATUS` (a flag with no `dest`, unlike yd-list's `STATUS`, which appends into `status_filter`) — each keeps its base's first long flag, so identity is preserved. The command is resolved from `sys.argv[0]` by exact lookup after `command_from_argv0()` normalises it (basename, a `.py`/`.exe` suffix stripped with any `-script` before it, underscores to hyphens, `yd-` prefixed), so a command name inside the install path does not matter and no substring ordering does either; an unknown name gets the API common set only, which is what pytest's executable gets. Post-parse checks are `validators` on the commands they apply to. A positional a data client command needs is optional to argparse (`nargs="*"`, or `"?"` for `yd-copy`'s two paths) with `Option.tool_required` (`yd-upload`'s `local_paths`, `yd-download`'s `remote_paths`, `yd-copy`'s two paths, checked by `check_copy_args`), so that `--which-rclone` and `--upgrade-rclone` run without one: `check_paths_given` requires it otherwise, and the MCP tools, which offer neither option, mark it required. yd-list's are table-driven: `LIST_NAME_TYPES`, `LIST_STATUS_TYPES`, `LIST_ACTIVE_TYPES`, `LIST_ID_TYPES`, `LIST_SUBSTITUTE_TYPES`, `LIST_DELETABLE_TYPES` (namespaces' `--deletable`), `LIST_UNHEALTHY_TYPES`, `LIST_PROVIDER_TYPES`, `LIST_DESCRIPTION_TYPES`, `LIST_WITH_ERRORS_TYPES`, `LIST_POOL_KIND_TYPES` (`--provisioned`/`--configured`, Worker Pools alone, searched for by type, which the Platform takes fully qualified: `entity_names.PLATFORM_MODEL_PACKAGE`), `LIST_LIMIT_TYPES` (`--limit`: Tasks, Instances, Nodes and Workers, `DEFAULT_LIST_LIMIT` when not given, `list.py`'s `_ListLimit` reading each search lazily, one item past it, through `entity_utils.iterate_tasks_in_task_group()`, `_matching_instances()`, `_matching_nodes()` and `_matching_workers()`, which send what filters they can with the search (`_searched_statuses()`, `_searched_providers()`, nothing searched when nothing can match) and apply the client-side filters item by item, so that the limit counts what they keep) and `LIST_WITHIN_TYPES` (`--within`, the keys of `LIST_WITHIN_KINDS`, which gives the kinds of parent each type takes, an ID of any other kind refused as parsed: a Work Requirement or Task Group named as `work_targets.resolve_named_target()` reads it, a Compute Requirement found as the actions find one, a Worker Pool by name, each or a Node by its YDID) say which entity types each filtering option applies to, and `check_list_options` refuses it for any other (`--public-ips-only`'s, Instances alone, is inline there, as is its refusal with `--json`, `--ids-only` or `--details`), so a new entity type, or a filter extended to one, is added to those tables; a new entity type also needs its function in `list.py`'s `_LISTERS`, which a test holds to `ENTITY_TYPES`. `yd-cloud-info`'s filters are table-driven the same way: `CLOUD_INFO_OPTION_TYPES` says which of its types each applies to and `check_cloud_info_options` refuses it for any other, also checking `--vcpus`/`--ram`, which `CLIParser`'s `vcpus_range`/`ram_range` parse (`parse_range()`); its sort keys, `CLOUD_INFO_SORT_KEYS`, are held by a test to `utils/cloud_info.py`'s `SORT_KEYS`, and its `TYPE` positional's `resolve_cloud_info_type` is mapped to an enum in `mcp/tools.py`'s `_item_schema()`. `--sort` takes one key or several separated by commas, the most significant first, so it is a `type=` (`parse_sort_keys()`, through `entity_sort_keys` for the listings and `cloud_info_sort_keys`, giving a tuple) rather than `choices=`; `SORT_KEY_TYPES` maps each to its keys, which the MCP catalogue offers as a list, and `check_cloud_info_options` holds each key to the type's. `requires_namespace_and_tag` is an explicit field rather than derived from having `--namespace`, because `yd-list` has the option and is not one of them. `help.py`'s `main()` renders `COMMANDS` for `yd-help`'s listing, sorted by name. A command's extra is read from its summary's trailing `(needs the <extra> extra)`, and `EXTRA_PROBES` names one package per extra that `find_spec()` looks for, never importing it, to say whether it is installed; `--json` gives the extra and `installed` as fields. `yd-commander` and `yd-mcp`, entry points with no registry entry, are listed from the registry's `OTHER_COMMANDS` table (`command_registry.py`, which `help.py` imports), which `tests/test_command_registry.py` holds to the entry points the registry lacks. `tests/test_command_registry.py` holds the registry to `pyproject.toml`'s entry points, less the commands with `script=False` (`yd-completion`, `yd-auto-shutdown`, `yd-init`: released after `yd`, so no `yd-*` command to deprecate, typed only as their `yd` word or noun verb, and absent from `top_level.SCRIPT_FORMS`; `command_module()` finds such a command's module by its name, so **a new command is `script=False` and gets no entry point**), and `tests/test_docs_command_list.py` holds the Command List (`docs/commands.md`, which the README points to) to the registry: the Universal and Shared tables' membership and short forms, the preamble's exceptions, and every option bullet under a `### yd-x` heading naming an option that command takes. Its section parser ignores fenced code blocks (`_outside_fences()`), so a `#` shell comment inside an example is never mistaken for a heading or a bullet, and `yd-list`'s options, given in a table rather than as bullets, are checked as table rows. Wording is never checked, and nothing in the documentation is generated. `tests/test_parser_snapshots.py` holds every command's option *shapes* — each action's kind, flags, `nargs`, `const`, `default`, `type`, `choices` and `required` — to `tests/parser_snapshots.json`, never their wording, and the file is regenerated with `pytest tests/test_parser_snapshots.py --update-parser-snapshots` when a shape change is intended.
