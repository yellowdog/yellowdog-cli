## Specification Schemas

`utils/specs/properties.py` records, as data, every specification property the CLI itself defines rather than the SDK: the Work Requirement properties and their levels, and the shells the Worker Pool, Compute Requirement, resource and Node Action files put around their SDK models. The rule: a Work Requirement property is added to `WORK_REQUIREMENT_PROPERTIES` *and* given a row in `README.md`'s Work Requirement Property Dictionary, with the same levels marked, and `make schema_descriptions` is run — `tests/test_spec_properties.py` fails on a row with no property, a property with no row, a level that disagrees, a duplicate row, or a `spec_data/descriptions.json` that is not a fresh extraction. A dictionary property's description is the README row's and nothing else (`description=None` in the registry), so the customer-facing table is the single source; a nested fragment's properties (the task data inputs and outputs, a Group's roles) and every shell property carry their own `description` in the registry, since no README row describes them. The dictionary is the reference for levels unless a loader contradicts it. `property_names.py`'s type comments stay as documentation, and a test holds them to the registry's fragment types.

`utils/specs/schema.py` builds each family's schema when asked, never from a stored copy, so a newer SDK is described the moment it is installed. What *is* stored is the compiled validator (`utils/specs/schema_cache.py`): fastjsonschema's code generation and Python's compile of the result are nearly all of the check's cost (the Resources family's code is 1.3MB of source, ~130ms on Apple silicon and several times that on an older machine), while building the schema is a few ms and checking a document a fraction of one, so the cache is keyed on a digest of the schema as built each run and cannot outlive the SDK that shaped it. It lives under the system's temporary directory deliberately, so that nothing the CLI leaves needs finding and removing: macOS and Linux age out or clear their temporary directories, and Windows' is cleared by Storage Sense or Disk Clean-up, which is less certain but bounded at `CACHE_KEEP` files per stem. The SDK side is `annotation_schema()`'s mapping table (`str`, `int`, `float`, `bool`, an `Enum`, `timedelta` as an ISO 8601 duration, `datetime` as `date-time`, `List`/`Set`, `Dict` with an enum key as `propertyNames`, `Optional` admitting null — a `null` added to the `type` or `enum`, or for a `$ref` or combinator `if` null `else` the schema — a dataclass as a `$ref`, a generic dataclass such as `Selection[T]` expanded inline with `T` substituted, a polymorphic base dispatched on its discriminator by `_polymorphic_dispatch()`, the `_dispatch()` shape, over `$ref`s to its members); **the rule is fail-loud**: an annotation outside the table raises `SchemaGenerationError` naming the model and field, and nothing falls through to an open schema, so a new SDK type is fixed by a row in the table rather than silently accepted. A polymorphic base's members are found as the SDK's deserialiser finds them (its leaf subclasses with a `type`/`action`/`errorType` discriminator), and `POLYMORPHIC_FAMILIES` is held to that by a test; a member's discriminator is the value its class declares, plus the short class name for the four families whose discriminator `resource_creation.py` reads and strips itself (`CLI_READ_DISCRIMINATORS`). The CLI's own departures from the SDK are named tables in the module, each with its reason: `FIELD_OVERRIDES` (the Allowance dates, read by dateparser), `SUPPLIED_BY_CONFIGURATION` (the usage properties the TOML file fills in a Worker Pool or Compute Requirement file), `NODE_ACTION_NOT_PASSED` (`action` and `nodeIdFilter`, which `yd-nodeaction` never passes, dropped in that family only: a Worker Pool file's `nodeEvents` is posted as written), `MEMBER_SHELL` (a compute source's `userDataFile(s)`), `CLI_REQUIRED` (`namespace` on the Compute Source Template, Compute Requirement Template and Configured Worker Pool, which `resource_creation.py` indexes with no default; the corpus's minimal variants that omit it are `resource_live.MISSING_NAMESPACE_FAILURE_NAMES`, and the corpus test asserts exactly those fail, on `namespace`). Three shapes are deliberate. The `{{variable}}` wrapping is `if` a variable `else` the schema, not an `anyOf`, and a resource or node action is dispatched on its `resource`/`type` by `if`/`then` rather than a `oneOf`, as a nested polymorphic member (a Compute Source Template's `source`, a Worker Pool's node actions) is on its discriminator and the Compute Requirement root is on whether `requirementTemplateUsage` is present, and an optional model admits null by `if` null `else` its `$ref` (a `{{variable}}` in a dispatch key matches no case and leaves the object unchecked, which cannot be helped), both because `fastjsonschema` reports an `anyOf` or `oneOf` failure as `cannot be validated by any definition` at the wrapper, where an `else` or `then` failure is the schema's own message with its path — and the repair, having no path inside a combinator, would blank the whole member and lose its other violations. And `build_schema()` returns a deep copy, because `fastjsonschema` rewrites every `$ref` it compiles in place, against the `$id`: a `$ref` dict shared between families sent the second family's compile to fetch the first family's `$id` over the network.

`schema.py` (`yd-schema`) is the one place a schema is turned into a file, and it does that at run time too, never from a copy shipped with the package: `--write <dir>` calls `build_schema()` for every `Family` and writes `<family>.schema.json` alongside an `index.json` naming the CLI and SDK versions that produced them — the index last, so a write failing part-way leaves none (or the old one) for `--check` to find, and an `OSError` is an error naming the path and exit 1, as `--check`'s unreadable index is — `--check <dir>` compares those two versions against `index.json`, then builds each family (a few ms each; fastjsonschema's compile, the expensive part, is not needed) and compares it with the file written, so a file edited, missing or left by another run is not reported up to date on the index's word alone; a printed family (`printing.print_json_text()`, the text as given, no colouring or wrapping) is byte for byte what `--write` writes (`schema_text()`), each file written atomically; the SDK's version comes from `version.sdk_version()`, the package metadata, so `--list` and `yd-schema config` import no SDK (`--check` does, since it builds every family), `--list` names the families, and a bare `<family>` prints that one schema to stdout. Nothing SDK-derived ships in the wheel: `pyproject.toml`'s package data for `yellowdog_cli.spec_data` is `descriptions.json` alone, the CLI's own property text extracted from the README, because a schema built from a bundled SDK snapshot would silently describe whatever SDK the wheel happened to be built against rather than the one actually installed — the same reasoning as `utils/specs/schema.py` building on demand rather than at import. `yd-schema` needs no configuration and no credentials, so like `doctor.py` it is a registry command running straight off `ARGS_PARSER`, on neither wrapper.

`utils/specs/validation.py` checks a specification at run time. **The hook rule**: a loader that reads a specification family calls `check_specification()` (or, for `yd-create`'s several files, `strip_schema_key()`, `warn_of_violations()` and `validate_all_and_exit()`) on the document once it is loaded — after the loader's variable substitution, Jsonnet evaluation, TOML conversion or CSV task expansion, so an unresolved `{{x}}` passes where the schema admits one and an `{{::}}`-unset property is already gone — and before anything uses it; the hooks are in `specs.loading.load_specification()`, which `yd-submit`, `yd-provision`, `yd-instantiate` and `yd-nodeaction` all load their file through (after the JSON/Jsonnet/TOML loader and any CSV expansion; `yd-submit` then calls `validate_properties()`, and `yd-instantiate` unwraps `requirementTemplateUsage` after it), and `load_resources.load_resource_specifications()` (per file, after the in-situ pass and before the source-directory stamp, for creation only: the schema is what `yd-create` accepts, and `yd-remove` reads only names). An ordinary run warns and goes on — **and is never refused by the schema itself**: `warn_of_violations()` catches a `SchemaGenerationError` or fastjsonschema's `JsonSchemaDefinitionException` from building or compiling the schema (a future SDK field the mapping cannot describe), prints one warning that the file went unchecked, naming the cause and `yd-schema <family>`, and returns no violations (as it does for any other exception from the check, a fault in it, which `--debug` re-raises, matching `warn_of_config_violations()`), so an SDK upgrade cannot stop every run until a CLI release, while `--validate` and `yd-schema` stay fail-loud and name the model and field; `--validate` (`VALIDATE` in the registry, on those five commands, `ARGS_PARSER.validate`) prints the violations as errors, records `{source, path, message}` for `--json` (whose document is therefore the array, `[]` when valid), and exits 1, or 0 with a line saying the file is valid; wherever it cannot check a document — no specification file (including `yd-submit`'s CSV-only run, whose document the CLI builds from the TOML configuration with task-level prototype properties no file may carry, and `yd-nodeaction` without `--actions`), `yd-submit --json-raw` (Platform JSON, not a specification) and `yd-nodeaction --status` — `--validate` is refused with an error, so it never exits 0 without having checked anything. Where `yd-submit`, `yd-provision` or `yd-instantiate` builds what it submits from the configuration, with no specification file, `specs.loading.refuse_file_options()` refuses `--jsonnet-dry-run` there too, which was ignored and let the command go on to submit. `$schema` (`SCHEMA_KEY` in `property_names.py`, in `ALL_KEYS`) is stripped by the hook, since a Worker Pool file is posted to the Platform as written and a resource's unknown key would be warned of by `_get_model_object()`. `fastjsonschema` stops at the first failure, so `validate_specification()` repairs each failure out of a copy of the document — deleting the properties an object must not contain, adding the ones it must, satisfying a one-of-these-keys `anyOf` (`ONE_OF_REQUIRED`) by adding its first alternative and a not-these-together `not` (a writeFile's content sources) by dropping the last key, each named in its own words (`must contain one of name, username, id`, `must contain exactly one of actions, actionGroups` for a `oneOf` of bare `required`s, repaired by adding the first or dropping all but the first, `must not have both content and contentFile`, a `pattern`, `anyOf` or `oneOf` failure as `must be <the node's description>` (so `_wrap_node()` keeps a hoisted description on the node too, unless it is a `$ref`), an enum as `must be one of a, b, c`, and for the properties deleted or added `unknown property 'nope'` and `missing required properties 'a', 'b'`, sorted) rather than fastjsonschema's, whose Python reprs (`must not contain {'nope'} properties`, a set in unstable order) never reach a user, replacing any other failing value with a `{{variable}}` token, which the wrapping admits wherever a value stands — and validates again, until it passes or the failure is the document's own, stopping at `MAX_VIOLATIONS` with a final `...and more` violation; fastjsonschema's path is its rendered name split on `.`, so `_locate()` joins parts back together to follow a key that contains one; the split is on `[` and `]` too, and a key containing either cannot be followed, so the repair loop stops there, after reporting that violation — documented in the module docstring rather than fixed. The tests hand every command's `ARGS_PARSER` mock `validate=False` and `jsonnet_dry_run=False` (`test_json_output.py`'s `_DEFAULTS` included): a `MagicMock`'s unset attribute is truthy.

The configuration file is the sixth family, `config`, and is checked in two parts. As the file loads, `load_config.py`'s `validate_properties()` runs exactly as it always has — before the `--property` overrides, `[dataClient]` profiles stripped, every key held to `ALL_KEYS` — and is still the only error: an unknown or deprecated key exits 3. Everything the schema adds is a warning, printed as a command starts by `warn_of_config_violations()`, which `main_wrapper` calls with `ALL_CONFIG_SECTIONS` and `dataclient_wrapper` with `DATA_CLIENT_CONFIG_SECTIONS` (the sections each kind reads; the subset also saves compiling the SDK-backed `[workRequirement]`), and `validate_config()` compiles the schema over only those of them the file actually has (`sections & frozenset(working)`, after its own key checks, which still use the full set to name an unknown section), so a file without `[workRequirement]` never compiles its SDK definitions — 36ms against 8ms for the rest on Apple silicon, before `specs/schema_cache.py` keeps either, straight after `warn_of_undefined_config_variables()`. Never as the configuration loads: `yd-doctor` loads it inside its checks, and warnings printed then would land in its table. It checks `_CONFIG_AS_WRITTEN`, a deep copy of `CONFIG_TOML` taken straight after the overrides and before any section loader pops or merges anything (`importCommon`, `[computeRequirement]` into `[workerPool]`), so a violation is named under the section it was written in and an unknown `--property` key, which `validate_properties()` never sees, is reported; it is `None` without a file (`--nc`, none found), and the `importCommon` file is not checked. `validate_config()` checks each section's top-level keys itself before the schema — a key in `ALL_KEYS` is `'<key>' is not read in this section`, anything else `unknown property` — because the schema's closed objects would call a misplaced key unknown. The rule: **a new configuration property goes in `CONFIG_SECTIONS` (for `[workRequirement]`, a dictionary property with the TOML level) and in `config-template.toml`, or `tests/test_config_schema.py` fails**; its fragment follows what the loader *accepts*, so a property the loader casts with `int()`/`float()` (`INT_CAST`/`FLOAT_CAST`) admits exactly what the cast takes — any number, a bool, and a string of digits with `_` separators, plus for `float()` a fraction, an exponent, `inf`/`infinity`/`nan` — as a type list with a `pattern`, never an `anyOf`, whose failure fastjsonschema reports as `cannot be validated by any definition`, and `validate_config()` rewords both of its failures (`_worded()`, by the property's fragment) as `must be an integer`/`must be a number`. A top-level key that is not a table is `'<key>' is not in a section`, a table that is no section `unknown section`. `warn_of_config_violations()` also catches any other exception from the check as one warning (re-raised under `--debug`), since the check is advisory and must never stop a command that would otherwise run. A key read but undocumented is caught too: `test_every_key_the_loaders_read_is_in_its_section` scans `load_config.py` for each `<x>_section.get(CONSTANT)` and `[CONSTANT]`, which is how `[workRequirement]`'s `workerTag`, a fallback with no dictionary row, came to be a registry entry of its own. `validate_config()` drops `None` values before checking, since TOML has none and one can only be a `--property section.key=null` unset. The SDK is imported only when a schema needs a model: `specs.sdk_models.model_class()` is the one place `yellowdog_client.model` is imported, so the `[common]` and `[dataClient]` schemas, and the data client commands that check only those, load no SDK. Once the version helpers and the shared utilities stopped importing it (see *Keeping the SDK out of start-up*), leaving this import eager would have been the last thing loading it for them. `warn_of_config_violations()` also returns at once when `printing.warnings_suppressed()` (`--quiet`, `--count-only`: `print_warning()`'s own rule) and not `--debug`, since it only warns and building a schema with an SDK-backed section imports the SDK — which Commander's `yd-variables --quiet` would otherwise pay on every discovery. `conftest`'s autouse `_no_config_snapshot` sets the snapshot to `None` for every test, since the test process loads whatever `config.toml` the checkout holds as it starts (`conftest.py`'s `pytest_configure()`).

## Modules

```
├── schema.py                    # yd-schema: prints, writes and checks the specification schemas; a registry command on ARGS_PARSER with no wrapper, like doctor.py; STANDALONE, ToolKind.READ_ONLY
├── spec_data/                   # Package data for the specification schemas; named apart from schema.py so the two do not collide as yellowdog_cli.schema (a package directory shadows a same-named module)
│   ├── __init__.py              # Empty: makes the directory a package, for importlib.resources
│   └── descriptions.json        # The Work Requirement dictionary's descriptions as plain text, generated from README.md by 'make schema_descriptions' (scripts/extract_schema_descriptions.py); never hand-edited
    └── specs/                   # The specification files: the CLI's own properties, the schemas, their compiled cache, the run-time checks and the loader
        ├── properties.py        # The typed registry of the CLI's own specification properties, the ones no SDK dataclass describes: Level (the dictionary's TOML/WR/TGrp/Task columns), SdkRef (a fragment the schema generator resolves against the installed SDK), Property; WORK_REQUIREMENT_PROPERTIES (one per README dictionary row; `inherited=False` for `name` and `tag`, whose rows say so), WORKER_POOL_SHELL, COMPUTE_REQUIREMENT_SHELL, RESOURCE_SHELL (per resource type, the keys its creator reads beside its SDK model's), COMPUTE_SOURCE_SHELL (the userDataFile(s) a Compute Source Template's 'source' takes beside its compute source class's), ONE_OF_REQUIRED (the resource types that need at least one of several identity keys, which the generator expresses as an anyOf), NODE_ACTION_SHELL; the configuration file's CONFIG_COMMON, CONFIG_DATA_CLIENT, CONFIG_WORKER_POOL and CONFIG_SECTIONS (all five sections, [workRequirement] being properties_at(Level.TOML) and [computeRequirement] the same tuple as [workerPool]), ALL_CONFIG_SECTIONS, DATA_CLIENT_CONFIG_SECTIONS; properties_at(), load_descriptions() (spec_data/descriptions.json via importlib.resources)
        ├── schema.py            # The specification schema generator: Family (the six: work-requirement, worker-pool, compute-requirement, resources, node-actions, and config, the TOML configuration file), FAMILY_COMMANDS, build_schema() (a family's draft-07 schema from specs/properties.py and the installed SDK, wrapped once so a {{variable}} string stands for any value that is not a plain string), compile_schema() (fastjsonschema, cached per family), build_config_schema()/compile_config_schema() (the config family over a subset of sections, the others admitted as they are, cached per subset), model_schema() (a dataclass as a closed object: exactly settable_properties(), required as the SDK says), annotation_schema() (the type mapping, raising SchemaGenerationError naming model and field for anything it does not know), polymorphic_members() (a base's concrete classes, as the SDK's own deserialiser dispatches them); imports nothing from args.py, wrapper.py or printing.py
        ├── validation.py        # Run-time validation of a loaded specification: Violation (path, message), validate_specification() (every violation, found by repairing each one out of a copy and validating again), warn_of_violations() (one print_warning() per violation, on stderr under --json), validate_all_and_exit()/validate_and_exit() (--validate: the violations as errors and {source, path, message} records, exit 1, or a valid line and exit 0), strip_schema_key(), check_specification() (the hook: strip, then --validate or warn), validate_config() (the configuration file: each section's top-level keys checked here, a key another section reads reported as misplaced and anything else as unknown, then the repair loop, _violations(), over the rest)
        ├── loading.py           # refuse_file_options(what, validate=..., jsonnet_dry_run=...): '--validate' and '--jsonnet-dry-run' refused where yd-submit, yd-provision or yd-instantiate has no specification file and builds from the configuration; load_specification(path, what, family=..., ...): the one loader yd-submit (with '--json-raw'), yd-provision, yd-instantiate and yd-nodeaction read their specification file through -- '--jsonnet-dry-run' refused for a file that is not Jsonnet and an extension the command does not take refused (or, with other_extensions_as_json, the three Worker Pool commands' way, read as JSON), both before anything is read; 'Loading <what> data from' printed; the JSON, Jsonnet or (toml=True, yd-submit's) TOML loader, or its CSV-expanding counterpart given a CsvExpansion; then check_specification() for the family (None for '--json-raw', Platform JSON with no schema). yd-create and yd-remove keep load_resources.py
        ├── schema_cache.py      # compile_validator(): a schema compiled by fastjsonschema, its code object kept marshalled between runs under the system's temporary directory (per user, mode 0700 on POSIX, refused if a symlink, another user's or open to others), named by stem and a digest of the built schema, fastjsonschema's version and the interpreter's, the `CACHE_KEEP` (4) most recently used files per stem, a hit touching its file, since the directory is the user's and two environments building different schemas (tox's interpreters, pipx beside a venv) deleted each other's file on every run when one was kept; cached code that raises as it loads is recompiled, as a corrupt file is; any failure compiles as without it, and is handed to the reporter the two wrappers register as a command starts (`report_problems_to(print_debug)`, beside `enable_undefined_variable_warnings()`), once per reason per process — a file not cached yet is never reported, and `yd-doctor`, on neither wrapper, registers none; specs/schema.py's compile_schema() and compile_config_schema() are its callers; imports nothing from the CLI; conftest's autouse _session_schema_cache points _temp_root() at a session directory and clears the reporter
        └── sdk_models.py        # The SDK-model knowledge the corpus gate (tests/resource_models.py) and the specification schemas share: MODEL_FOR_RESOURCE/DYNAMIC/DYNAMIC_MODELS, the polymorphic class sets and POLYMORPHIC_FAMILIES, RESOURCE_TYPES (create_resources()'s dispatch), the evidenced exclusions (SERVER_ASSIGNED_COVERAGE, NOT_SETTABLE, NOT_TESTED), model_class(), nested_model_class(), settable_properties(), required_properties(); never imports resource_creation.py, which imports the SDK at import
```
