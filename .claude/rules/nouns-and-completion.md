## Nouns and Verbs

`utils/noun_registry.py` maps each noun (`yd workrequirement`, short form `yd wr`; `yd taskgroup`/`yd tg`, `yd task`, `yd workerpool`/`yd wp`, `yd computerequirement`/`yd cr`, `yd instance`, `yd node`, `yd worker`, `yd resource`, `yd allowance`, `yd data`, `yd cloudinfo`, `yd jsonnet`) and verb to a registry command, and `NOUN_COMMANDS` holds a `Command` derived for each (`derive_command()`: `dataclasses.replace()` of the registry command, named `yd <noun> <verb>`, `runs` the registry name; `Noun.name` and `Noun.alias` are the bare words, `workrequirement` and `wr`). A derived command keeps every option of its registry command, so the command's code reads `ctx.args` unchanged, but **hides** those that do not apply to the object (`help=SUPPRESS`, refused if given a value other than the parsed default by `_check_hidden()`; `Command.offers()` is false for them, and `mcp_excluded()` excludes them), supplies its **fixed** arguments (`yd-list`'s entity type, `yd-cloud-info`'s type, `yd-resize`'s `--compute-requirement`), hidden but not refused, overrides a positional's `nargs`/`metavar`/`help` by option identity, and holds its **targets** to the object's kinds (`Targets`, `target_kind()`: a YDID type, `INSTANCE` for `cr_id.instance_id`, or `NAME`); a verb whose registry command takes IDs alone (`show`, `follow`, `wait`, `compare`) takes names where its `Targets.named` gives the type a name stands for, which the target check records on the parsed arguments (`NAMED_TARGET_TYPE_DEST`, `CLIParser.named_target_type`) for the registry command's own checks, and which the command hands to `utils/named_targets.py` to replace each name by its ID before anything else is done. An ID-only verb (`yd instance`, `yd node`) gets `nargs='+'` and hides `--sort`, `--reverse`, `--namespace`, `--tag` and `--interactive`, so it can never fall back to selecting Compute Requirements by namespace. The verb's own validators run before the registry command's, which may change values. `yd-list`, `yd-show`, `yd-follow` and `yd-wait` are `GENERIC_COMMANDS`: offered under each noun, type-restricted, and not deprecated; every other registry command a verb runs is in `REPLACED_BY_VERBS` (with its noun forms, a `script=False` command's included), and the rest (`yd-application`, `yd-cloudwizard`, `yd-doctor`, `yd-init`, `yd-variables`, `yd-schema`, `yd-status`, `yd-format-json`, `yd-help`, `yd-version`) are utilities; `tests/test_noun_commands.py` requires every registry command to be exactly one of the three, so **a new command is given a verb, made generic or kept as a utility on purpose**.

`noun_dispatch.run_noun()` takes the verb from `argv[1]` (a noun with no verb prints its help to stderr, exit 2; `--help` to stdout; an unknown verb or an option before the verb is a usage error), calls `invocation.select_command(derived name, invoked prog)`, rewrites `sys.argv` to `[argv0, *fixed, *rest]`, and imports and runs the registry command's module; `CLIParser` reads the selection in place of `argv[0]` when `ARGS_PARSER` is built. `CLIParser.command` is then the derived command, `command_name` the registry name (so `events_as_json`'s `yd-follow` check holds under `yd workrequirement follow`), and `parser.prog` the form typed (`yd wr submit`). `CLIParser.replaced_by` holds a deprecated `yd-*` command's `yd` forms (`top_level.SCRIPT_FORMS`: a verb's noun forms, or `yd list` for `yd-list`) when `argv[0]`'s basename is literally its name (`invoked_name()`; `python -m`, as Commander and the MCP server run commands, gives the module's file and is never deprecated), and `command_runner.warn_if_deprecated()`, in `prepare_run()` after the output settings, warns on stderr (`print_warning(stderr=True)`, so `--quiet` suppresses it); the commands off the wrappers warn themselves, `yd-doctor` and `yd-schema` through `warn_if_deprecated(ARGS_PARSER)` and the standalone parsers and the two launchers through `top_level.warn_if_deprecated_script()`. `command_named()` resolves a registry name, a noun form, an alias form (`yd wr submit`) or the `yd` form of a registry command no verb replaces (`yd list`, but not `yd submit`), and Commander adds its options only to a command it resolves; `module_invocation()` gives the module `python -m` runs and the arguments that come first: every `yd …` command runs the dispatcher (`python -m yellowdog_cli.yd wr submit`), so a child shows the form typed in its usage and errors and is refused what `yd` refuses (`yd submit`), and a `yd-*` name runs its own module, or the dispatcher, which reports it, when this installation has none — never a `yd-*` command found on the `PATH`; Commander's `host.cli_program()` and the MCP server's `command_argv()` (given each tool's `yd` form, `ToolSpec.program`) share it; and `typed_command()` reads a typed command line into the command and its arguments, which Commander's command box uses. The registry commands keep their names in code, comments and tests; user-facing text (messages, help, docs) names the `yd` forms.

**`yd` itself** (`yd.py`) reads the word after it from `utils/top_level.py`'s `TOP_LEVEL` (a noun or alias, a registry command no verb replaces, or an `OTHER_COMMANDS` entry, each a word less `yd-`, built from the registries; `tests/test_top_level.py` holds that no word stands for two things), hands a noun to `run_noun(noun, invoked='yd <word>')` and selects a command (`select_command('yd-list', 'yd list')`) before importing only its module, so start-up stays SDK-free. The standalone commands build their parsers from the registry too (`build_parser(COMMANDS[name], prog=selected_prog(name))`: `yd help`, `yd version`, `yd format-json`, `yd completion`, `yd init`, and the `yd jsonnet` verbs, `tojson` (`yd-jsonnet2json`), `fromjson` (`yd-jsonnet-fromjson`) and `factor` (`yd-jsonnet-factor`), a noun's verbs running standalone commands), so completion, Commander, the MCP catalogue and the parser snapshots see their options; the two launchers, which are no registry commands, keep parsers of their own, and they too take their prog from `invocation.selected_prog()`. `yd` with no word prints `yd help`'s listing on stderr (exit 2); `-h`/`--help` on stdout.

**Shell completion** (`yd completion`, `utils/completion.py`) reads the same registries, so a new noun, verb or option completes with nothing added; what it cannot infer is whether an option's value is a local file or directory, which the option states with `completes=Completes.FILE`/`DIR` (`option()`, `Option(...)`, or `variant(completes=...)`, which a variant that changes what the value is must use, as yd-nodeaction's `--worker-pool` name does), held to the metavars by `tests/test_completion.py`. Values are offered from `choices`, `SORT_KEY_TYPES`, `_TYPE_VALUES` (entity and Cloud Info types) and `_VERB_VALUES` (a verb that narrows a value by a check of its own, `yd resource list`); hidden options and fixed positionals never. The stubs register `yd` alone and call `yd completion --complete <shell> <index> <words...>` (the current word `words[index]`, or empty when absent, since PowerShell 5.1 drops an empty argument) and must keep `IFS` default while passing words: bash 3.2, macOS's, joins an array slice into one word otherwise. Bash and zsh pass every word as typed and fish and PowerShell the current one, so `completion_reply()` reads them through `unquoted()` (`-t ''` is the empty tag, `'my ns'` a namespace with a space); `join_bash_words()` takes off the prefix readline keeps whether bash split the word at its last `=` or `:` (bash 4 and later) or not (3.2); and a file or directory after `--option=` is completed after the `=` by each stub (bash's `${cur##*[=:]}`, zsh's `compset -P '*='`, PowerShell's `CompleteFilename()` on the part after it, its own path completion taking the option for part of the path). `complete()` offers the words after `yd` first (`TOP_LEVEL`, no deprecated name), then works on the noun's verb or the command. A command whose arguments the registry does not describe — `OTHER_COMMANDS` (`yd commander`, `yd mcp`), which have no registry options — completes its arguments as local files (`Mode.FILES`, `--help` after a `-`): the stub claims `yd`, so answering nothing would take away the shell's own file completion, which `yd commander`'s configuration file relies on; a file argument the registry describes is marked `Completes.FILE` instead, as `yd format-json`'s and the `yd jsonnet` verbs' are. A deprecated `yd-*` command is not completed. `OTHER_COMMANDS` lives in `command_registry.py` (help.py imports it), so completion never imports `help.py`'s Rich. **Names and IDs come from the Platform without `complete()` making a call:** for an argument in `completion_targets.LOOKUPS` (keyed by verb and a positional's name, or an option's long flag: `--within`, whose lookup for `yd list <type>` is `WITHIN_LOOKUPS[type]`, the type typed resolved as the command resolves it; a `Lookup` that is not `tagged` ignores the configured tag, and one with `task_groups` offers, after `wr/`, that Work Requirement's Task Groups as `wr/tg`, and one with `tasks` too, after `wr/tg/`, the Task Group's Tasks as `wr/tg/task` in its `task_statuses` (`namespace/wr/` read as a Work Requirement's where no such Task Group is found); an `ET_INSTANCES` or `ET_NODES` lookup offers IDs from the newest `LOOKUP_MAX_PARENTS` Compute Requirements or Worker Pools in its `parent_statuses`, the Platform searching them one parent at a time, or, after `cr_id.`, that Compute Requirement's Instances; one `scoped_by` an option (`yd node action --node`, by `--worker-pool`) is given that option's typed value as `LookupRequest.scope`, and offers that one Worker Pool's Nodes; after `--type` on a remove's or a show's targets (`RESOURCE_TARGETS`), `RESOURCE_LOOKUPS[type]`, whose `resource` names the type `completion_lookups._fetch_resources()` reads, a Credential's after `keyring/`) it returns a `LookupRequest` (the lookup, the word, the configuration options typed on the line, captured by option identity as the CLIParser properties `load_config` reads, and the names already typed, which are not offered again); an option word is read as argparse reads it (`_option_in()`: `--flag=value`, an unambiguous abbreviation of a long flag, a short flag with its value attached, a value-optional flag given none taking its `const`), with the option names as the fallback when nothing is typed, and `yellowdog_cli/completion.py` makes it through `completion_lookups.candidates()` on a daemon thread given `LOOKUP_TIMEOUT_SECONDS`, abandoning it with `os._exit(0)` once the answer is written. While a request is answered, descriptors 1 and 2 and `sys.stdout`/`sys.stderr` point at the null device and the answer goes to a duplicate of the real stdout, since `load_config`, the SDK and every library print. Lookups are off by default: a script printed with `yd completion <shell> --names` runs `yd completion --complete --names ...` (`completion_script(shell, names=True)` rewrites the stub's one `--complete` call, so the choice lives in the start-up file's line), and only then does `completion_reply()` make one; `yd doctor` reports whether that line has `--names`. `YD_COMPLETION_LOOKUPS` (`off`, `0`, `false`, `no`) switches them off even then, never on, and `conftest` sets it for the whole test session so no test's completion reaches the Platform: a lookup test clears it. A verb's statuses are written as SDK member names in the table, held to the enums and to the commands' own sets by `tests/test_completion_targets.py`, so a command that changes what it acts on changes the table too. Local completion still imports no SDK; a lookup is the one Tab that does. The stubs are run in each shell present by `tests/test_completion.py`, PowerShell's under each of `pwsh` and Windows PowerShell 5.1's `powershell` found; `.github/workflows/windows-tests.yml`, which runs the whole suite on Windows, runs those under both, checking both are present, since 5.1 exists on Windows alone.
