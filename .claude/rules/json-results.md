## The `--json` Result and Exit Codes

With `--json`, stdout holds one JSON document, the command's result, and the exit code names the kind of failure; the contract, shapes and codes are in *Machine-readable Output and Exit Codes* (`docs/json-output.md`). `utils/results.py` is the accumulator: a command calls `record()` for each outcome (a dict, or an SDK object, serialised as `yd-list` serialises it) or `record_document()` for a one-object result, and both wrappers call `flush_results()` after `main()` returns and, on an exception, a `SystemExit` or a keyboard interrupt, before exiting — so a failure part-way still reports what was done, bar a `SystemExit` of 2 or 3 with nothing recorded (`results.nothing_recorded()`), a usage or configuration error found as the command starts, which leaves stdout empty as argparse's and the loader's do; under `--debug` the failure's traceback is logged to the trace first, and its exit code is the same. The failure branches set the exit code *before* flushing, and flush through `flush_results_after_failure()`, which reports a flush that fails (an unserialisable record) rather than letting it escape or turn the failure into exit 0. Both wrappers also check `any_failed()` straight after a *successful* `main()` and its flush: a command that caught its own error, recorded it as `failed` and returned normally (e.g. `yd-boost` on a 404; a 401, a `SESSION_FAILURES` failure, raises `ReportedFailure` instead) would otherwise exit 0, so this is checked with or without `--json`, since the records exist either way; it sets the exit code and suppresses the `Done` print, without touching what was already flushed. The code is `results.failure_exit_code()`: the cause every failure shares when each was recorded with one (`record_failure_cause()`, which `action_runner.py`, for an `Unresolved` target (its `code`, else its `__cause__`'s) or a failed unit, `yd-shutdown`'s own failures, and `yd-abort`'s and `yd-nodeaction`'s record helpers (their `cause`) call beside each `failed` record), else `FAILURE`, so `yd wr cancel <no such name>` exits 6 and a refused cancel 5. `yd-cancel`, `yd-shutdown`, `yd-terminate`, `yd-delete` and `yd-download` take `--json` with or without `--dry-run`: the real, acting path records through `record_action()`/`record_deletion()`/`record_transfer()`. The flush does nothing without `--json` (`json_output` is `None` on a command without the option), prints once, and prints `[]` when nothing was recorded. A command that prints its own JSON through `print_json()` gets no flush (`printing.json_document_printed()`): that is the rule, since `yd-show`, `yd-list`, `yd-application`, `yd-variables` and `yd-doctor` keep printing their own documents, but JSON printed any other way would still get a trailing `[]`. A command that prints its own document *and* records is a mistake, and `flush_results()` raises a `RuntimeError` saying so rather than printing a second document. `results.py` must never import `wrapper.py` or `load_config.py`, which import it. `utils/exit_codes.py`'s `classify()` maps what reaches a wrapper to an `ExitCode` (defined there): typed checks first (the CLI's own `NotFoundError`, an `HTTPError`'s `response.status_code`, the SDK's `NotAuthorisedException`, `InternalServerException` and `ServerErrorException`, `requests` connection errors and timeouts), then the `MissingPermissionException` and `Unauthorized` text checks the wrapper's friendly messages also key on (`MISSING_PERMISSION_TEXT`, `UNAUTHORIZED_TEXT`), then the exception's `__cause__`, else `FAILURE` — so **a failure re-raised with a clearer message must be raised `from` the original**, or it loses its code, and a missing entity is raised as `NotFoundError`, never `KeyError`; a `SystemExit`'s code passes through. `load_config.py`'s and `variable_substitution.py`'s configuration-time exits use `ExitCode.CONFIGURATION`; a command that catches a failure itself exits `FAILURE`, except a `SESSION_FAILURES` one (authentication, connection) that stops an action command: having recorded the failing item and the not-attempted rest, the command raises `exit_codes.ReportedFailure(cause)`, which both wrappers exit on with the cause's code (`classify()` follows `__cause__`) without printing it again. Never raise it `from` anything: `from None` clears the cause the code comes from. `utils/action_runner.py` (for the commands on it: `yd-cancel`, `yd-shutdown`, `yd-priority`, `yd-token`, `yd-boost` and those on `compute_action_common.py` and `start_hold_common.py`), `abort.py`, `nodeaction.py`, `show.py`, `compare.py`, `follow_utils.work_requirement_exit_code()` (for `yd-submit -E`) and `utils/resource_processing.py` (for `yd-create` and `yd-remove`) do (`nodeaction.py` also raises it for a faulty specification whose faults it has printed, and for a `--follow` that `--timeout` cut short); `create_resources()` and `remove_resources()` otherwise carry on past a failed specification (or ID), printing each failure once, naming the resource (a creator or remover raises rather than printing first), and finish by raising `ReportedFailure` whose cause is the failures' shared cause, or a `RuntimeError` for different causes, so they exit by cause like `yd-wait`; the Cloud Wizard, which calls `create_resources()`, still sees it raise, and its `remove_resource_by_id()` still returns `False` on a failure, having reported it, except that a `SESSION_FAILURES` failure is raised as `ReportedFailure` once recorded: `CommonCloudConfig._remove_yd_templates_by_prefix()` then records the rest as not attempted (`record_not_attempted()`), keeps the failure in `platform_failure` and skips the Keyring, the provider's own (cloud-side) removals still run, and `run_operation()` raises it, so a teardown exits with the failure's code and a second one removes what was left; Azure setup keeps a session failure creating its credential, its last Platform call, in `platform_failure` the same way, and `run_operation()` raises it after setup, once the resource file is saved and the Keyring's details shown. `yd-remove` recognises an argument that is a YellowDog ID (`--ids`, which says they all are, is optional and says so), and removes files and IDs given together in one run in removal order (`remove_resources_and_ids()`, an ID ranked by its resource type); it fetches each resource it removes by ID before confirming its removal (`_removable_by_id()`, a table per YDID type), so an ID that does not exist is `NotFoundError` (exit 6) without a prompt. `yd-create` makes a Group's, Application's or User's memberships match a `roles`/`groups` list, so `[]` removes them all, but are left alone without one, and every name in the list is resolved, one that does not exist failing the resource, before anything is changed, since reconciling against a list with a misspelt name would remove the membership it meant. Under `--json`, `print_warning()` writes to stderr (`CONSOLE_ERR`, or `sys.stderr` under `--no-format`) rather than being dropped, and `interactive._get_user_input()` writes its prompt to stderr, so stdout still parses. **The rule for new code: a site that reports an outcome with `print_info()` also calls `record()`**, since `--json` silences the one and only the other reaches the script. The seventeen action commands (`yd-cancel`, `yd-shutdown`, `yd-terminate`, `yd-start`/`yd-hold` in `start_hold_common.py`, `yd-finish`, `yd-abort`, `yd-resize`, `yd-boost`, `yd-priority` (one `update_work_requirement` per Work Requirement, to a copy fetched just before it, recording `previousPriority` and `priority`), the five `yd-compute-*` in `compute_action_common.py` (`yd-compute-restart` and `yd-compute-deprovision` taking Instances and Nodes only, their `ComputeAction` having no `cr_method_name`, and `yd-compute-reprovision` Compute Requirements only, having no `instance_method_name`), `yd-auto-shutdown` on the same module (Compute Requirements only, its records carrying the `autoShutdownTime` the Platform set), and `yd-token`, whose refresh and regenerate records carry the new `token` and `expiryTime`) do so through `record_action(entity, entity_type, action, outcome, error=None, **extra)`, beside every print of what was done, skipped (declined, filtered, already in that state) or failed; `entity` is an SDK object, an `{id, name}` dict, or a string the command was given (a YDID becomes the `id`, anything else the `name`). An Instance is recorded as `{"id": "<cr_id>.<instance_id>", "name": "<instance_id>"}`, the form those commands accept. `yd-shutdown --terminate` records each Compute Requirement it terminates as a `compute-requirements` record with action `terminate` and an extra `workerPoolId`, its `id` `null` when the pool could not be fetched for it — never the pool's ID under the Compute Requirement's type; a Configured Worker Pool, which has none, is warned of and not recorded. `shutdown.py` runs through `action_runner.py` like the others (resolve in the order given, `Unresolved`, confirm once, act, a `SESSION_FAILURES` failure recording the rest as not attempted); its units report and record their own failures, `--terminate`'s included, and raise `SessionStop` for a session failure. `yd-resize` re-raises a failed resize after recording it, so the wrapper still exits non-zero with the record emitted, and records a failure to find its target the same way (`_found()`: not found, ambiguous, or the lookup's own failure, a 401 or a lost connection included), as the action commands on `action_runner.py` do. Their `--json` is `ACTIONS_JSON` in `command_registry.py` (`DRY_RUN_JSON` for `yd-cancel`, `yd-shutdown` and `yd-terminate`), both spelled without `-J`. `yd-create` and `yd-remove` record through `record_resource(resource_type, name, id, action, error=None, **extra)` at every created/updated/unchanged/removed/skipped site, the Image Groups and Images of an Image Family included (`unchanged` is `yd-create`'s for an existing resource `resource_plan.plan_one()` finds unchanged, left alone without a prompt by `_create_all()` unless `--dry-run` or `--force-update`), and in `create_resources()`/`remove_resources()`'s failure branches, the name coming from `load_resources.resource_display_name()`, read before the creator pops anything from the specification; a real `yd-create` run then prints a summary counting its own records by action (`_print_summary()`, over `results.records_since()` from the `record_count()` taken as it starts, so a Cloud Wizard run counts only its own), before any failure is raised and never under `--dry-run` or `--json`; `yd-create --dry-run --json` records each processed specification with `record()` instead of printing it (`_show_dry_run_specification()`, which takes the resource type and puts `resource` back as the record's first key, since `create_resources()` popped it and a mixed file's array would otherwise be untyped; the printed form still omits it), and records no failures, so its document is the array of specifications, and a Jsonnet dry run under `--json` from a loader that converts several files (`exit_on_dry_run=False`) records a copy of each. `yd-resource-plan` (`utils/resource_plan.py`'s `plan_resources()`) records one `record_resource()` per specification, its `action` `create`, `update`, `unchanged`, `unknown` or `failed`, with `changes` (`{path, from, to}`, through `_recorded_value()`, so User Data is summarised) wherever the entry has them and `reason` on an `unknown` (a Configured Worker Pool whose name is taken is `failed`, as the Platform refuses it), failures going through `process_each()` as `yd-create`'s do; `--fail-on-changes` exits `FAILURE` after the plan and its records when anything is `create`, `update` or `unknown` and nothing failed, a failure's own `ReportedFailure` taking precedence. `yd-resource-export` (`utils/resource_export.py`'s `export_resources()`) prints its own document, the specifications through `print_json_text()`, when there is no `-o`, so it records nothing then; with `-o` it records one `record_resource()` per resource once the file is written, `id` always `None`, `action` `exported` or `skipped`, and `reason` for a skipped resource's failure or a dependency's referrer (`a dependency of <name>`), a failed search recorded with the type word and no name, and a dependency that could not be looked up with its resource type and the reference's name. A per-resource failure is printed, kept, and once the rest are written raised as `ReportedFailure` with the first failure's cause; a `SESSION_FAILURES` failure propagates from the read, before any file or record. Its `-o` has a `dest` of its own (`export_file`), since the universal `--output-file` would send the records into the file in place of the specifications. `yd-submit`, `yd-provision` and `yd-instantiate` call `record_entity()` straight after the Platform call, and under `--dry-run --json` `record_document()`/`record_document_part()` in place of the print; `record_document_part()` makes the document the one part, or the array of them once batching adds a second. `yd-resubmit` records as `yd-submit` does, `record_entity()` of the new Work Requirement (or the `--add-to` target) with the extra fields `resubmittedFrom` (the original's ID) and `taskCount`, one `record({"file", "resubmittedFrom", "taskCount"})` under `-o`, `[]` when no Task is selected, and under `--dry-run --json` the document as `-o` would write it, or, with `--add-to`, the target's `record_entity()` with `appendedTaskGroups` (the names of the Task Groups that would be appended) added. The creators' `--quiet` bare IDs go through `printing.print_quiet_result()`, which prints nothing under `--json`, so `--quiet --json` is the document alone. Those three also carry `check_json_excludes_streaming()` (`command_registry.py`), which refuses `--json` with `--progress` or `--report`: the Rich progress bar and the template report both write to stdout. `--follow` alone reports through `print_info()` and is allowed. A Configured Worker Pool's record carries its `token` and `expiryTime`, as an Application's carries its key, since `--json` silences the prints that show them. The remaining commands: `yd-wait` records `{id, name, status, succeeded}` per ID given, in the order given, and treats an entity not in a terminal state when following ends (its `--timeout`, passed to `follow_ids()`, or a lost stream) as a failure, exiting with the single cause's code (`follow_exit_code()` for a lost stream) or 1 for a Work Requirement failure or mixed causes; `yd-follow`'s `--json` prints each event as a JSON document (`print_event()` keys on `OUTPUT.events_as_json`, configured from the `events_as_json` property in `args.py`, true for that command alone, so an action command's `--follow --json` prints no events) and `main()` calls `results_are_streamed()`, so nothing, not even `[]`, follows the events; `check_follow_json_excludes_progress()` refuses it with `--progress`, whose bar consumes the events. The data client records in `dataclient/operations.py`, per file for the three transfers (`record_transfer()`, the listing of a remote directory's files done only when `json_requested()`, since it costs an rclone call) and per item for deletion (`record_deletion()`, with `name` and `isDir` beside `path` and `action`; `deletion_targets()` lists a path or a wildcard's matches once, so `yd-delete` confirms and deletes exactly those, a path already gone recorded `skipped` and a directory without `-R` `failed`, and `delete_item()` deletes one, recording it; `delete.py` refuses the remote's root and the configured bucket, and Commander's delete chooser offers only the `would delete` records). `yd-download`'s records add `match`, the top-level item each file belongs to, because Commander's download chooser offers top-level items and `selection.parse_download_summaries()` groups the per-file records back into them; yd-delete's records are what `parse_object_summaries()` reads. `yd-ls` records `lsjson_listing()`'s entries in place of printing its table, each with `Listing`, the remote path it was listed under; a path that does not exist, or cannot be reached, is an error (exit 1) while the other paths are still listed, but an empty directory or a wildcard matching nothing (`glob_matches(allow_empty=True)`) is an empty listing. `yd-compare` and `yd-nodeaction` record their tables with `rows_as_objects()`; where a message is printed despite `--quiet`, `yd-compare` passes `override_quiet=not json_requested()`, since `override_quiet=True` also prints under `--json`, and `yd-nodeaction` skips the print under `--json`. `yd-version` and `yd-help` are standalone and print their documents with `json.dumps(..., cls=CompactJSONEncoder)`.
