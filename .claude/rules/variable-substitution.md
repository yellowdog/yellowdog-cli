## Variable Substitution

Specs (TOML/JSON/Jsonnet) support `{{variable_name}}` substitution with type tags: `num:`, `bool:`, `array:`, `table:`, `format_name:`. Every value in the substitutions dictionary is a string, so a value arriving as something else has to be rendered as text: `_stringify()` does that, and renders it as **JSON** rather than with `str()`'s Python repr, because the tags read the value back as JSON — `array:` and `table:` with `json_loads()`, `bool:` as the JSON spelling — so a repr's apostrophes meant a TOML `strs = ["a", "b"]` could not be used as an array at all, and `true` was held as `"True"`. Two things it must *not* do, each with a test: a string is passed through untouched, since every value is re-rendered on each resolution pass and one given JSON's quotes would gain another pair every time; and a value with no JSON form falls back to `str()`, which is what keeps TOML's date, time and datetime values (`tomli` returns real `date`/`datetime` objects, which `json_dumps` raises `TypeError` on) rendering as the text they were written as. Three entry points need it, and all three were wrong: `_update_and_resolve_substitutions()`, the `[common.variables]` comprehension in `load_toml_file_with_variable_substitutions()`, and `add_or_update_substitution()` (which `load_config.py` calls for a `--property common.variables.x=...` override, whose value has already been JSON-parsed into a real list, dict, number or boolean). The type tags are `_TYPE_CONVERTERS` in `variable_substitution.py`, each tag with the function converting its value (`_number()`, JSON's syntax or Python's, finite; `_boolean()`, any case, any space around it; `_collection_of()` for `array:` and `table:`, reading JSON, refusing the NaN and infinities `json.loads()` accepts, and only where that fails a Python literal by `ast.literal_eval()` (which evaluates no code), held by `_json_form()` to what JSON could have held: strings for keys, finite numbers, no tuples, sets, bytes or complex numbers, each refused saying why rather than changed; `format_yd_name()`), and `TYPE_TAGS` and the tag regex in `process_variable_substitutions()` are built from its keys, so a tag cannot be recognised without a converter, and `process_typed_variable_substitution()` raises for one it does not know rather than returning `None`. Its errors name the expression as written (`Cannot substitute '{{num:x:=abc}}': 'abc' is not a number`). A typed expression inside a longer string is converted, so checked, and then written as text by `typed_value_as_text()`: as JSON, as `_stringify()` holds a value, but a number as written; it was `str()`, which wrote `True` and Python's `['p', 'q']`. And a typed expression whose name is still undefined once its nested parts are resolved (`{{num:x_{{y}}}}` with no `x_Y`; `_is_whole_expression()`) is passed through with its tag, as an untyped one is, for a later pass or the undefined-variable warning, rather than converted as its own text and reported as `'{{x_Y}}' is not a number`. Default substitutions are defined in `VARIABLE_SUBSTITUTIONS` in `variable_substitution.py`; `{{pid2}}` is `misc_utils.PROCESS_DISCRIMINATOR`, so a hand-written name can be disambiguated the same way a generated one is, and `{{pid}}` is the full PID (`misc_utils.PID`); `{{random}}` and `{{random6}}` are three and six base 36 digits from `misc_utils.random_base36()`, base 36 rather than hexadecimal because it is the widest alphabet a YellowDog name may be built from. Variable names follow one rule, `VARIABLE_NAME_PATTERN` in `variable_syntax.py` (a letter, digit or `_`, then letters, digits, `_`, `.` and `-`), checked by `check_variable_name()` at every definition source — the `YD_VAR_*` scan and `-v` parsing (`register_user_variables()`, run once by `ensure_config_loaded()` before the file is read, outside the command's exception handling, so they print and exit), `add_or_update_substitution()`, `add_substitutions_without_overwriting()` and `add_substitutions_from_config_file()`, each taking a `source` for the error (the `--property` override and `[dataClient]` profile registration catch it and exit) — and the same pattern builds `_VARIABLE_REFERENCE`, so a `{{...}}` whose name breaks it is text, not a reference: that is what makes the undefined-variable warning and the circular check exact rather than heuristic. The four sources a *user* writes — `YD_VAR_*`, `-v`, `[common.variables]` (in `add_substitutions_from_config_file()`) and the `--property common.variables.<name>` override (in `load_config.py`, ahead of `add_or_update_substitution()`) — call `check_user_variable_name()` instead, which also refuses `RESERVED_VARIABLE_NAMES` (`variable_syntax.py`: `namespace`, `tag`, `key`, `secret`, `url`), naming where each is set instead. Those five are registered by `load_config_common()` and `_load_namespace_and_tag()` with `add_substitutions_without_overwriting()`, so a user definition used to win in the table while `CONFIG_COMMON`, which every command acts on, kept the configuration's value — `-v tag=foo` changed `{{tag}}` and not the tag a Work Requirement was named with — and one unset with `{{::}}` was removed from the table and then simply defined again. The CLI's own registration keeps going through `check_variable_name()`, which is why the reserved check is a separate function rather than part of it; `tests/test_variable_names.py` holds both. `.` and `-` may not lead because `{{.ID}}` and `{{- ...}}` are other tools' syntax; an `env:` name is the OS's and gets `ENV_VARIABLE_NAME_PATTERN` (anything but whitespace and the syntax). Default values use `:=` separator. Environment variables via `env:` prefix. Nesting has no depth limit. Syntactic nesting (`{{a_{{b}}}}`) is resolved by recursion within one pass; a substituted value that reveals a further reference needs another pass, so every loader — the three spec loaders and `load_config.py`'s section loaders, via `_resolve_section_variables()` — calls `resolve_variables_insitu()`, which repeats `_substitute_insitu_pass()` until a pass reports no changed paths. Two things make a circular reference an error (`ValueError`, naming the properties) rather than a hang or a silent pass-through: values still changing after `VAR_SUBSTITUTION_MAX_PASSES` (10) passes, which catches mutually- and self-referring `env:` values; and, once settled, an expression left referring to a defined variable (`_unsubstituted_references()`, sorted by `_undefined_unless_circular()`), since a pass always substitutes a defined variable — this is what catches circular *table* variables, which `_update_and_resolve_substitutions()` resolves at definition to their own token (`p = '{{p}}'`), a value every pass then substitutes back to itself and so looks settled. The check uses the pass's own delimiters (and the Worker Pool ones for `userData`), so Mustache left for the platform is never mistaken for a cycle. An undefined variable is unchanged by the first pass and passes through, and the same walk (`_unsubstituted_references()`, which also looks inside a nested expression such as `{{template_{{x}}}}`) reports it with `print_warning()`, once per expression per process (`_UNDEFINED_VARIABLES_REPORTED`). Three things keep that honest. It is off until `enable_undefined_variable_warnings()`, which `main_wrapper` and `dataclient_wrapper` call as the command starts: the configuration's own passes run as it loads, before `namespace`, `tag`, `key`, `url` and `dataClient.*` are defined, and would report every one of them. A section resolved as the configuration loads and never again would therefore go unchecked, which is what the Worker Pool sections are: `load_config_worker_pool()` keeps a copy of each as resolved, before `computeRequirement` is merged into `workerPool` (`_WORKER_POOL_SECTIONS_AS_LOADED`, so a value is listed under the section it was written in, once), and `yd-provision` and `yd-instantiate` pass it to `warn_of_undefined_worker_pool_variables()` as `main()` begins — a check-only walk (`warn_of_undefined_variables()`) sharing the once-only record. Text is substituted the same way (the text passes and the specification loaders are `file_substitution.py`'s): `process_variable_substitutions_in_file_contents()` repeats its pass (`_substitute_file_contents_pass()`) until the text stops changing, under the same cap, and then applies the same circular check (`_undefined_unless_circular()`, shared with the in-situ resolver), naming the `source` its caller passes — the file. It serves User Data, Task Data and `writeFile` content files, which nothing walks afterwards (so a type-tagged expression there is written in this pass, never left for a later one: in quotes as its JSON, quotes and all, anywhere else as text by `typed_value_as_text()`, a number keeping its written form), and the Jsonnet loader's pass over the raw text; for Jsonnet that pass is before evaluation, so it is the only one that can resolve a chain the Jsonnet code computes with, and `load_jsonnet_file_with_variable_substitutions()` hands the substituted text to `_jsonnet.evaluate_snippet()` under the file's own name, with `jpathdir=[os.getcwd()]`, so imports resolve beside the file first and the current directory second, and errors name the file; it once wrote a `VariableSubstitutedJsonnetFile` copy into the current directory for `evaluate_file()`, which resolved imports from there, named the copy (`tmp7bbg02ql:3:6`) in errors, failed in a read-only directory and could leave the substituted copy behind. The pass is `_substitute_jsonnet_pass()` (`jsonnet=True`) rather than the plain text pass: `_JSONNET_LITERAL` lexes the strings (double, single, both verbatim forms, text blocks) and skips the comments, so that an apostrophe in `// don't` opens no string, and each expression, found by position (`misc_utils.find_delimited_expression_spans()`, since one expression can sit in strings needing different escaping), is read through its string's escapes (`_jsonnet_unescaped()`) and its value written back with them (`_jsonnet_escaped()`, which indents a multi-line value in a text block as the block is); outside a string a value is inserted as code, a typed one as its JSON, and a typed one that is a whole string (not a text block, which is left for the in-situ pass) replaces the literal, quotes and all. Each distinct expression is substituted once per pass, which with the scanner's compiled pattern cached per delimiter pair (`_inside_expression_pattern()`) took a 742kB file with 12,000 substitutions from 187ms to 56ms, against 15ms for the plain text pass. One exception in the text passes' circular check: a leftover type-tagged reference to a defined variable is never taken for a cycle, since the Jsonnet pass leaves a type-tagged expression inside a longer string for the in-situ pass after evaluation to substitute as text. A single value is substituted the same way again: `resolve_variables_in_string()` repeats `process_variable_substitutions()` until the value stops changing (a type-tagged result, a non-string and the unset marker are returned as they are), then applies the circular check and the undefined warning, naming its `source`. Every single-value site outside `variable_substitution.py` goes through it — in `load_config.py` via `_resolve_value()`, which exits on the error as `_resolve_section_variables()` does and names each `[common]` and `[dataClient]` value by its property (`key` and `secret` included, so their text is never a message); `resolve_remote_path()` names a path by itself — and `tests/test_variable_subs.py` fails if a bare `process_variable_substitutions()` call appears outside `variable_substitution.py` and `file_substitution.py`, whose text passes are the engine's own. It matters beyond chains: a single pass also made the undefined-variable warning call a *defined* variable undefined, because the warning assumes the value it is handed has been fully resolved, and a `--tag` or `YD_TAG` that is a chain generated names from the unresolved token (`envc1_...`), since a command-line or environment value replaces the config file's after the file's own passes. What is substituted other than by a walk checks its own result the same way. The configuration values resolved one string at a time as the configuration loads — `namespace`, `tag`, `url` and every `{{dataClient.*}}` value, read back from the variable table where they are registered resolved, credentials deliberately excluded — are checked by `warn_of_undefined_config_variables()` (`load_config.py`), which both wrappers call straight after enabling the warnings. File contents substituted as text — User Data files (`provision_utils._read_user_data()`), `yd-nodeaction` `writeFile` content files, Task Data files (`submit_utils._substituted_task_data_file()`) — each call `warn_of_undefined_variables({source: text})`, the source being the file, which is what the warning names; the data client paths (`resolve_remote_path()`) are checked by `resolve_variables_in_string()` itself, named by the path. The three file sites pass `per_source=True`, which records the pair (expression, file) in `_UNDEFINED_VARIABLES_REPORTED` rather than the expression alone, so each file of a `userDataFiles`, `contentFiles` or `taskDataFiles` list holding an expression is reported, while one file read for every Task is still reported once; `_read_user_data()` substitutes and checks each file of the list separately for the same reason, rather than the concatenation under all their names. `yd-variables` checks the variables it reports (every one, or those named, less `key` and `secret`) with `warn_of_undefined_variables()`, since the table is resolved as the configuration loads and so never checked otherwise. Its output follows `yd-show`'s, the other command whose output is always JSON: warnings ahead of the JSON and the wrapper's `Done` after it, on stdout, and `--quiet` for the JSON alone. It used to set `ARGS_PARSER.json_output` itself, so that its JSON came out alone without `--quiet`, but `json_output` means the user asked for JSON output with `--json` and gates `print_warning()` too, so it hid the warnings; routing them to stderr, and then exempting them from the gate, were both tried and dropped in favour of the CLI's ordinary convention. Commander therefore passes `--quiet` in `_yd_variables_command()` — before it did, `main_wrapper`'s own `[common]` check could print onto stdout ahead of the JSON and break discovery's parse — and `test_commander_config_discovery.py` holds it to that, while `test_variables_command.py` runs the same shape of command with a warning due and parses the result. It also explains a variable the `::` syntax removed (`explain_unset_variable()`, every one of them in the full report, via `get_unset_variable_names()`), which would otherwise report `null` exactly as one never defined does. That works from `_DEFINITIONS` in `utils/variable_substitution.py`, each variable's definition as written, because the table cannot say why — the variable is gone from it. `_update_and_resolve_substitutions()` records a merged value as a new definition unless the table already held it (a resolved value, not a definition), and `add_or_update_substitution()` records its own. The same record lets the undefined-variable warning (`_warn_of_undefined()`) say that a reference is to a variable that is *unset*, and why, rather than 'not defined', which sends the reader looking for a typo. The lazy variables `yd-submit` defines per Task Group and Task (`LAZY_VARIABLE_NAMES` in `variable_syntax.py`) are never reported, since the loader passes run before they exist. For the same reason a Task Group's and the Work Requirement's properties, substituted as the Task Groups are built, still hold `{{task_name}}` and `{{task_number}}` when a Task inherits them, so `task_generation._TaskLevels` substitutes each inherited value for the Task in a copy (as `update_config_work_requirement_object()` does the configuration's), and `_task_data_for_task()` the inherited `taskData*`; a value with no `{{` is passed on uncopied. And only an expression shaped like a reference — optional type tag, optional `env:`, then a name — counts (`_VARIABLE_REFERENCE`), so Docker's `{{.ID}}` or a Go template's `{{ .Values.x }}` in a task argument is left alone; a bare word such as Go's `{{end}}` would still be reported, which is why this is a warning and not an error. Every in-situ pass outside `variable_substitution.py` goes through `resolve_variables_insitu()` — the late passes in `submit.py`, `csv_data.py`, `load_resources.py`, `submit_utils.py` and the Cloud Wizard included — and `tests/test_submit_utils.py` fails if a single-pass `process_variable_substitutions_insitu()` call reappears.

The `::` unset suffix (`{{varname::}}`) removes a property entirely when the variable is undefined; if defined, its value is used normally. The bare `{{::}}` always removes the property unconditionally. A *variable* so defined is removed from the table, and is then undefined to everything, so a plain `{{varname}}` reference to it is left unsubstituted and only a `{{varname::}}` one propagates the unset. `_update_and_resolve_substitutions()` removes the unset variables, repeatedly, *before* storing anything it substitutes: it used to remove them after the sweep, by which point every variable resolved in the same sweep had taken in the unset one's `{{::}}` as text and was unset in turn on the next — an unset that spread by plain reference, but only to variables in the same sweep, never to `[common]` values or specifications, which were left unsubstituted. `tests/test_variables_command.py` (`TestUnsetIsNotTransitive`) holds both halves. Both work in TOML, JSON, and Jsonnet — for Jsonnet, `process_variable_substitutions_in_file_contents` leaves unset tokens intact so `resolve_variables_insitu()` can remove them after evaluation. A JSON file has no text pass: `load_json_file_with_variable_substitutions()` parses it first and substitutes its values in situ, as the TOML loader does, because substituting the raw text read every value through JSON's escapes and inserted it without them — a default's `[\"x\"]` failed to parse and a Windows path's `\t` became a tab. So a substitution in a JSON file must be inside a string (an unquoted one is reported by the parse error's hint) and in a value: one in a property name, which only the text pass ever reached, is an error (`_substituted_property_names()`). Nested inside another expression, an unset one is replaced by `_UNSET_MARKER` while the outer one resolves, and the outer one is itself unset if the marker survives — that is, if the value was needed, to build a name or as a default that is used. Leaving the inner token in place instead, as it once did, made the outer expression look up a name containing `{{missing::}}` and pass through unresolved.

CSV batch task prototypes use a separate `<<variable_name>>` delimiter system (defined in `csv_data.py`), distinct from `{{`/`}}` to allow both to coexist in the same spec without ambiguity.

## Modules

```
    ├── variable_syntax.py       # The substitution syntax: delimiters (VAR_*, CSV_VAR_*, WP_VARIABLES_*), type tags, VARIABLE_NAME_PATTERN/RULE, ENV_VARIABLE_NAME_PATTERN, RESERVED_VARIABLE_NAMES, the lazy names (L_*, LAZY_VARIABLE_NAMES), the '{{random}}' widths, SECRET_VARIABLE_NAME_PATTERN
    ├── variable_substitution.py # Variable substitution engine ({{ }} delimiters) and the variable table; undefined_variable_references() reports, without substituting anything, the names 'data' references that nothing defines — `yd-doctor`'s seam
    ├── file_substitution.py     # Substitution in files: the JSON, Jsonnet and TOML specification loaders (parse_json_file(), load_*_file_with_variable_substitutions()), and the text passes over a file's contents (process_variable_substitutions_in_file_contents(), the Jsonnet lexing pass); part of the engine, so exempt with variable_substitution.py from the bare-call guard
    ├── csv_data.py              # CSV batch task processing; substitution uses << >> delimiters, made in the prototype Task's data string by string (`_substituted()`, property names included), never by pasting values into its `str()` and `literal_eval()`-ing the result, which an apostrophe crashed, a backslash corrupted and a value could add properties to; typed values through `variable_substitution`'s `process_typed_variable_substitution()` and `typed_value_as_text()`, so `<<array:…>>` and `<<table:…>>` work too, errors prefixed with the file, line and column; files read as `utf-8-sig` with `newline=''`, blank lines skipped, an empty or repeated heading and a file without data rows refused; perform_csv_task_expansion() gives each Task Group at most one file however it is chosen (position, `:N`, `:name`), and the JSON loader shares file_substitution.parse_json_file() with the plain one; `split_csv_file_suffix()` parses a `:<number>`/`:<name>` suffix after the last `:` only, so a Windows drive letter is never one
```
