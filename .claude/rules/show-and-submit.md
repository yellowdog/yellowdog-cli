## show.py and submit.py

`show.py` splits resolution from printing, and the split is load-bearing: `resolve_details()` returns the object(s) a YDID names (a list, because `--show-token` yields a Configured Worker Pool *and* its token, `--show-members` a Group or Role and its members (an object of its own, never merged into the Group, whose JSON stays a specification `yd-create` takes), and `--show-source-report`/`--show-exhaustion` a Compute Requirement, or a Provisioned Worker Pool, and its reports: `_diagnostics()`, where a report the Platform lacks (404) is a warning rather than the ID's failure) or `None` having reported why it could not, and `_print_items()` is the only place the JSON array's indentation and separating commas are applied. Threaded through the individual branches instead, they would be passed on by some and forgotten by others, so a multi-ID `yd-show` would emit an array whose elements run together without commas, which is unparseable. `tests/test_show_output.py` parses the output, rather than asserting the arguments handed to `print_yd_object()`, which cannot see that. Each YDID type's resolution is an entry in `_RESOLVERS` (`_fetched()` for an entity with its own lookup, `_member_of()` for one found among its parent's members, which raises `NotFoundError` when absent), held to every `YDIDType` by a test, and `resolve_details()` prints the progress line and handles the failures for all of them. An array is emitted whenever more than one object will be printed, which includes more than one ID being asked for even if some of them fail — the shape follows the request, not how much of it succeeded — and `show_ydids()` returns the exit code: 0, `NOT_FOUND` when every failure was a not-found (counted by `_report_not_found()` in a per-run `_TALLY`, since the resolvers report and return `None`), else 1. The resolvers re-raise a `SESSION_FAILURES` failure instead of reporting it; `show_ydids()` then prints what was resolved and raises `ReportedFailure`.

`submit.py` keeps one run's state in a `_Submission` (`ctx`, the `[workRequirement]` configuration as the run re-substitutes it, the Work Requirement's name, the dry-run snapshot, the uploaded files, the batch size and the legacy-retry warning), which `main()` builds and passes to every function that needs any of it in place of `ctx`, rather than in module globals; a test builds one with its file's `_submission(**state)` helper, which reads the wrapper's globals and `submit.py`'s `CONFIG_WR` as patched. Submitting a new Work Requirement (`submit_work_requirement()`) and adding to one (`add_to_existing_work_requirement()`, `--add-to`) are one pipeline of shared steps — `_specification()`, `_name_the_run()`, `_task_groups()`, `_add_tasks()` (with the clean-up on failure: a new Work Requirement cancelled, one added to warned of and left) and `_follow()` — and differ only in the step between, `_create_work_requirement()` or `_extend_work_requirement()` (which carries out the plan `_plan_extension()` makes without a client: the specification's Task Groups matched by name to the existing ones, their task types checked, and the rest appended), which returns the `_Addition`s (a Task Group and its `TaskGroupPosition`, and whether the Task Group is `matched`, an existing one) that `_add_tasks()` works through; a matched Task Group's position starts from its summary's `taskCount`, which the Platform updates seconds after Tasks are added, so `add_tasks_to_task_group()` checks it first (`_settled_source()`: the group searched for the name its first new Task would have, `task_generation.first_task_name()`, which defines nothing; while that name is taken, the count waited on until it changes, `limits.TASK_COUNT_UPDATE_WAIT`, and the Tasks numbered again; unnamed Tasks counted, `entity_utils.count_tasks_in_task_group()`), never by counting every Task, a request per thousand; **a Task Group's place is one `TaskGroupPosition`** (`utils/task_group_position.py`: its index in the specification, its number and the count in the Work Requirement, the Tasks it already holds), built once per Task Group and passed down, never as separate indexes and offsets, and its `substitute()` is the one place the Task Group's lazy substitutions are set; the Task Groups themselves are built by `utils/task_groups.py`, a library given the `[workRequirement]` configuration, the position and an `on_legacy_retry` callback (the once-per-run deprecation warning stays the run's), never `_Submission`, and `create_task_group()` runs its named steps in an order its errors and warnings depend on; the Tasks likewise by `utils/task_generation.py`, from one `TaskSource` per Task Group (the configuration, the Work Requirement's name and namespace, the specification, the Task Group and its position, the Tasks and where their input files are uploaded), the Task's name and its substitutions decided before anything else of it is read, and a property it inherits from its Task Group or the Work Requirement substituted for it in a copy (`_TaskLevels`, a `Cascade` whose `get()` does it, so every lookup stays `levels.checked(CONSTANT, ...)` for `test_property_cascade.py`'s scan; `_task_data_for_task()` for the `taskData*` properties), since those levels were substituted before any Task existed; a change to how either path checks, names, builds, adds or follows goes in the shared step. **A property inherited across the levels is read through `property_cascade.Cascade`** (`levels.checked(VCPUS, double_range_from_list, config_wr.vcpus)`), never as nested `.get()`s: the levels it may be set at are the dictionary's, so a new one needs a dictionary row (which the rule in *Specification Schemas* already asks for) and the configuration's value as the default. A table that accumulates down the levels rather than being replaced (`addEnvironment`) is read with `levels.merged(...)`, a lower level winning a key and `null` clearing what came from above.
