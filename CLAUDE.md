# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

YellowDog CLI (`yellowdog-cli`) is a Python CLI tool suite for managing distributed computing jobs and resources on the YellowDog platform. It provides ~39 `yd-*` commands (e.g., `yd-submit`, `yd-provision`, `yd-list`, `yd-upload`, `yd-download`) installable as a package. It also provides `yd-commander`, a PyQt6 desktop GUI that drives those same commands (see [Commander](#commander)), and `yd-mcp`, an MCP server over them (see [MCP Server](#mcp-server)).

Current version: defined in `yellowdog_cli/_version.py`.

## Commands

```bash
# Install in editable/development mode
make install          # builds, then uv pip install -U -e ".[commander,jsonnet,cloudwizard]"

# Format code (ruff check --fix + ruff format)
make format

# Build distribution
make build            # python -m build

# Run tests
pytest -v                           # standard tests only
pytest -v --run-demos               # include demo integration tests
pytest -v -n 4 --run-demos tests/test_demos.py  # parallel demos (target file to avoid unit tests consuming workers first)
pytest -v -k test_variable          # run a single test file/pattern

# Run tests across all supported Python versions (3.10–3.14) via tox + uv
make tox
tox -e py315          # Python 3.15 pre-release: opt-in, kept out of env_list (see DEVELOPMENT.md)

# Type checking
make pyright

# Code complexity: McCabe worst first, ruff's function-structure counts, lengths (a report, never a failure)
make complexity

# Update dependencies
make update           # uv pip install -U -e ".[dev,commander,jsonnet,cloudwizard]"
```

## Architecture

### Package Structure

One line per module; the module docstrings carry the detail. The Commander, MCP, specification-schema and substitution modules are described in full in their `.claude/rules/` files.

Rules recorded in those modules that are easy to break:

- **`entity_utils.py`.** Every namespaced search goes through `search_namespaces()`, because the Platform refuses an unscoped search (403) from an Application without global read access. Every mutation in `resource_creation.py`/`resource_removal.py` clears the caches it invalidates *in the mutating function*, straight after the SDK call (`tests/test_cache_clearing.py`). A lookup returns `None`/`[]` only for the specific failure it tolerates (404, missing permission) and raises anything else, so a 401 reaches the wrapper instead of being recorded as "not found"; display-only lookups re-raise `SESSION_FAILURES`. An ambiguous bare name raises `AmbiguousNameError` rather than taking the first match. Work Requirement name lookups search for the name, never list the namespace.
- **`dataclient/operations.py`.** Transfers record their outcome and return `False` instead of raising, so every argument is attempted. They run with `check=False` and with rclone_api's `UserWarning` silenced, because that warning spells out an inline remote's credentials. `remote_stat()` lists one level on bucket-based remotes, which report any non-object path as a directory. `warnings.catch_warnings()` is not thread-safe, so worker threads leave the filter to the pool's thread.

### Command Pattern

Most command modules use `@main_wrapper` (requires YellowDog SDK client):

```python
from yellowdog_cli.utils.wrapper import main_wrapper

# The command's configuration section, built on first use (lazy.py);
# the wrapper builds it before main() runs, so a broken one exits first
CONFIG_XXX: ConfigXxx = lazy(load_config_xxx)

@main_wrapper
def main(ctx: RunContext):
    # Command logic using ctx.args, ctx.config and ctx.client, passing ctx
    # on to the code it calls
    ...

if __name__ == "__main__":
    main()
```

A small number of standalone commands (`yd-help`, `yd-version`, `yd-format-json`, `yd-jsonnet2json`) need neither credentials nor a config file — they just define a bare `main()` function with no decorator.

`yd-doctor` is the one registry command on neither wrapper: both `@main_wrapper` and `@dataclient_wrapper` exit on a missing or broken configuration before `main()` runs, which is exactly the state `yd-doctor` exists to diagnose, so `doctor.py` builds its own `Context` from `ARGS_PARSER` and runs `utils/doctor_checks.CHECKS` over it instead. PAC belongs to the Proxy row: it reports `HTTPS_PROXY`, or with PAC on resolves the proxy for the API URL (a WARN when none resolves) and keeps it in `HTTPS_PROXY`, so the live checks after it — Reachable included, which no longer resolves PAC itself — use it.

`show.py` splits resolution from printing, and the split is load-bearing: `resolve_details()` returns the object(s) a YDID names (a list, because `--show-token` yields a Configured Worker Pool *and* its token) or `None` having reported why it could not, and `_print_items()` is the only place the JSON array's indentation and separating commas are applied. Threaded through the individual branches instead, they were passed on by ten of the nineteen and forgotten by the other nine, so a multi-ID `yd-show` emitted an array whose elements ran together without commas — unparseable for Compute Requirements, Compute Sources, Nodes, Workers, Work Requirements, Task Groups, Tasks, Image Groups and Images, which is most of what anyone shows. The old tests asserted the arguments handed to `print_yd_object()` and so saw nothing; `tests/test_show_output.py` parses the output instead. Each YDID type's resolution is an entry in `_RESOLVERS` (`_fetched()` for an entity with its own lookup, `_member_of()` for one found among its parent's members, which raises `NotFoundError` when absent), held to every `YDIDType` by a test, and `resolve_details()` prints the progress line and handles the failures for all of them. An array is emitted whenever more than one object will be printed, which includes more than one ID being asked for even if some of them fail — the shape follows the request, not how much of it succeeded — and `show_ydids()` returns the exit code: 0, `NOT_FOUND` when every failure was a not-found (counted by `_report_not_found()` in a per-run `_TALLY`, since the resolvers report and return `None`), else 1. The resolvers re-raise a `SESSION_FAILURES` failure instead of reporting it; `show_ydids()` then prints what was resolved and raises `ReportedFailure`.

`submit.py` keeps one run's state in a `_Submission` (`ctx`, the `[workRequirement]` configuration as the run re-substitutes it, the Work Requirement's name, the dry-run snapshot, the uploaded files, the batch size and the legacy-retry warning), which `main()` builds and passes to every function that needs any of it in place of `ctx`, rather than in module globals; a test builds one with its file's `_submission(**state)` helper, which reads the wrapper's globals and `submit.py`'s `CONFIG_WR` as patched. Submitting a new Work Requirement (`submit_work_requirement()`) and adding to one (`add_to_existing_work_requirement()`, `--add-to`) are one pipeline of shared steps — `_specification()`, `_name_the_run()`, `_task_groups()`, `_add_tasks()` (with the clean-up on failure: a new Work Requirement cancelled, one added to warned of and left) and `_follow()` — and differ only in the step between, `_create_work_requirement()` or `_extend_work_requirement()` (which carries out the plan `_plan_extension()` makes without a client: the specification's Task Groups matched by name to the existing ones, their task types checked, and the rest appended), which returns the `_Addition`s (a Task Group and its `TaskGroupPosition`) that `_add_tasks()` works through; **a Task Group's place is one `TaskGroupPosition`** (`utils/task_group_position.py`: its index in the specification, its number and the count in the Work Requirement, the Tasks it already holds), built once per Task Group and passed down, never as separate indexes and offsets, and its `substitute()` is the one place the Task Group's lazy substitutions are set; the Task Groups themselves are built by `utils/task_groups.py`, a library given the `[workRequirement]` configuration, the position and an `on_legacy_retry` callback (the once-per-run deprecation warning stays the run's), never `_Submission`, and `create_task_group()` runs its named steps in an order its errors and warnings depend on; the Tasks likewise by `utils/task_generation.py`, from one `TaskSource` per Task Group (the configuration, the Work Requirement's name and namespace, the specification, the Task Group and its position, the Tasks and where their input files are uploaded), the Task's name and its substitutions decided before anything else of it is read, and a property it inherits from its Task Group or the Work Requirement substituted for it in a copy (`_TaskLevels`, a `Cascade` whose `get()` does it, so every lookup stays `levels.checked(CONSTANT, ...)` for `test_property_cascade.py`'s scan; `_task_data_for_task()` for the `taskData*` properties), since those levels were substituted before any Task existed; a change to how either path checks, names, builds, adds or follows goes in the shared step. **A property inherited across the levels is read through `property_cascade.Cascade`** (`levels.checked(VCPUS, double_range_from_list, config_wr.vcpus)`), never as nested `.get()`s: the levels it may be set at are the dictionary's, so a new one needs a dictionary row (which the rule in *Specification Schemas* already asks for) and the configuration's value as the default.

`yd-commander` is the exception to all of this: it uses neither wrapper, loads no config at import, and never touches the SDK, because it runs the other commands as child processes. Its `main()` is in `commander/launcher.py` and stays free of Qt so that the missing-extra message works without PyQt6 installed. See [Commander](#commander).

Data client commands (`yd-upload`, `yd-download`, `yd-delete`, `yd-ls`, `yd-copy`) use `@dataclient_wrapper` instead — no SDK client is initialised:

```python
from yellowdog_cli.utils.dataclient.wrapper import dataclient_wrapper

CONFIG_DATA_CLIENT: ConfigDataClient = lazy(load_config_data_client)

@dataclient_wrapper
def main(ctx: DataClientContext):
    # Command logic using ctx.args and CONFIG_DATA_CLIENT
    ...
```

These commands never contact the Platform API, so they are registered as `CommandKind.DATA_CLIENT` in the command registry, whose common option set omits `--key`, `--secret`, `--url` and `--pac`: `load_config_data_client()` still bypasses `load_config_common()`, which is the sole reader of all four, and no `PlatformClient` is built. The four `ARGS_PARSER` properties are still decorated with `@allow_missing_attribute` and so return `None` rather than raising when unregistered — which is what lets `load_config_common()` keep reading them unconditionally. Passing one of the four to a data client command is an argparse error rather than a silent no-op.

### Command Registry

Every `yd-*` command's options are defined once in `utils/command_registry.py`, as data. `CLIParser` builds argparse from a command's `all_options()` — the kind's common set, then the command's own, in the order argparse will print them — so the option order in a `Command` is load-bearing for `--help`. A shared option is one module constant (`NAMESPACE`, `FOLLOW`, `DRY_RUN`, ...) and a command whose wording differs uses `CONSTANT.variant(help=...)`, which keeps the option's identity; `Command.has()` and `option_named()` both compare by that identity, and `option_named()` is what the README checker relies on to look a flag up. Three options are separate constants rather than `variant()`s, because a `variant()` merges keyword arguments onto the base rather than replacing them and cannot change the `flags` tuple, so it can narrow a keyword's value but never drop one or remove an alias: `DRY_RUN_JSON` (a bare `--json` with no `-J`, unlike the shared `JSON`), `RESIZE_COMPUTE_REQUIREMENT` (a flag with no `type`, unlike `COMPUTE_REQUIREMENT`'s) and `NODE_ACTION_STATUS` (a flag with no `dest`, unlike yd-list's `STATUS`, which appends into `status_filter`) — each keeps its base's first long flag, so identity is preserved. The command is resolved from `sys.argv[0]` by exact lookup after `command_from_argv0()` normalises it (basename, `.py`/`.exe`/`-script` stripped, underscores to hyphens, `yd-` prefixed), so a command name inside the install path no longer matters and no substring ordering does either; an unknown name gets the API common set only, which is what pytest's executable gets. Post-parse checks are `validators` on the commands they apply to. A positional a data client command needs is `nargs="*"` with `Option.tool_required` (`yd-upload`'s `local_paths`, `yd-download`'s `remote_paths`, `yd-copy`'s two paths, checked by `check_copy_args`), so that `--which-rclone` and `--upgrade-rclone` run without one: `check_paths_given` requires it otherwise, and the MCP tools, which offer neither option, mark it required. yd-list's are table-driven: `LIST_NAME_TYPES`, `LIST_STATUS_TYPES`, `LIST_ACTIVE_TYPES`, `LIST_ID_TYPES` and `LIST_SUBSTITUTE_TYPES` say which entity types each filtering option applies to, and `check_list_options` refuses it for any other, so a new entity type, or a filter extended to one, is added to those tables; a new entity type also needs its function in `list.py`'s `_LISTERS`, which a test holds to `ENTITY_TYPES`. `yd-cloud-info`'s filters are table-driven the same way: `CLOUD_INFO_OPTION_TYPES` says which of its types each applies to and `check_cloud_info_options` refuses it for any other, also checking `--vcpus`/`--ram`, which `CLIParser`'s `vcpus_range`/`ram_range` parse (`parse_range()`); its sort keys, `CLOUD_INFO_SORT_KEYS`, are held by a test to `utils/cloud_info.py`'s `SORT_KEYS`, and its `TYPE` positional's `resolve_cloud_info_type` is mapped to an enum in `mcp/tools.py`'s `_item_schema()`. `requires_namespace_and_tag` is an explicit field rather than derived from having `--namespace`, because `yd-list` has the option and is not one of them. `help.py`'s `main()` renders `COMMANDS` for `yd-help`'s listing, sorted by name — which moved `yd-copy` to its true alphabetical position, the old hand-written table having had it out of place; A command's extra is read from its summary's trailing `(needs the <extra> extra)`, and `EXTRA_PROBES` names one package per extra that `find_spec()` looks for, never importing it, to say whether it is installed; `--json` gives the extra and `installed` as fields. `yd-commander` and `yd-mcp`, entry points with no registry entry, are listed from `help.py`'s own `OTHER_COMMANDS` table, which `tests/test_command_registry.py` holds to the entry points the registry lacks. `tests/test_command_registry.py` holds the registry to `pyproject.toml`'s entry points, and `tests/test_readme_command_list.py` holds the README's Command List to the registry: the Universal and Shared tables' membership and short forms, the preamble's exceptions, and every option bullet under a `### yd-x` heading naming an option that command takes. Its section parser ignores fenced code blocks (`_outside_fences()`), so a `#` shell comment inside an example is never mistaken for a heading or a bullet, and `yd-list`'s options, given in a table rather than as bullets, are checked as table rows. Wording is never checked, and nothing in the README is generated. `tests/test_parser_snapshots.py` holds every command's option *shapes* — each action's kind, flags, `nargs`, `const`, `default`, `type`, `choices` and `required` — to `tests/parser_snapshots.json`, never their wording, and the file is regenerated with `pytest tests/test_parser_snapshots.py --update-parser-snapshots` when a shape change is intended.

### Global State (wrapper.py)

`wrapper.py` holds two module-level globals used everywhere:
- `CLIENT` — `PlatformClient` instance (YellowDog SDK), built the first time the command uses it (`_create_client()`, which also applies `set_user_agent()`)
- `CONFIG_COMMON` — loaded from `config.toml` (or `--config` arg / env vars), built by `prepare_run()` before the command runs

`ARGS_PARSER` is a `CLIParser` instance from `args.py`, also module-level. No command module imports these three: each is given them as its context (below).

**Every command takes them as a context** (`utils/context.py`): `main_wrapper` passes a `RunContext` to `main(ctx)`, built as the command runs from the wrapper's own `ARGS_PARSER`, `CONFIG_COMMON` and `CLIENT` (so a test sets those three on `wrapper`, never on a command module), and `dataclient_wrapper` passes a `DataClientContext`, the command line alone. The command passes it on to the code it calls, which reads `ctx.args`, `ctx.config` and `ctx.client` instead of module globals — the library code included: `follow_utils` (`follow_ids(ctx, ...)`, its threads given `ctx` too), `resource_creation`/`resource_removal` (`create_resources(ctx, ...)`), `submit_utils` (`RcloneUploadedFiles(ctx, ...)`), `task_batches` (`run_batches(ctx, ...)`) and the Cloud Wizard's provider classes (constructed with `ctx`, which they pass to the resource libraries). A command's own configuration sections (`CONFIG_WR`, `CONFIG_WP`, `CONFIG_DATA_CLIENT`) stay its module's, built lazily; `yd-doctor` and `yd-schema`, on neither wrapper, read `ARGS_PARSER` directly. **The rule for new code: a function that needs the command line, the configuration or the client takes `ctx` as its first parameter**, and a callback handed to a thread or another function carries it (`functools.partial(_remove_resource, ctx)`, `Thread(..., args=(ctx, ydid))`). A test calls such code with a context of its own (`RunContext(args=SimpleNamespace(...), config=..., client=fake.client)`, as `test_cancel.py` does), or, where it drives the real `ARGS_PARSER` and client, with its file's `_ctx()` helper, which builds one from the wrapper's (patched) globals; a stub standing in for such a function takes `_ctx` first. **No library reads `ARGS_PARSER`** (`utils/output_settings.py`): what decides how output looks and how the CLI asks (`--quiet`, `--debug`, `--json`, `--no-format`, `--pp`, `--count`, `--output-file`, `--strip-ids`, `--hide-user-data`, events as JSON, `--yes`, interactive selection, `--sort`/`--reverse`/`--details`) is `OUTPUT`, one `OutputSettings` object that `printing.py`, `tables.py`, `interactive.py`, `results.py`, `event_printing.py`, `dataclient/rclone.py` and `specs/validation.py` read, configured in place from the command line by `prepare_run()` (and by `yd-doctor` and `yd-schema`, on neither wrapper) as a command starts; a command that adjusts its options for output configures it again (`yd-list` after `--count` and its `--details`, `yd-abort` after turning interactive selection on), since the settings are a copy, not a view. What a library needs of the command's input it is given: `load_config` the command line, once (`ensure_config_loaded(args)`, by `prepare_run()`, `CONFIG_COMMON`'s builder or `yd-doctor`; the first given is kept, and `_ARGS` holds it for the lazy loaders), `register_user_variables()` the `-v` variables, the configuration file, `--env-override` and whether `--config` chose the file, the `.env` functions the file and the override, `load_resource_specifications(args, ...)` the command line, the Jsonnet loaders `dry_run`, the CSV loaders `csv_only`, the `--substitute-ids` lookups `substitute`, and `yd-doctor`'s checks their `Context.args`. The rule for new code: output behaviour is read from `OUTPUT`, never the command line, and anything else a library needs of the command line is a parameter. A test sets `OUTPUT` with `output_settings.configure_output(args)` or, for a block, `with output_settings.configured(args):`; `conftest`'s autouse `_output_settings_restored` puts it back after every test, and a test that changes a setting after configuring changes `OUTPUT` itself (`output_settings.OUTPUT.sort = ...`), not the arguments it was configured from. The action commands' shared rules are `utils/action_runner.py`'s, so a test of a prompt or message those rules make patches `action_runner` (its `confirmed`, `print_error`, `print_warning`), not the command module.

**Importing a module does nothing.** All three, and every command's configuration section (`CONFIG_WR`, `CONFIG_WP`, `CONFIG_DATA_CLIENT`, ...), are `lazy.py` stand-ins built on first use, and `load_config.py` reads the file, and `variable_substitution.py` registers the `YD_VAR_*` and `-v` variables, only when first asked (`ensure_config_loaded()`), so importing any module parses no command line, reads no configuration, builds no client, prints nothing and exits nowhere; `tests/test_lazy.py` imports every module in a fresh interpreter with a bad command line and a missing file to hold that. What import once did, the wrappers now do before the command runs (`command_runner.prepare_run()`), in the same order and outside the command's exception handling, so an argument error still exits 2 and a broken configuration 3, with nothing on stdout, before the command starts. The rules for new code: a command's configuration section is `lazy(load_config_xxx)`, never a call at module level; nothing reads `ARGS_PARSER`, a configuration value or `CLIENT` at module level (`submit.py`'s `TASK_BATCH_SIZE` became `_task_batch_size()` for that reason); and a test that needs the value itself, for `dataclasses.replace()` or to patch a property on `CLIParser`, takes it with `lazy.value()`. The test process builds the command line, the configuration and `CONFIG_COMMON` in `conftest.py`'s `pytest_configure()`, before any test module is imported, as importing once did (and supplies dummy credentials first where none load), with stdout and stderr redirected while it does, since that is before pytest captures anything and `printing.py`'s consoles, created as it is imported, take their colouring from whether stdout is a terminal: in a terminal every test reading output found escape codes, while a run through a pipe passed (`test_printing.py`'s `test_the_consoles_came_up_without_colour` fails only in a terminal): left to first use, the command line would be parsed with whatever `sys.argv` a test had set, and the configuration loaded inside a test that had patched it. A command module's own sections are built when its `main()` first runs, or a test first touches them.

The `@main_wrapper` decorator handles: PAC proxy setup (under `--dry-run` too, since most dry runs call the platform), exception catching (permission and credential errors worded by `classify()`, as the exit code is chosen), closing `CLIENT` if it was built (`_close_client()`, which closes whatever the module holds, so a test's mock is closed rather than a real client), and exit codes. The run itself is `command_runner.run_command()`, shared with `@dataclient_wrapper`, so a fix to how a command is run, flushed and exited is made once; a test patching the start-up checks patches them on `command_runner`.

`variables.py` (`yd-variables`) redacts the `key` and `secret` variables, named or not, substituting `REDACTED_VALUE` from `output_style.py` (`resource_creation.py` uses the same constant for a withheld Keyring password). Those two (`SECRET_VARIABLES`) are the only variables in the table the CLI put there itself — `load_config_common()` adds them alongside `url`, `namespace` and `tag` — so they are the only ones that can be *known* to be credentials. It also redacts every other variable whose name matches `SECRET_VARIABLE_NAME_PATTERN` in `variable_syntax.py` (`secret|password|passwd|token|credential|private_key`, case-insensitive, `re.search`), and says so: when at least one was redacted that way, `main()` prints one `print_warning()` line ahead of the JSON giving the count and the pattern and saying everything else is shown in full and `--show-secrets` reports all (so `--quiet` suppresses it with the other warnings). Name-pattern redaction was once considered and rejected: it would catch identifiers, miss badly-named secrets such as `APP_CREDS`, and read as a guarantee the command cannot keep. That objection was to a *silent* heuristic; this one states what it matched and that nothing else was withheld, so it cannot be read as a guarantee — and `key` alone is left out of the pattern so that `APP_KEY_DEMO`, an identifier, is still shown. A value redacted by the pattern is already `REDACTED_VALUE` by the time the undefined-variable check runs, so it carries no reference to check, and only `key` and `secret` are left out of that check by name. All of the redaction applies to a named variable too, with a line saying `key`/`secret` were redacted when they were named, and `--show-secrets` (the same option name `yd-cloudwizard` uses) is the one way round it: naming a variable used to report it whatever it was, which let an MCP tool, which can never pass `--show-secrets`, ask for `secret` by name. `report_variables()` returns a `Report` (the variables, and which were redacted as credentials, by the pattern, or by value), so the rules and the notes counting them are decided in one place. `yd-variables` is the one command with `requires_credentials=False` in the registry (`ARGS_PARSER.credentials_required`), so `wrapper.py` loads `[common]` non-strictly for it and it runs, and reports `key`/`secret` as `null`, without an application key or secret; a named variable never defined is warned of, and a name no variable could have is refused as parsed (`check_variable_names`). And `tests/test_variables_command.py` holds the misses (`APP_KEY_DEMO`, `APP_CREDS`) as well as the matches; its `_run()` drops inherited `YD_VAR_*` variables, which would otherwise join every full report and the note's count. The one extension of that limit is structural, not a name guess: the `{{dataClient.remote}}` and `{{dataClient.<profile>.remote}}` variables are the CLI's own too, and an inline rclone connection string carries its credentials in its parameters, which the rclone parser can identify — so the full report renders those through `dataclient.rclone.shown_remote()` (name, type and provider kept, `<N parameters redacted>` for the rest; a named remote unchanged), exactly as `yd-doctor`'s profile rows do, under the same rule: lifted by `--show-secrets` alone. `is_remote_variable()` in `variables.py` is the name test, built from the `dataClient` section and `remote` property constants. The same rendering applies to any variable whose *value* is an inline connection string (`dataclient.rclone.is_inline_remote()`: rclone's `:backend,...` form, or `NAME,...` with a `type` parameter, optionally `rclone:`-prefixed — deliberately strict, since `parse_rclone_config()` reads anything with a comma as a remote and `shown_remote()` would turn `a,b` into `a`), because a user's `remote_with_keys` carries its credentials exactly as `{{dataClient.remote}}` does; for a variable the CLI did not register, `main()` prints a note giving the count (`withheld_remotes()`), as it does for the name pattern. `shown_remote()` keeps an `rclone:` prefix but withholds a trailing `:path` with the last parameter: it cannot be told from the `:port` of a URL-valued parameter such as `endpoint`, and splitting on the last `:` leaked that port in `yd-doctor`'s report.

### Keeping the SDK out of start-up

Importing *anything* from `yellowdog_client` — even `yellowdog_client._version` — runs the package's `__init__`, which imports `PlatformClient` and with it every client, all ~300 model modules and `requests`: about 140ms, most of a command's start. The commands that never use a client — `yd-variables` (Commander's discovery runs it, `--quiet`, on every reparse) and the five data client commands — therefore import no SDK at all (`interactive.py`, which `yd-delete` imports to confirm, has `PlatformClient` under `TYPE_CHECKING`; at module level it loaded the SDK for every `yd-delete`, unseen because the test ran only `yd-ls`), and `tests/test_sdk_free_startup.py` runs each one's real `main()` in a fresh interpreter, checking it succeeded, and fails if `yellowdog_client` was ever imported (with a control case that must load it, so the probe is known to see it). **The rule: a module every command imports never imports the SDK at module level.** That is `utils/version_info.py` (`sdk_version()` reads the package metadata), `printing.py`, `tables.py` and `event_printing.py` (`from __future__ import annotations`, the SDK names under `TYPE_CHECKING`, a local import in each function that uses one at run time — ruff's `TC004` finds those — and `event_printing.py`'s `status_counts_*()` lists built on first use), `items.py` and `misc_utils.py` (type-only), `results.py` and `printing._sdk_json()` (`Json` for an SDK object only, so a list of dicts — a data client command's `--json` result — needs none), `exit_codes.classify()` and `misc_utils.is_http_not_found()` (an SDK or `requests` exception class is checked only if its package is in `sys.modules`, since no instance can exist otherwise), `specs.sdk_models.model_class()` (the one import of `yellowdog_client.model`, reached only for an SDK-backed schema), and `wrapper.py` (`CLIENT` on first access; `pypac` and `user_agent`, which imports `requests`, only where used). A test that patched one of those names on the importing module (`printing.Json`, `wrapper.pac_context_for_url`) now patches it at its source, where the local import looks it up. `CLIENT` is never built by `prepare_run()`, only on the command's first use of it. Two costs remain by design: `yd-variables` without `--quiet` builds the config schema, whose `[workRequirement]` and `[workerPool]` sections need the SDK; and interactive selection (`tables.py`'s `sorted_objects()`, `print_numbered_object_list()`) imports it for its `isinstance` checks, after the user has been prompted.

### The `--json` Result and Exit Codes

With `--json`, stdout holds one JSON document, the command's result, and the exit code names the kind of failure; the contract, shapes and codes are in the README's *Machine-readable Output and Exit Codes*. `utils/results.py` is the accumulator: a command calls `record()` for each outcome (a dict, or an SDK object, serialised as `yd-list` serialises it) or `record_document()` for a one-object result, and both wrappers call `flush_results()` after `main()` returns and, on an exception, a `SystemExit` or a keyboard interrupt, before exiting — so a failure part-way still reports what was done; the `--debug` branch flushes in a `finally` and still re-raises unclassified. The failure branches set the exit code *before* flushing, and flush through `flush_results_after_failure()`, which reports a flush that fails (an unserialisable record) rather than letting it escape or turn the failure into exit 0. Both wrappers also check `any_failed()` straight after a *successful* `main()` and its flush: a command that caught its own error, recorded it as `failed` and returned normally (e.g. `yd-boost` on a 401) used to exit 0 regardless, so this is checked with or without `--json`, since the records exist either way; it sets `ExitCode.FAILURE` and suppresses the `Done` print, without touching what was already flushed. `yd-cancel`, `yd-shutdown`, `yd-terminate`, `yd-delete` and `yd-download` no longer restrict `--json` to `--dry-run` (`command_registry.py`'s `check_json_requires_dry_run` validator is gone): the real, acting path already recorded through `record_action()`/`record_deletion()`/`record_transfer()`, so lifting the parse-time guard was the only change these five needed. The flush does nothing without `--json` (`json_output` is `None` on a command without the option), prints once, and prints `[]` when nothing was recorded. A command that prints its own JSON through `print_json()` gets no flush (`printing.json_document_printed()`): that is the permanent rule, since `yd-show`, `yd-variables` and `yd-doctor` keep printing their own documents, but JSON printed any other way would still get a trailing `[]`. A command that prints its own document *and* records is a mistake, and `flush_results()` raises a `RuntimeError` saying so rather than printing a second document. `results.py` must never import `wrapper.py` or `load_config.py`, which import it. `utils/exit_codes.py`'s `classify()` maps what reaches a wrapper to an `ExitCode` (defined there): typed checks first (the CLI's own `NotFoundError`, an `HTTPError`'s `response.status_code`, the SDK's `NotAuthorisedException`, `InternalServerException` and `ServerErrorException`, `requests` connection errors and timeouts), then the `MissingPermissionException` and `Unauthorized` text checks the wrapper's friendly messages also key on (`MISSING_PERMISSION_TEXT`, `UNAUTHORIZED_TEXT`), then the exception's `__cause__`, else `FAILURE` — so **a failure re-raised with a clearer message must be raised `from` the original**, or it loses its code, and a missing entity is raised as `NotFoundError`, never `KeyError`; a `SystemExit`'s code passes through. `load_config.py`'s and `variable_substitution.py`'s configuration-time exits use `ExitCode.CONFIGURATION`; a command that catches a failure itself exits `FAILURE`, except a `SESSION_FAILURES` one (authentication, connection) that stops an action command: having recorded the failing item and the not-attempted rest, the command raises `exit_codes.ReportedFailure(cause)`, which both wrappers exit on with the cause's code (`classify()` follows `__cause__`) without printing it again. `abort.py`, `boost.py`, `cancel.py`, `shutdown.py`, `nodeaction.py`, `compute_action_common.py`, `start_hold_common.py` and `utils/resource_processing.py` (for `yd-create` and `yd-remove`) do (`nodeaction.py` also raises it for a faulty specification whose faults it has printed, and for a `--follow` that `--timeout` cut short); `create_resources()` and `remove_resources()` otherwise carry on past a failed specification (or ID), printing each failure once, naming the resource (a creator or remover raises rather than printing first), and finish by raising `ReportedFailure` with the failures' shared cause, or a `RuntimeError` for different causes, so they exit by cause like `yd-wait`; the Cloud Wizard, which calls `create_resources()`, still sees it raise, and its `remove_resource_by_id()` still returns `False` on a failure, having reported it, except that a `SESSION_FAILURES` failure is raised as `ReportedFailure` once recorded: `CommonCloudConfig._remove_yd_templates_by_prefix()` then records the rest as not attempted (`record_not_attempted()`), keeps the failure in `platform_failure` and skips the Keyring, the provider's own (cloud-side) removals still run, and `run_operation()` raises it, so a teardown exits with the failure's code and a second one removes what was left; Azure setup keeps a session failure creating its credential, its last Platform call, in `platform_failure` the same way, and `run_operation()` raises it after setup, once the resource file is saved and the Keyring's details shown. `yd-remove --ids` fetches each resource before confirming its removal (`_removable_by_id()`, a table per YDID type), so an ID that does not exist is `NotFoundError` (exit 6) without a prompt. Its Group, Application and User memberships are made to match a `roles`/`groups` list, so `[]` removes them all, but are left alone without one, and every name in the list is resolved, one that does not exist failing the resource, before anything is changed, since reconciling against a list with a misspelt name would remove the membership it meant. Never raise it `from` anything: `from None` clears the cause the code comes from. Under `--json`, `print_warning()` writes to stderr (`CONSOLE_ERR`, or `sys.stderr` under `--no-format`) rather than being dropped, and `interactive._get_user_input()` writes its prompt to stderr, so stdout still parses. **The rule for new code: a site that reports an outcome with `print_info()` also calls `record()`**, since `--json` silences the one and only the other reaches the script. The thirteen action commands (`yd-cancel`, `yd-shutdown`, `yd-terminate`, `yd-start`/`yd-hold` in `start_hold_common.py`, `yd-finish`, `yd-abort`, `yd-resize`, `yd-boost`, the three `yd-compute-*` in `compute_action_common.py`, and `yd-token`, whose refresh and regenerate records carry the new `token` and `expiryTime`) do so through `record_action(entity, entity_type, action, outcome, error=None, **extra)`, beside every print of what was done, skipped (declined, filtered, already in that state) or failed; `entity` is an SDK object, an `{id, name}` dict, or a string the command was given (a YDID becomes the `id`, anything else the `name`). An Instance is recorded as `{"id": "<cr_id>.<instance_id>", "name": "<instance_id>"}`, the form those commands accept. `yd-shutdown --terminate` records each Compute Requirement it terminates as a `compute-requirements` record with action `terminate` and an extra `workerPoolId`, its `id` `null` when the pool could not be fetched for it — never the pool's ID under the Compute Requirement's type; a Configured Worker Pool, which has none, is warned of and not recorded. `shutdown.py` runs through `action_runner.py` like the others (resolve in the order given, `Unresolved`, confirm once, act, a `SESSION_FAILURES` failure recording the rest as not attempted); its units report and record their own failures, `--terminate`'s included, and raise `SessionStop` for a session failure. `yd-resize` re-raises a failed resize after recording it, so the wrapper still exits non-zero with the record emitted, and records a failure to find its target the same way (`_found()`: not found, ambiguous, or the lookup's own failure, a 401 or a lost connection included), as the action commands on `action_runner.py` do. Their `--json` is `ACTIONS_JSON` in `command_registry.py`, spelled without `-J`. `yd-create` and `yd-remove` record through `record_resource(resource_type, name, id, action, error=None, **extra)` at every created/updated/removed/skipped site, the Image Groups and Images of an Image Family included, and in `create_resources()`/`remove_resources()`'s failure branches, the name coming from `load_resources.resource_display_name()`, read before the creator pops anything from the specification; `yd-create --dry-run --json` records each processed specification with `record()` instead of printing it (`_show_dry_run_specification()`, which takes the resource type and puts `resource` back as the record's first key, since `create_resources()` popped it and a mixed file's array would otherwise be untyped; the printed form still omits it), and records no failures, so its document is the array of specifications, and a Jsonnet dry run under `--json` from a loader that converts several files (`exit_on_dry_run=False`) records a copy of each. `yd-submit`, `yd-provision` and `yd-instantiate` call `record_entity()` straight after the Platform call, and under `--dry-run --json` `record_document()`/`record_document_part()` in place of the print; `record_document_part()` makes the document the one part, or the array of them once batching adds a second. The creators' `--quiet` bare IDs go through `printing.print_quiet_result()`, which prints nothing under `--json`, so `--quiet --json` is the document alone. Those three also carry `check_json_excludes_streaming()` (`command_registry.py`), which refuses `--json` with `--progress` or `--report`: the Rich progress bar and the template report both write to stdout. `--follow` alone reports through `print_info()` and is allowed. A Configured Worker Pool's record carries its `token` and `expiryTime`, as an Application's carries its key, since `--json` silences the prints that show them. The remaining commands: `yd-wait` records `{id, name, status, succeeded}` per ID given, in the order given, and treats an entity not in a terminal state when following ends (its `--timeout`, passed to `follow_ids()`, or a lost stream) as a failure, exiting with the single cause's code (`follow_exit_code()` for a lost stream) or 1 for a Work Requirement failure or mixed causes; `yd-follow`'s `--json` prints each event as a JSON document (`print_event()` keys on the `events_as_json` property in `args.py`, true for that command alone, so an action command's `--follow --json` still prints no events; the `--raw-events` option that duplicated this on `yd-follow` and every command taking `--follow` is gone) and `main()` calls `results_are_streamed()`, so nothing, not even `[]`, follows the events; `check_follow_json_excludes_progress()` refuses it with `--progress`, whose bar consumes the events. The data client records in `dataclient/operations.py`, per file for the three transfers (`record_transfer()`, the listing of a remote directory's files done only when `json_requested()`, since it costs an rclone call) and per item for deletion (`record_deletion()`, with `name` and `isDir` beside `path` and `action`; `deletion_targets()` lists a path or a wildcard's matches once, so `yd-delete` confirms and deletes exactly those, a path already gone recorded `skipped` and a directory without `-R` `failed`, and `delete_item()` deletes one, recording it; `delete.py` refuses the remote's root and the configured bucket, and Commander's delete chooser offers only the `would delete` records). `yd-download`'s records add `match`, the top-level item each file belongs to, because Commander's download chooser offers top-level items and `selection.parse_download_summaries()` groups the per-file records back into them; yd-delete's records are what `parse_object_summaries()` reads, so the old `matched_item_rows()` listing is gone. `yd-ls` records `lsjson_listing()`'s entries in place of printing its table, each with `Listing`, the remote path it was listed under; a path that does not exist, or cannot be reached, is an error (exit 1) while the other paths are still listed, but an empty directory or a wildcard matching nothing (`glob_matches(allow_empty=True)`) is an empty listing. `yd-compare` and `yd-nodeaction` record their tables with `rows_as_objects()`, and pass `override_quiet=not json_requested()` where a message is printed despite `--quiet`, since `override_quiet=True` also prints under `--json`. `yd-version` and `yd-help` are standalone and print their documents with `json.dumps(..., cls=CompactJSONEncoder)`.

### Configuration

Config is loaded from (in priority order): CLI args → environment variables → TOML file. Exception: if the config file is explicitly selected with `--config`/`-c`, its contents (including `[common.variables]`) take precedence over environment variables, but not over CLI args (see `config_file_explicitly_selected()` in `misc_utils.py` and `add_substitutions_from_config_file()` in `variable_substitution.py`). Key env vars: `YD_KEY`, `YD_SECRET`, `YD_NAMESPACE`, `YD_TAG`, `YD_URL`. Variables prefixed `YD_VAR_` are available for substitution in specs.

`load_config_common()` records where each `[common]` value came from in `CONFIG_SOURCES` (`command line`, `environment (YD_KEY)`, `config file (<name>)`, `default`, `not set`), and takes `strict=False` to return a partial `ConfigCommon` with `None` for a missing key or secret instead of exiting; `yd-doctor` is the only caller of either. `ConfigCommon.key` and `.secret` are therefore `str | None`, and `wrapper.py` asserts both before building the API key.

Any TOML property can be overridden on the command line with `--property 'section.key=value'` (repeatable). Valid sections: `common`, `dataClient`, `workRequirement`, `workerPool`, `computeRequirement`. Values are JSON-parsed first (handles bool, int, float, list, dict), falling back to plain string — except for the properties listed in `STRING_PROPERTIES` (`property_names.py`), where the supplied text is kept whenever JSON would make it something other than a string, so `--property workRequirement.name=123` is a name and not an integer (`null` still unsets). The registry is keyed on the property name alone, a name being the same type wherever it appears, and `tests/test_property_overrides.py` checks it against the types recorded in that module's comment column. The config loaders type-check a few properties (`check_str`/`check_list` in `load_config.py`), among them the Work Requirement's `name`, `taskGroupName` and `taskName` and the Worker Pool's `name`, and `format_yd_name()` type-checks the name it is handed, so `name = 123` in a TOML *or* a specification file is a reported configuration error rather than an `AttributeError` raised inside the formatter. Overrides are applied after TOML validation in `load_config.py` via `_apply_property_overrides()`, and the schema check that runs as a command starts sees them (see *Specification Schemas*).

File paths follow two rules. A specification file (Work Requirement, Worker Pool, Compute Requirement, resource, Node Action), from the command line or from the configuration file (which `pathname_relative_to_config_file()` rewrites relative to the current directory), is named from the current directory and opened as it is given: the loaders take no `files_directory`. A file a specification refers to — a `taskDataFile`, a CSV file, a `writeFile` content file, a `userDataFile` — is found from the files directory: `--content-path`, else the specification's directory, else the configuration file's (an absolute path is itself), by a plain `os.path.join()` at each site, `provision_utils._read_user_data()` included (it used to `chdir()` there, which changed the whole process's directory and reported a missing file without saying where it was looked for). A `resolve_filename()` in `variable_substitution.py` used to serve both kinds, guessing from whether a path read from the current directory landed in the files directory that it was a specification, which broke `--content-path` for any specification outside it (and `yd-submit`'s `relpath()` of the specification made even an absolute one fail) and misread a referenced file under a subdirectory named as the specification's; with the guess gone it was only `os.path.join()`, and was removed.

### Resource Specification Test Corpus

`tests/resources/` is the single source of resource specifications used by the resource-definition tests (`test_resource_specs.py`, `test_resource_property_coverage.py`, `test_system_resources.py`) — one Jsonnet file per resource type, each with a minimal variant (only required properties) and a maximal one (every settable property), loaded through the CLI's own loader rather than duplicated as separate fixtures. See `tests/resources/README.md` for the minimal/maximal convention and how to add a new resource type.

`tests/resource_models.py` is a write-side coverage gate: it introspects the SDK's own dataclasses for every model the corpus's resource types build (via `resource_creation.py`'s `_get_model_object`) and fails, naming the property, when a settable property is set by no specification at all. A property can only be excluded from the gate by a registry entry (`SERVER_ASSIGNED_COVERAGE`, `NOT_SETTABLE`, `NOT_TESTED`) carrying a stated reason. Those registries, `MODEL_FOR_RESOURCE` and `settable_properties()` live in `yellowdog_cli/utils/specs/sdk_models.py`, shared with the specification schemas, and `resource_models.py` re-exports them under their old names (the same objects, so a test mutating one changes what the gate reads); `build_models()`, `comparable()` and the nested-model walk stay in the tests, being the gate's alone. An exclusion is never inferred from the dataclass's own `field.init`, since the SDK structures an `init=False` field from a specification exactly like any other. A live read gate in `test_system_resources.py` then demands every property excluded as platform-assigned either actually come back from a real `yd-show` at least once, or carry a recorded reason why this suite cannot make it come back (most of the waived ones belong to a compute source that never provisions a real instance, so it has no status, no instance summary and no exhaustion to report); an exclusion the platform has started honouring is reported as stale, so a waiver cannot outlive its reason. Consequently, closing a coverage gap the SDK opens (a new property on an existing model) is an edit to one `.jsonnet` file, not to several JSON fixtures.

### Coding Conventions

- Python 3.10+ syntax: use `str | None` (not `Optional[str]`), `match` statements where appropriate
- A broad exception handler (`except Exception`, `except BaseException`, a bare `except:`) re-raises its failure, or routes it by its exit code (`classify()`, `SESSION_FAILURES`, `_raise_session_failure()`, or a helper in `tests/test_broad_excepts.py`'s `ROUTING_HELPERS` that does so itself), or is listed in that test's `ALLOWED` with the reason it need not: it is where an authentication or connection failure gets swallowed or given the wrong exit code, as a review of all of them found ten doing. The test fails on a new handler that does none of these, and on an `ALLOWED` entry that no handler needs any more
- Every text file is opened with `encoding="utf-8"` (`open()`, `Path.read_text()`, `Path.write_text()`): without it Python uses the locale's encoding, cp1252 on Windows, and a UTF-8 specification or script holding a non-ASCII character fails to decode or arrives mangled. `tests/test_file_encoding.py` walks the package's source and fails on a text-mode call that names none
- Type hints on all new functions
- A utility never imports a command module: work two callers share is a library under `utils/` that the command is a thin layer over (`resource_creation.py` under `create.py`, `version_info.py` for the version helpers), and a utility that needs the command's help takes a callback (`json_raw.py`'s `follow`)
- Every docstring puts its triple quotes on lines of their own, a one-line docstring included (`"""`, the text, `"""`); no text on a quote line
- Constants (UPPERCASE) go in the module for their concern: `limits.py` (sizes, retries, timeouts, concurrency), `variable_syntax.py` (the substitution syntax), `output_style.py` (how output looks), `entity_names.py` (resource type names prefixed `RN_`, entity type names `ET_`), `property_names.py` (specification keys, in `ALL_KEYS`, and resource and Platform object properties, prefixed `PROP_`), `exit_codes.py` (`ExitCode`), and `settings.py` for configuration and environment names and anything else
- Use `print_error()`, `print_info()`, `print_warning()` from `printing.py` — never `print()` directly. Every Rich console print passes `soft_wrap=True`, since `print_string()` has already wrapped a message to `LOG_WIDTH` (`terminal_width()`, `DEFAULT_LOG_WIDTH` without a terminal or for one reporting 0 columns, where `fill()` raised) and a table is not wrapped at all, while Rich, at 80 columns whenever the output is not a terminal, wrapped every line again and broke tables, `yd-ls` paths and messages written to a pipe or a file; `event_printing.print_event()` reads an event's fields through `_field()`/`_counts()`, since the Platform leaves a summary null and an exception there ended the stream being followed. Every Rich console the CLI builds has `emoji=False` (and `ConsoleWithInputBackspaceFixed.input()` defaults to the console's setting rather than Rich's `emoji=True`), because Rich turns `:x:` into an emoji and the CLI prints user text: `{{num:x:=1}}` came out as `{{num❌=1}}`. A new console must do the same. Two wrappers over `print_info()` carry a marker from `output_style.py`, so the marker is stated once rather than at every call site: `print_debug()` (`DEBUG_MARKER`) for the startup preamble — *every* message printed before a command's own output, so `load_config.py` no longer calls `print_info()` at all — which it also gates on `--debug` and colours `DEBUG_STYLE`; and `print_dry_run()` (`DRY_RUN_MARKER`) for the `--dry-run` messages, which gates nothing and is uncoloured, because every caller is already inside a dry-run branch and the messages are ordinary output. `print_error()` and `print_warning()` likewise prepend `ERROR_MARKER` and `WARNING_MARKER`, so a warning goes through `print_warning()` rather than spelling its prefix, and anything printing an error without `printing.py` — Commander, `yd-jsonnet2json` — uses `ERROR_MARKER`, never a literal. A site that needs the marker without printing it — a conditional prefix, as in `resize.py` — imports the constant instead. The colouring is why `print_info()` takes an optional `style`: it is a Rich *base* style, so the highlighter's own colours for timestamps, quoted strings and YDIDs still apply on top, and `--no-format` ignores it with all other colouring. Reaching for it anywhere else needs a reason — plain `print_info()` is the default
- LRU cache on entity lookup functions in `entity_utils.py`
- Config dataclasses in `config_types.py`; no raw dicts for structured config

## Keeping the Ancillary Files in Step

Documentation here is spread across several files, each with its own audience, and a change that lands in the code but not in them leaves the repo describing something it no longer is. **Before finishing any change, go through this list and update what the change has made wrong or incomplete.** Most changes touch one or two of these; some touch none. Say which ones you updated, or that none needed it.

| File | Update it when |
|---|---|
| `README.md` | User-visible CLI behaviour changes: a new command, flag, property, or a change in what one does. Run `make toc` afterwards — never hand-edit the table of contents |
| `README_CLOUDWIZARD.md` | Cloud Wizard behaviour changes (`make toc_cloudwizard` for its TOC) |
| `PYPI_README.md` | The command list or the headline description changes — it is the PyPI landing page, so it summarises rather than documents |
| `yellowdog_cli/commander/README.md` | Commander's GUI behaviour changes: a new button, dialog, or a change in what an action does (`make toc_commander` for its TOC, which the Help window shows too) |
| `DEVELOPMENT.md` | Anything a developer runs or needs installed changes: make targets, prerequisites, the venv or extras, `setup-ubuntu.sh`, the project layout |
| `tests/README.md` | Test files are added, renamed or removed, or a category, flag, marker or shared fixture changes |
| `CLAUDE.md` (this file) | A new module, pattern or convention arrives, or an existing one is described here and changes |
| `.claude/rules/*.md` | The subsystem a rule file covers changes (Commander, the MCP server, variable substitution, the specification schemas). Subsystem detail goes there, not in `CLAUDE.md`, which must stay under Claude Code's 150k-character limit; a new rule file needs `paths:` frontmatter, or it loads in every session |
| `config-template.toml` | A new or changed TOML configuration property — it is the annotated reference for all of them |
| `pyproject.toml` | A new entry point, extra, package-data file or subpackage (`include-package-data` is `false`, so an unlisted asset ships broken, and the packages are listed by name, which `tests/test_packaging.py` holds to the directories; the `Makefile`'s `SRC`, which `make format`, `make pyright` and `make build` use, reaches one level of subpackage under `utils/`) |
| `CHANGELOG.md` | A user-visible change: a line under `## Unreleased`, in the same commit as the change, saying what users will notice (behaviour and exit codes, not the implementation). `release.sh` stamps the section with the version and date at release, and makes it the tag's message |
| `RELEASING.md` | The release process, branch model or PyPI arrangements change |

Two traps worth naming, both of which have bitten:

- A **new test file is invisible** unless it is added to `tests/README.md` — nothing fails, the table just quietly stops being a list of the tests.
- **Docs that describe a mechanism drift silently.** If a paragraph names a function, flag, package or file, check that it still exists and still behaves that way, rather than assuming the prose is fine because the code compiles.
