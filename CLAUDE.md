# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

YellowDog CLI (`yellowdog-cli`) is a Python CLI tool suite for managing distributed computing jobs and resources on the YellowDog platform. The CLI is one command, `yd` (`yd.py`). Users type noun commands, `yd <noun> <verb>` (`yd workrequirement submit`, `yd instance terminate`, `yd data upload`; see [Nouns and Verbs](#nouns-and-verbs)), each verb running one of ~42 registry commands (`yd-submit`, `yd-terminate`, `yd-upload`), and `yd <command>` for a registry command no verb replaces (`yd list`, `yd doctor`). The registry commands remain the code's units, keep their `yd-*` names in code, and their `yd-*` commands, released before `yd`, are deprecated entry points. It also provides `yd commander`, a PyQt6 desktop GUI that drives those same commands (see [Commander](#commander)), and `yd mcp`, an MCP server over them (see [MCP Server](#mcp-server)).

Current version: defined in `yellowdog_cli/_version.py`.

## Commands

```bash
# Install in editable/development mode
make install          # builds, then uv pip install -U -e ".[commander,mcp,jsonnet,cloudwizard]"

# Format code (ruff check --fix + ruff format)
make format

# Build distribution
make build            # uv build

# Run tests
make test                           # pytest -v -n 8
pytest -v                           # standard tests only
pytest -v -k test_variable          # run a single test file/pattern

# Run tests across all supported Python versions (3.10–3.15) via tox + uv; every extra installed, -n 8
make tox
tox -e py316          # a Python pre-release: opt-in, needing no entry (see DEVELOPMENT.md)

# Type checking
make pyright

# Code complexity: McCabe worst first, ruff's function-structure counts, lengths (a report, never a failure)
make complexity

# Install scripts/pre-push, which refuses unsigned commits headed for main (main requires signed commits)
make pre_push_hook

# Update dependencies
make update           # uv pip install -U -e ".[dev,commander,mcp,jsonnet,cloudwizard]"
```

## Architecture

### Package Structure

Each module's docstring describes it, and `ls` gives the layout: `yellowdog_cli/` holds one module per registry command (`yd-*`), `nouns/` one per noun, `commander/` and `mcp/` the two applications, and `utils/` the libraries (`dataclient/`, `specs/` and `cloudwizard/` below it). The Commander, MCP, specification-schema and substitution modules are described in full in their `.claude/rules/` files. The modules below carry a constraint their code does not make obvious:

Rules recorded in those modules that are easy to break:

- **`entity_utils.py`.** Every namespaced search goes through `search_namespaces()`, because the Platform refuses an unscoped search (403) from an Application without global read access. It also expands a namespace pattern (`yd list -n 'team-*'`, the only command taking one: `Command.namespace_patterns`, refused elsewhere by `check_namespace_is_no_pattern()` as parsed and, as configured, by `load_config._refuse_namespace_pattern()` in both `load_config_common()` and `_load_namespace_and_tag()` (the data client commands' only reader) wherever `CLIParser.namespace_pattern_refused`, which credentials and `--validate` do not affect, and which `NAMESPACE_PATTERN_REPORTERS`, `yd-doctor` and `yd-variables`, escape) into the readable namespaces it matches (`matching_namespaces()`, cached), raising `NoMatchingNamespaces` for none, which `list.list_entities()` makes an empty listing, so an empty list never reaches a search that could read it as every namespace, and `TooManyNamespaces` past `NAMESPACE_PATTERN_MAX_MATCHES`, since a search names its namespaces in its URL; an exact namespace filter after a search the Platform matches as a substring goes through `in_namespace_scope()`, and `list._in_pattern_scope()` holds a pattern listing to the namespaces matched (Image Families excepted, whose search adds public ones on purpose). Every mutation in `resource_creation.py`/`resource_removal.py` clears the caches it invalidates *in the mutating function*, straight after the SDK call (`tests/test_cache_clearing.py`). A lookup returns `None`/`[]` only for the specific failure it tolerates (404, missing permission) and raises anything else, so a 401 reaches the wrapper instead of being recorded as "not found"; display-only lookups re-raise `SESSION_FAILURES`. An ambiguous bare name raises `AmbiguousNameError` rather than taking the first match. Work Requirement name lookups search for the name, never list the namespace.
- **`literal_text()` (`variable_substitution.py`).** A `{{raw:...}}` literal is held with private-use markers in place of its delimiters until a value leaves the CLI, so that the repeated passes over a specification never substitute it; a new place a resolved value leaves (an SDK object built, a specification sent or printed, a path used) calls `literal_text()` after the value's last pass, never before one, and a new second pass over a value means moving its `literal_text()` after it (`.claude/rules/variable-substitution.md` lists the exits; `tests/test_raw_literals.py` holds them).
- **`dataclient/operations.py`.** Uploads and downloads record their outcome and return `False` instead of raising, so every argument is attempted (`copy_remote()`, for yd-copy's single pair, records and then raises). They run with `check=False` and with rclone_api's `UserWarning` silenced, because that warning spells out an inline remote's credentials. `remote_stat()` lists one level on bucket-based remotes, which report any non-object path as a directory. `warnings.catch_warnings()` is not thread-safe, so worker threads leave the filter to the pool's thread. Many files go to rclone as one list in one run (`_copy_files()`, `_delete_files()`: `--files-from-raw`, never `--files-from`, which reads a `#`, `;` or leading-space name otherwise), never one rclone process per file; a failed run's files are each recorded by whether it arrived (or went), not all as failed, and a deletion whose check listing fails too records every file failed (`_files_left()`), none being known to have gone; files each renamed on the way (`--flatten`) are copied `DATA_CLIENT_TRANSFER_WORKERS` at a time (`_copy_each()`), those sharing a destination in order. A listing reads no modification time (`--no-modtime`: on S3 one request per object) but where `yd data list` shows it (`modtime=True`). A run of many files (`_copy()`, `_copy_files()`, `_rclone_sync()`) takes `--transfers` from `limits.DATA_CLIENT_RCLONE_TRANSFERS`. `remote_stat()` runs the stat and the listing that confirms a bucket-based directory at once (`_run_quietly_together()`), since a bucket's stat of a directory lists it too; the listing is on a daemon thread, always joined, never a pool's, whose threads the interpreter waits for at exit, which `yd-doctor`'s abandoned stats must not hold up.

### Command Pattern

Most command modules use `@main_wrapper` (requires YellowDog SDK client):

```python
from yellowdog_cli.utils.wrapper import main_wrapper

# The command's configuration section, built on first use (lazy.py);
# the wrapper builds it before main() runs, so a broken one exits first
CONFIG_XXX: ConfigXxx = lazy(load_config_xxx)

@main_wrapper
def main(ctx: RunContext):
    # Command logic using ctx.args, ctx.config and ctx.client, passing ctx
    # on to the code it calls
    ...

if __name__ == "__main__":
    main()
```

A small number of standalone commands (`yd-help`, `yd-version`, `yd-format-json`, `yd-jsonnet2json`, `yd-jsonnet-fromjson` and `yd-jsonnet-factor` (`yd jsonnet tojson`, `fromjson` and `factor`), `yd-init`) need neither credentials nor a config file — they just define a bare `main()` function with no decorator.

`yd-doctor` is, with `yd-schema`, one of the two registry commands that read `ARGS_PARSER` but are on neither wrapper: both `@main_wrapper` and `@dataclient_wrapper` exit on a missing or broken configuration before `main()` runs, which is exactly the state `yd-doctor` exists to diagnose, so `doctor.py` builds its own `Context` from `ARGS_PARSER` and runs `utils/doctor_checks.CHECKS` over it instead. PAC belongs to the Proxy row: it reports `HTTPS_PROXY`, or with PAC on resolves the proxy for the API URL (a WARN when none resolves) and keeps it in `HTTPS_PROXY`, so the live checks after it — Reachable included, which does not resolve PAC itself — use it.

`show.py` (resolution split from printing, which the JSON array's shape depends on) and `submit.py` (one run's state in a `_Submission`, new and added-to Work Requirements as one pipeline, a Task Group's place as one `TaskGroupPosition`, inherited properties read through `property_cascade.Cascade`) are described in `.claude/rules/show-and-submit.md`, loaded when working on them, the Task Group and Task libraries or their tests.

`yd-commander` is the exception to all of this: it uses neither wrapper, loads no config at import, and never touches the SDK, because it runs the other commands as child processes. Its `main()` is in `commander/launcher.py` and stays free of Qt so that the missing-extra message works without PyQt6 installed. See [Commander](#commander).

Data client commands (`yd-upload`, `yd-download`, `yd-delete`, `yd-ls`, `yd-copy`) use `@dataclient_wrapper` instead — no SDK client is initialised:

```python
from yellowdog_cli.utils.dataclient.wrapper import dataclient_wrapper

CONFIG_DATA_CLIENT: ConfigDataClient = lazy(load_config_data_client)

@dataclient_wrapper
def main(ctx: DataClientContext):
    # Command logic using ctx.args and CONFIG_DATA_CLIENT
    ...
```

These commands never contact the Platform API, so they are registered as `CommandKind.DATA_CLIENT` in the command registry, whose common option set omits `--key`, `--secret`, `--url` and `--pac`: `load_config_data_client()` still bypasses `load_config_common()`, which is the sole reader of all four, and no `PlatformClient` is built. The four `ARGS_PARSER` properties are still decorated with `@allow_missing_attribute` and so return `None` rather than raising when unregistered — which is what lets `load_config_common()` keep reading them unconditionally. Passing one of the four to a data client command is an argparse error rather than a silent no-op.

### Command Registry

Every `yd-*` command's options are defined once, as data, in `utils/command_registry.py`. Its rules (option identity and `variant()`, the `yd list` and `yd cloudinfo` filter tables, command resolution from `argv[0]`, the tests holding the registry to the entry points, the Command List and the parser snapshots) are in `.claude/rules/command-registry.md`, loaded when working on the registry, `args.py`, `list.py`, `cloud_info.py`, `docs/commands.md`, `pyproject.toml` or their tests. **A new command is `script=False` and gets no entry point**, and a new `yd list` entity type, or a filter extended to one, is added to the registry's `LIST_*_TYPES` tables and to `list.py`'s `_LISTERS`.

### Nouns and Verbs

The nouns and verbs over the registry (`utils/noun_registry.py`, `utils/noun_dispatch.py`), `yd` itself (`yd.py`, `utils/top_level.py`, `utils/invocation.py`) and shell completion (`yd completion`, `utils/completion*.py`, `completion_scripts/`) are described in `.claude/rules/nouns-and-completion.md`, loaded when working on those modules or their tests. `tests/test_noun_commands.py` requires every registry command to be exactly one of generic, replaced by a verb, or a utility, so **a new command is given a verb, made generic or kept as a utility on purpose**. The registry commands keep their names in code, comments and tests; user-facing text (messages, help, docs) names the `yd` forms.

### Global State (wrapper.py)

`wrapper.py` holds two module-level globals used everywhere:
- `CLIENT` — `PlatformClient` instance (YellowDog SDK), built the first time the command uses it (`_create_client()`, which also applies `set_user_agent()`)
- `CONFIG_COMMON` — loaded from `config.toml` (or `--config` arg / env vars), built by `prepare_run()` before the command runs

`ARGS_PARSER` is a `CLIParser` instance from `args.py`, also module-level. No command module imports these three: each is given them as its context (below), bar `yd-doctor` and `yd-schema`, which import `ARGS_PARSER`, and `tests/test_command_runner.py` holds that. A command's lazy configuration section that depends on its own options reads them in `load_config.py` from the command line it holds (`load_config_data_client_destination()`, `yd-copy`'s `--dst-profile` and `--dst-prefix`).

**Every command takes them as a context** (`utils/context.py`): `main_wrapper` passes a `RunContext` to `main(ctx)`, built as the command runs from the wrapper's own `ARGS_PARSER`, `CONFIG_COMMON` and `CLIENT` (so a test sets those three on `wrapper`, never on a command module), and `dataclient_wrapper` passes a `DataClientContext`, the command line alone. The command passes it on to the code it calls, which reads `ctx.args`, `ctx.config` and `ctx.client` instead of module globals — the library code included: `follow_utils` (`follow_ids(ctx, ...)`, its threads given `ctx` too), `resource_creation`/`resource_removal` (`create_resources(ctx, ...)`), `submit_utils` (`RcloneUploadedFiles(ctx, ...)`), `task_batches` (`run_batches(ctx, ...)`) and the Cloud Wizard's provider classes (constructed with `ctx`, which they pass to the resource libraries). A command's own configuration sections (`CONFIG_WR`, `CONFIG_WP`, `CONFIG_DATA_CLIENT`) stay its module's, built lazily; `yd-doctor` and `yd-schema`, on neither wrapper, read `ARGS_PARSER` directly. **The rule for new code: a function that needs the command line, the configuration or the client takes `ctx` as its first parameter**, and a callback handed to a thread or another function carries it (`functools.partial(_remove_resource, ctx)`, `Thread(..., args=(ctx, ydid))`). A test calls such code with a context of its own (`RunContext(args=SimpleNamespace(...), config=..., client=fake.client)`, as `test_cancel.py` does), or, where it drives the real `ARGS_PARSER` and client, with its file's `_ctx()` helper, which builds one from the wrapper's (patched) globals; a stub standing in for such a function takes `_ctx` first. **No library reads `ARGS_PARSER`** (`utils/output_settings.py`): what decides how output looks and how the CLI asks (`--quiet`, `--debug`, `--json`, `--no-format`, `--pp`, `--count`, `--output-file`, `--strip-ids`, `--hide-user-data`, events as JSON, `--yes`, interactive selection, `--sort`/`--reverse`/`--details`) is `OUTPUT`, one `OutputSettings` object that `printing.py`, `tables.py`, `interactive.py`, `results.py`, `event_printing.py`, `load_config.py`, `file_substitution.py`, `dataclient/rclone.py` and `specs/validation.py` read, configured in place from the command line by `prepare_run()` (and by `yd-doctor`, `yd-schema` and the standalone `yd-version`, `yd-help` and `yd-jsonnet2json`, on neither wrapper) as a command starts; a command that adjusts its options for output configures it again (`yd-list` after `--count` and its `--details`, `yd-cloud-info` after `--count` overrides `--json`, `yd-abort` after turning interactive selection on), since the settings are a copy, not a view. What a library needs of the command's input it is given: `load_config` the command line, once (`ensure_config_loaded(args)`, by `prepare_run()`, `CONFIG_COMMON`'s builder or `yd-doctor`; the first given is kept, and `_ARGS` holds it for the lazy loaders), `register_user_variables()` the `-v` variables, the configuration file, `--env-override` and whether `--config` chose the file, the `.env` functions the file and the override, `load_resource_specifications(args, ...)` the command line, the Jsonnet loaders `dry_run`, the CSV loaders `csv_only`, the `--substitute-ids` lookups `substitute`, and `yd-doctor`'s checks their `Context.args`. The rule for new code: output behaviour is read from `OUTPUT`, never the command line, and anything else a library needs of the command line is a parameter. A test sets `OUTPUT` with `output_settings.configure_output(args)` or, for a block, `with output_settings.configured(args):`; `conftest`'s autouse `_output_settings_restored` puts it back after every test, and a test that changes a setting after configuring changes `OUTPUT` itself (`output_settings.OUTPUT.sort = ...`), not the arguments it was configured from. The action commands' shared rules are `utils/action_runner.py`'s, so a test of a prompt or message those rules make patches `action_runner` (its `confirmed`, `print_error`, `print_warning`), not the command module.

**Importing a module does nothing.** All three, and every command's configuration section (`CONFIG_WR`, `CONFIG_WP`, `CONFIG_DATA_CLIENT`, ...), are `lazy.py` stand-ins built on first use, and `load_config.py` reads the file, and `variable_substitution.py` registers the `YD_VAR_*` and `-v` variables, only when first asked (`ensure_config_loaded()`), so importing any module parses no command line, reads no configuration, builds no client, prints nothing and exits nowhere; `tests/test_lazy.py` imports every module in a fresh interpreter with a bad command line and a missing file to hold that. The wrappers parse the command line and load the configuration before the command runs (`command_runner.prepare_run()`), outside the command's exception handling, so an argument error exits 2 and a broken configuration 3, with nothing on stdout, before the command starts. The rules for new code: a command's configuration section is `lazy(load_config_xxx)`, never a call at module level; nothing reads `ARGS_PARSER`, a configuration value or `CLIENT` at module level (`submit.py`'s batch size is `_Submission.batch_size` for that reason); and a test that needs the value itself, for `dataclasses.replace()` or to patch a property on `CLIParser`, takes it with `lazy.value()`. The test process builds the command line, the configuration and `CONFIG_COMMON` in `conftest.py`'s `pytest_configure()`, before any test module is imported (and supplies dummy credentials first where none load), with stdout and stderr redirected while it does, since that is before pytest captures anything and `printing.py`'s consoles, created as it is imported, take their colouring from whether stdout is a terminal: without the redirection every test reading output would find escape codes in a terminal, while a run through a pipe would pass (`test_printing.py`'s `test_the_consoles_came_up_without_colour` fails only in a terminal): left to first use, the command line would be parsed with whatever `sys.argv` a test had set, and the configuration loaded inside a test that had patched it. A command module's own sections are built when its `main()` first runs, or a test first touches them.

The `@main_wrapper` decorator handles: PAC proxy setup (under `--dry-run` too, since most dry runs call the platform), exception catching (permission and credential errors worded by `classify()`, as the exit code is chosen), closing `CLIENT` if it was built (`_close_client()`, which closes whatever the module holds, so a test's mock is closed rather than a real client), and exit codes. The run itself is `command_runner.run_command()`, shared with `@dataclient_wrapper`, so a fix to how a command is run, flushed and exited is made once; a test patching the start-up checks patches them on `command_runner`.

`variables.py` (`yd-variables`) redacts credentials, secret-looking names and inline rclone remotes; its rules (what is redacted and said, `--show-secrets`, the misses the tests hold) are in `.claude/rules/variables.md`, loaded when working on it or its tests.

### Keeping the SDK out of start-up

Importing *anything* from `yellowdog_client` — even `yellowdog_client._version` — runs the package's `__init__`, which imports `PlatformClient` and with it every client, all ~300 model modules and `requests`: about 140ms, most of a command's start. The commands that never use a client — `yd-variables` (Commander's discovery runs it, `--quiet`, on every reparse) and the five data client commands — therefore import no SDK at all (`interactive.py`, which `yd-delete` imports to confirm, has `PlatformClient` under `TYPE_CHECKING`, since at module level it would load the SDK for every `yd-delete`), and `tests/test_sdk_free_startup.py` runs each one's real `main()` in a fresh interpreter, checking it succeeded, and fails if `yellowdog_client` was ever imported (with a control case that must load it, so the probe is known to see it). **The rule: a module every command imports never imports the SDK at module level.** That is `utils/version_info.py` (`sdk_version()` reads the package metadata), `printing.py`, `tables.py` and `event_printing.py` (`from __future__ import annotations`, the SDK names under `TYPE_CHECKING`, a local import in each function that uses one at run time — ruff's `TC004`, enabled in `pyproject.toml`, finds those (its fix, a module-level import, is unsafe, so `make format` reports it and leaves it alone) — and `event_printing.py`'s `status_counts_*()` lists built on first use), `items.py` and `misc_utils.py` (type-only), `results.py` and `printing._sdk_json()` (`Json` for an SDK object only, so a list of dicts — a data client command's `--json` result — needs none), `exit_codes.classify()` and `misc_utils.is_http_not_found()` (an SDK or `requests` exception class is checked only if its package is in `sys.modules`, since no instance can exist otherwise), `specs.sdk_models.model_class()` (the one import of `yellowdog_client.model`, reached only for an SDK-backed schema), and `wrapper.py` (`CLIENT` on first access; `pypac` and `user_agent`, which imports `requests`, only where used). A test patches one of those names (`printing.Json`, `wrapper.pac_context_for_url`) at its source, where the local import looks it up, not on the importing module. `CLIENT` is never built by `prepare_run()`, only on the command's first use of it. Two costs remain by design: `yd-variables` without `--quiet` builds the config schema, whose `[workRequirement]` and `[workerPool]` sections need the SDK; and interactive selection (`tables.py`'s `sorted_objects()`, `print_numbered_object_list()`) imports it for its `isinstance` checks, after the user has been prompted.

### The `--json` Result and Exit Codes

With `--json`, stdout holds one JSON document, the command's result, and the exit code names the kind of failure; the contract, shapes and codes are in *Machine-readable Output and Exit Codes* (`docs/json-output.md`). How the result is accumulated and flushed (`utils/results.py`), how a failure is given its exit code (`utils/exit_codes.py`'s `classify()`) and what each command records are in `.claude/rules/json-results.md`, loaded when working on a command module, the libraries that record or exit, or their tests. The rules for any new code:

- **A site that reports an outcome with `print_info()` also calls `record()`** (or the command's `record_*()` helper), since `--json` silences the one and only the other reaches the script.
- **A failure re-raised with a clearer message is raised `from` the original**, or it loses its exit code, and a missing entity is raised as `NotFoundError`, never `KeyError`.
- A `SESSION_FAILURES` failure (authentication, connection) that stops an action command is recorded with the not-attempted rest and raised as `exit_codes.ReportedFailure(cause)`, never `from` anything: `from None` clears the cause the code comes from.
- A command prints its own JSON document through `print_json()` or records, never both; `results.py` never imports `wrapper.py` or `load_config.py`, which import it.

### Configuration

Config is loaded from (in priority order): CLI args → environment variables → TOML file. The file is `--config`'s, else `config.toml` in the current directory, else the user's own (`paths.default_config_file()`), read as `./config.toml` is, environment first; `load_config.CONFIG_FILE` names it absolutely, `yd doctor` says it is the user's, and its `.env` comes after the current directory's search (`dotenv_file_path()`). `conftest.py` points `XDG_CONFIG_HOME` at an empty directory for the session, so no test reads the developer's own. Exception: if the config file is explicitly selected with `--config`/`-c`, its contents (including `[common.variables]`) take precedence over environment variables, but not over CLI args (see `config_file_explicitly_selected()` in `misc_utils.py` and `add_substitutions_from_config_file()` in `variable_substitution.py`); a file read after it, such as one it imports with `importCommon`, never replaces a variable the configuration file defines itself (`_CONFIG_FILE_VARIABLES`, filled when the loader is given `selected_file=True`). Key env vars: `YD_KEY`, `YD_SECRET`, `YD_NAMESPACE`, `YD_TAG`, `YD_URL`. Variables prefixed `YD_VAR_` are available for substitution in specs.

`load_config_common()` records where each `[common]` value came from in `CONFIG_SOURCES` (`command line`, `environment (YD_KEY)`, `config file (<name>)`, `default`, `not set`), and takes `strict=False` to return a partial `ConfigCommon` with `None` for a missing key or secret instead of exiting: `wrapper.py` passes `strict=ARGS_PARSER.credentials_required` (false for `yd-variables` alone), `yd-doctor` passes `strict=False`, and `yd-doctor` is the only reader of `CONFIG_SOURCES`. Where a file chosen with `--config` wins over a different environment value, the loser is recorded by name, never value — `ENVIRONMENT_OUTRANKED` (`_outranked()`, from `_apply_common_overrides()`, `_load_namespace_and_tag()` and `_data_client_value()`, the last only where `--config` alone put the file first) and `variable_substitution.environment_variables_outranked()` for `YD_VAR_*` — said once each under `--debug` and listed by `yd-doctor`'s 'Environment outranked' row. `ConfigCommon.key` and `.secret` are therefore `str | None`, and `wrapper.py` asserts both before building the API key.

Any TOML property can be overridden on the command line with `--property 'section.key=value'` (repeatable). Valid sections: `common`, `dataClient`, `workRequirement`, `workerPool`, `computeRequirement`. Values are JSON-parsed first (handles bool, int, float, list, dict), falling back to plain string — except for the properties listed in `STRING_PROPERTIES` (`property_names.py`), where the supplied text is kept whenever JSON would make it something other than a string, so `--property workRequirement.name=123` is a name and not an integer (`null` still unsets). The registry is keyed on the property name alone, a name being the same type wherever it appears, and `tests/test_property_overrides.py` checks it against the types recorded in that module's comment column. The config loaders type-check a few properties (`check_str`/`check_list` in `load_config.py`), among them the Work Requirement's `name`, `taskGroupName` and `taskName` and the Worker Pool's `name`, and `format_yd_name()` type-checks the name it is handed, so `name = 123` in a TOML *or* a specification file is a reported configuration error rather than an `AttributeError` raised inside the formatter. Overrides are applied after TOML validation in `load_config.py` via `_apply_property_overrides()`, bar a `common.variables.<name>` override, which `_register_variable_overrides()` registers before the file is read, as `-v` is, so the file's own values and variables take it; and the schema check that runs as a command starts sees them (see *Specification Schemas*).

File paths follow two rules. A specification file (Work Requirement, Worker Pool, Compute Requirement, resource, Node Action), from the command line or from the configuration file (which `pathname_relative_to_config_file()` rewrites relative to the current directory), is named from the current directory and opened as it is given: the loaders take no `files_directory`. A file a specification refers to — a `taskDataFile`, a CSV file, a `writeFile` content file, a `userDataFile` — is found from the files directory: `--content-path`, else the specification's directory, else the configuration file's (an absolute path is itself), by a plain `os.path.join()` at each site, `provision_utils._read_user_data()` included (never a `chdir()`, which would change the whole process's directory and report a missing file without saying where it was looked for). Nothing guesses which kind a path is: guessing it a specification when a path read from the current directory lands in the files directory would break `--content-path` for any specification outside it and misread a referenced file under a subdirectory named as the specification's.

### Coding Conventions

- Python 3.10+ syntax: use `str | None` (not `Optional[str]`), `match` statements where appropriate
- A broad exception handler (`except Exception`, `except BaseException`, a bare `except:`) re-raises its failure, or routes it by its exit code (`classify()`, `SESSION_FAILURES`, `_raise_session_failure()`, or a helper in `tests/test_broad_excepts.py`'s `ROUTING_HELPERS` that does so itself), or is listed in that test's `ALLOWED` with the reason it need not: it is where an authentication or connection failure gets swallowed or given the wrong exit code. The test fails on a new handler that does none of these, and on an `ALLOWED` entry that no handler needs any more
- The unit suite also runs on GitHub Actions on every push to `next-version`, advisory: on Linux under each Python from 3.10 to 3.15 (`.github/workflows/linux-tests.yml`, each machine set up by `setup-ubuntu.sh`, so a change to that script is tested there; pyright on the 3.10 and 3.15 jobs, each checking the code as its own Python's (`make pyright PYRIGHT_PYTHON=X.Y`)), on macOS under 3.10 and 3.15 (`.github/workflows/macos-tests.yml`), and on Windows (`.github/workflows/windows-tests.yml`). A test runs on Windows unchanged or is skipped there with the reason it cannot: paths compared by `os.path` or normalised rather than by `/` (Qt gives `C:/...`, Windows `C:\...`), a directory given to a run as `cwd` rather than by `cd` in a shell command (`cmd` changes no drive), `yd`'s output read as UTF-8 (`encoding="utf-8"`, which it writes to a pipe there too), the home directory set as `USERPROFILE` beside `HOME`, and a process probed by something other than `os.kill(pid, 0)`, which on Windows terminates it
- Every text file is opened with `encoding="utf-8"` (`open()`, `Path.read_text()`, `Path.write_text()`): without it Python uses the locale's encoding, cp1252 on Windows, and a UTF-8 specification or script holding a non-ASCII character fails to decode or arrives mangled. `tests/test_file_encoding.py` walks the package's source and fails on a text-mode call that names none
- Type hints on all new functions
- A utility never imports a command module: work two callers share is a library under `utils/` that the command is a thin layer over (`resource_creation.py` under `create.py`, `version_info.py` for the version helpers), and a utility that needs the command's help takes a callback (`json_raw.py`'s `follow`)
- Every docstring puts its triple quotes on lines of their own, a one-line docstring included (`"""`, the text, `"""`); no text on a quote line
- Constants (UPPERCASE) go in the module for their concern: `limits.py` (sizes, retries, timeouts, concurrency), `variable_syntax.py` (the substitution syntax), `output_style.py` (how output looks), `entity_names.py` (resource type names prefixed `RN_`, entity type names `ET_`), `property_names.py` (specification keys, in `ALL_KEYS`, and resource and Platform object properties, prefixed `PROP_`), `exit_codes.py` (`ExitCode`), and `settings.py` for configuration and environment names and anything else
- A count in a message goes through `printing.counted()` (`counted(len(items), 'Work Requirement')`: '1 Work Requirement', '3 Work Requirements', thousands separated), or `plural()` for the noun alone, never a `Thing(s)`; help text describing an argument keeps `(s)`
- Use `print_error()`, `print_info()`, `print_warning()` from `printing.py` — never `print()` directly. Every Rich console print passes `soft_wrap=True`, the input prompts included, since `print_string()` has already wrapped a message to `LOG_WIDTH` (`terminal_width()`, `DEFAULT_LOG_WIDTH` without a terminal or for one reporting 0 columns, where `fill()` would raise) and a table is not wrapped at all, while Rich, at 80 columns whenever the output is not a terminal, would wrap every line again and break tables, `yd-ls` paths and messages written to a pipe or a file; `event_printing.print_event()` reads an event's fields through `event_field()`/`event_counts()`/`event_count()`, as does the `--progress` bar's `_TaskCounts.of_event()` in `follow_utils.py`, since the Platform leaves a summary null and an exception there would end the stream being followed. Every Rich console the CLI builds has `emoji=False` (and `ConsoleWithInputBackspaceFixed.input()` defaults to the console's setting rather than Rich's `emoji=True`), because Rich turns `:x:` into an emoji and the CLI prints user text: `{{num:x:=1}}` would print as `{{num❌=1}}`. A new console must do the same. `print_debug()` is a line of the `--debug` trace (`debug_log.py`), logged as the calling module's, for the startup preamble — *every* message printed before a command's own output, so `load_config.py` never calls `print_info()`. `print_dry_run()`, a wrapper over `print_info()`, carries `DRY_RUN_MARKER` for the `--dry-run` messages, which gates nothing and is uncoloured, because every caller is already inside a dry-run branch and the messages are ordinary output. `print_error()` and `print_warning()` likewise prepend `ERROR_MARKER` and `WARNING_MARKER`, so a warning goes through `print_warning()` rather than spelling its prefix, and anything printing an error without `printing.py` — Commander, `yd-jsonnet2json`, `yd-format-json` — uses `ERROR_MARKER`, never a literal. A site that needs the marker without printing it imports the constant instead, as `doctor_checks.py` does to strip `ERROR_MARKER` from a message. The colouring is why `print_info()` takes an optional `style`: it is a Rich *base* style, so the highlighter's own colours for timestamps, quoted strings and YDIDs still apply on top, and `--no-format` ignores it with all other colouring. Reaching for it anywhere else needs a reason — plain `print_info()` is the default
- LRU cache on entity lookup functions in `entity_utils.py`, bar a search read lazily (`iterate_tasks_in_task_group()`), which a cache would read to its end
- Config dataclasses in `config_types.py`; no raw dicts for structured config
- The `--debug` trace is stdlib `logging`: a module logs through `LOG = logging.getLogger(__name__)` (`_LOG` where the module's other private names are), formatted by the logger (`LOG.debug("resolved %s to %s", name, ydid)`, never an f-string, which ruff's `G` rules refuse), so a run without `--debug` formats nothing. It logs a decision or a call outside the CLI that changes what the command does (a name resolved, a file found, a batch resent, a stream reconnected, an rclone run), never a step; a failure handled under `--debug` is logged with `exc_info=True` and then handled exactly as without it, never re-raised for its traceback, so the exit code never depends on `--debug`. Never log a credential: no request headers, no key or secret or a value holding one, no variable's value, an rclone remote only through `shown_remote()`, a token or Keyring secret never; `tests/test_debug_secrets.py` runs commands under `--debug` and fails on one

## Keeping the Ancillary Files in Step

Documentation here is spread across several files, each with its own audience, and a change that lands in the code but not in them leaves the repo describing something it no longer is. **Before finishing any change, go through this list and update what the change has made wrong or incomplete.** Most changes touch one or two of these; some touch none. Say which ones you updated, or that none needed it.

|---|---|
| `README.md` | The landing page: what the CLI is, prerequisites, installation, usage, the typical workflow, and the documentation map, its Documentation section, a table row per page saying what it covers; a new `docs/` page or extension README gets a row (`tests/test_docs_map.py`), and a page whose scope changes gets its row's description changed. Run `make toc` afterwards — never hand-edit the table of contents |
| `docs/*.md` | User-visible CLI behaviour changes, on the page for the topic: `commands.md` (the Command List) for a new command or flag or a change in what one does; `work-requirement-property-dictionary.md` for a new Work Requirement property (then `make schema_descriptions`); `installation.md`, `concepts.md`, `troubleshooting.md`, `configuration.md`, `variables.md`, `work-requirements.md`, `worker-pools.md`, `data-client.md`, `resources.md`, `jsonnet.md`, `json-output.md` for the rest; and `schemas.md` for the specification schemas, `--validate` and `yd schema`. Guide pages are written to `.claude/rules/docs.md` (the common case and a runnable example first, edge cases in a Details subsection). Two traps worth naming:

- A **new test file is invisible** unless it is added to `tests/README.md` — nothing fails, the table just quietly stops being a list of the tests.
- **Docs that describe a mechanism drift silently.** If a paragraph names a function, flag, package or file, check that it still exists and still behaves that way, rather than assuming the prose is fine because the code compiles.
