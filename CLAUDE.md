# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

YellowDog CLI (`yellowdog-cli`) is a Python CLI tool suite for managing distributed computing jobs and resources on the YellowDog platform. It provides ~26 `yd-*` commands (e.g., `yd-submit`, `yd-provision`, `yd-list`, `yd-upload`, `yd-download`) installable as a package. It also provides `yd-commander`, a PyQt6 desktop GUI that drives those same commands (see [Commander](#commander)).

Current version: defined in `yellowdog_cli/_version.py`.

## Commands

```bash
# Install in editable/development mode
make install          # builds, then uv pip install -U -e ".[commander,jsonnet,cloudwizard]"

# Format code (ruff check --fix + ruff format)
make format

# Build distribution
make build            # python -m build

# Run tests
pytest -v                           # standard tests only
pytest -v --run-demos               # include demo integration tests
pytest -v -n 4 --run-demos tests/test_demos.py  # parallel demos (target file to avoid unit tests consuming workers first)
pytest -v -k test_variable          # run a single test file/pattern

# Run tests across all supported Python versions (3.10–3.14) via tox + uv
make tox
tox -e py315          # Python 3.15 pre-release: opt-in, kept out of env_list (see DEVELOPMENT.md)

# Type checking
make pyright

# Update dependencies
make update           # uv pip install -U -e ".[dev,commander,jsonnet,cloudwizard]"
```

### Command Pattern

Most command modules use `@main_wrapper` (requires YellowDog SDK client):

```python
from yellowdog_cli.utils.wrapper import main_wrapper

# Module-level config loading (runs at import time)
CONFIG_XXX = load_config_xxx()

@main_wrapper
def main():
    # Command logic using CLIENT, ARGS_PARSER, CONFIG_COMMON from wrapper
    ...

if __name__ == "__main__":
    main()
```

A small number of standalone commands (`yd-help`, `yd-version`, `yd-format-json`, `yd-jsonnet2json`) need neither credentials nor a config file — they just define a bare `main()` function with no decorator.

`show.py` splits resolution from printing, and the split is load-bearing: `resolve_details()` returns the object(s) a YDID names (a list, because `--show-token` yields a Configured Worker Pool *and* its token) or `None` having reported why it could not, and `_print_items()` is the only place the JSON array's indentation and separating commas are applied. Threaded through the individual branches instead, they were passed on by ten of the nineteen and forgotten by the other nine, so a multi-ID `yd-show` emitted an array whose elements ran together without commas — unparseable for Compute Requirements, Compute Sources, Nodes, Workers, Work Requirements, Task Groups, Tasks, Image Groups and Images, which is most of what anyone shows. The old tests asserted the arguments handed to `print_yd_object()` and so saw nothing; `tests/test_show_output.py` parses the output instead. An array is emitted whenever more than one object will be printed, which includes more than one ID being asked for even if some of them fail — the shape follows the request, not how much of it succeeded — and `show_ydids()` returns the failure count so `main()` can exit 1.

`yd-commander` is the exception to all of this: it uses neither wrapper, loads no config at import, and never touches the SDK, because it runs the other commands as child processes. Its `main()` is in `commander/launcher.py` and stays free of Qt so that the missing-extra message works without PyQt6 installed. See [Commander](#commander).

Data client commands (`yd-upload`, `yd-download`, `yd-delete`/`yd-rm`, `yd-ls`, `yd-copy`) use `@dataclient_wrapper` instead — no SDK client is initialised:

```python
from yellowdog_cli.utils.dataclient_wrapper import dataclient_wrapper

CONFIG_DATA_CLIENT: ConfigDataClient = load_config_data_client()

@dataclient_wrapper
def main():
    # Command logic using ARGS_PARSER and CONFIG_DATA_CLIENT
    ...
```

These commands never contact the Platform API, so `args.py` does not register `--key`, `--secret`, `--url` or `--pac` for them: `load_config_data_client()` bypasses `load_config_common()`, which is the sole reader of all four, and no `PlatformClient` is built. The gate is the `is_data_client` predicate hoisted to the top of `CLIParser.__init__`, which also selects the data-client-only options further down. The four `ARGS_PARSER` properties are decorated with `@allow_missing_attribute` and so return `None` rather than raising when unregistered — which is what lets `load_config_common()` keep reading them unconditionally. Passing one of the four to a data client command is now an argparse error rather than a silent no-op.

### Global State (wrapper.py)

`wrapper.py` initialises two module-level globals used everywhere:
- `CLIENT` — `PlatformClient` instance (YellowDog SDK)
- `CONFIG_COMMON` — loaded from `config.toml` (or `--config` arg / env vars)

`ARGS_PARSER` is a `CLIParser` instance from `args.py`, also module-level. These three are imported directly by command modules.

The `@main_wrapper` decorator handles: PAC proxy setup, exception catching (permission/auth errors), `CLIENT.close()`, and exit codes.

`variables.py` (`yd-variables`) redacts the `key` and `secret` variables when it reports every variable, substituting `REDACTED_VALUE` from `settings.py` (`create.py` uses the same constant for a withheld Keyring password). Those two are redacted and nothing else is, because they are the only variables in the table the CLI put there itself — `load_config_common()` adds them alongside `url`, `namespace` and `tag` — so they are the only ones that can be *known* to be credentials. Redacting by name pattern was considered and rejected: it would catch `APP_KEY_DEMO`, which is an identifier rather than a secret, miss anything called `APP_CREDS`, and read as a guarantee the command cannot keep, so a user-defined variable holding a credential is reported in full and the `--help` text and README say so. Naming a variable reports it whatever it is, `--show-secrets` (the same option name `yd-cloudwizard` uses) lifts the redaction from the full report, and `tests/test_variables_command.py` holds the limit as well as the behaviour.

### Configuration

Config is loaded from (in priority order): CLI args → environment variables → TOML file. Exception: if the config file is explicitly selected with `--config`/`-c`, its contents (including `[common.variables]`) take precedence over environment variables, but not over CLI args (see `config_file_explicitly_selected()` in `misc_utils.py` and `add_substitutions_from_config_file()` in `variables.py`). The `YD_CONF` env var is no longer supported (commands error if it is set). Key env vars: `YD_KEY`, `YD_SECRET`, `YD_NAMESPACE`, `YD_TAG`, `YD_URL`. Variables prefixed `YD_VAR_` are available for substitution in specs.

Any TOML property can be overridden on the command line with `--property 'section.key=value'` (repeatable). Valid sections: `common`, `dataClient`, `workRequirement`, `workerPool`, `computeRequirement`. Values are JSON-parsed first (handles bool, int, float, list, dict), falling back to plain string — except for the properties listed in `STRING_PROPERTIES` (`property_names.py`), where the supplied text is kept whenever JSON would make it something other than a string, so `--property workRequirement.name=123` is a name and not an integer (`null` still unsets). The registry is keyed on the property name alone, a name being the same type wherever it appears, and `tests/test_property_overrides.py` checks it against the types recorded in that module's comment column. The config loaders type-check a few properties (`check_str`/`check_list` in `load_config.py`), among them the Work Requirement's `name`, `taskGroupName` and `taskName` and the Worker Pool's `name`, and `format_yd_name()` type-checks the name it is handed, so `name = 123` in a TOML *or* a specification file is a reported configuration error rather than an `AttributeError` raised inside the formatter. Overrides are applied after TOML validation in `load_config.py` via `_apply_property_overrides()`.

### Variable Substitution

Specs (TOML/JSON/Jsonnet) support `{{variable_name}}` substitution with type tags: `num:`, `bool:`, `array:`, `table:`, `format_name:`. Every value in the substitutions dictionary is a string, so a value arriving as something else has to be rendered as text: `_stringify()` does that, and renders it as **JSON** rather than with `str()`'s Python repr, because the tags read the value back as JSON — `array:` and `table:` with `json_loads()`, `bool:` as the JSON spelling — so a repr's apostrophes meant a TOML `strs = ["a", "b"]` could not be used as an array at all, and `true` was held as `"True"`. Two things it must *not* do, each with a test: a string is passed through untouched, since every value is re-rendered on each resolution pass and one given JSON's quotes would gain another pair every time; and a value with no JSON form falls back to `str()`, which is what keeps TOML's date, time and datetime values (`tomli` returns real `date`/`datetime` objects, which `json_dumps` raises `TypeError` on) rendering as the text they were written as. Three entry points need it, and all three were wrong: `_update_and_resolve_substitutions()`, the `[common.variables]` comprehension in `load_toml_file_with_variable_substitutions()`, and `add_or_update_substitution()` (which `load_config.py` calls for a `--property common.variables.x=...` override, whose value has already been JSON-parsed into a real list, dict, number or boolean). Default substitutions are defined in `VARIABLE_SUBSTITUTIONS` in `variables.py`; `{{pid2}}` is `misc_utils.PROCESS_DISCRIMINATOR`, so a hand-written name can be disambiguated the same way a generated one is, and `{{pid}}` is the full PID (`misc_utils.PID`); `{{random}}` and `{{random6}}` are three and six base 36 digits from `misc_utils.random_base36()`, base 36 rather than hexadecimal because it is the widest alphabet a YellowDog name may be built from. Default values use `:=` separator. Environment variables via `env:` prefix. Nesting has no depth limit. Syntactic nesting (`{{a_{{b}}}}`) is resolved by recursion within one pass; a substituted value that reveals a further reference needs another pass, so every loader — the three spec loaders and `load_config.py`'s section loaders, via `_resolve_section_variables()` — calls `resolve_variables_insitu()`, which repeats `_substitute_insitu_pass()` until a pass reports no changed paths. Two things make a circular reference an error (`ValueError`, naming the properties) rather than a hang or a silent pass-through: values still changing after `VAR_SUBSTITUTION_MAX_PASSES` (10) passes, which catches mutually- and self-referring `env:` values; and, once settled, an expression that is exactly a defined variable's token (`_unsubstituted_defined_variables()`), since a pass always substitutes a defined variable — this is what catches circular *table* variables, which `_update_and_resolve_substitutions()` resolves at definition to their own token (`p = '{{p}}'`), a value every pass then substitutes back to itself and so looks settled. The check uses the pass's own delimiters (and the Worker Pool ones for `userData`), so Mustache left for the platform is never mistaken for a cycle. An undefined variable is unchanged by the first pass and passes through, and the same walk (`_unsubstituted_references()`, which also looks inside a nested expression such as `{{template_{{x}}}}`) reports it with `print_warning()`, once per expression per process (`_UNDEFINED_VARIABLES_REPORTED`). Three things keep that honest. It is off until `enable_undefined_variable_warnings()`, which `main_wrapper` and `dataclient_wrapper` call as the command starts: the configuration's own passes run at import, before `namespace`, `tag`, `key`, `url` and `dataClient.*` are defined, and would report every one of them. A section resolved at import and never again would therefore go unchecked, which is what the Worker Pool sections are: `load_config_worker_pool()` keeps a copy of each as resolved, before `computeRequirement` is merged into `workerPool` (`_WORKER_POOL_SECTIONS_AS_LOADED`, so a value is listed under the section it was written in, once), and `yd-provision` and `yd-instantiate` pass it to `warn_of_undefined_worker_pool_variables()` as `main()` begins — a check-only walk (`warn_of_undefined_variables()`) sharing the once-only record. The lazy variables `yd-submit` defines per Task Group and Task (`LAZY_VARIABLE_NAMES` in `settings.py`) are never reported, since the loader passes run before they exist. And only an expression shaped like a reference — optional type tag, optional `env:`, then a name — counts (`_VARIABLE_REFERENCE`), so Docker's `{{.ID}}` or a Go template's `{{ .Values.x }}` in a task argument is left alone; a bare word such as Go's `{{end}}` would still be reported, which is why this is a warning and not an error. Every in-situ pass outside `variables.py` goes through `resolve_variables_insitu()` — the late passes in `submit.py`, `csv_data.py`, `load_resources.py`, `submit_utils.py` and the Cloud Wizard included — and `tests/test_submit_utils.py` fails if a single-pass `process_variable_substitutions_insitu()` call reappears.

The `::` unset suffix (`{{varname::}}`) removes a property entirely when the variable is undefined; if defined, its value is used normally. The bare `{{::}}` always removes the property unconditionally. Both work in TOML, JSON, and Jsonnet — `process_variable_substitutions_in_file_contents` leaves unset tokens intact so `process_variable_substitutions_insitu` can remove them after parsing. Nested inside another expression, an unset one is replaced by `_UNSET_MARKER` while the outer one resolves, and the outer one is itself unset if the marker survives — that is, if the value was needed, to build a name or as a default that is used. Leaving the inner token in place instead, as it once did, made the outer expression look up a name containing `{{missing::}}` and pass through unresolved.

CSV batch task prototypes use a separate `<<variable_name>>` delimiter system (defined in `csv_data.py`), distinct from `{{`/`}}` to allow both to coexist in the same spec without ambiguity.

### Commander

`yd-commander` is a PyQt6 desktop GUI over the CLI, in `yellowdog_cli/commander/`. It is not a second API client: **every action it takes runs a `yd-*` command as a child process** (`_run_command_in_subprocess`, via `QProcess`), so behaviour, output and configuration precedence are the CLI's. Nothing in the package imports the SDK or `wrapper.py`, and there is no `CLIENT`. `yellowdog_cli/commander/README.md` documents it for users; the notes here are the ones that matter when changing it.

- **PyQt6 is an optional extra** (`pip install "yellowdog-cli[commander]"`). `launcher.py` is deliberately free of Qt and of the heavy CLI imports, so `--help` and the missing-extra message (`check_commander_imports()`) work without it. Only after that guard does it import `commander.py` and call `run_app()`.
- **Launch options only fill the window in.** `launcher.py` parses the config file (positional or `-c`), `-y`, and the options named after the CLI's own — `-n`, `-t`, `--name`, `-P`, `-v`, `-r`, `-p` — into a frozen `StartupSettings` (`startup.py`), which `run_app()` hands to `YellowDogApp`; nothing downstream knows a value came from the command line. Three things are deliberate. Everything Commander could not hold as given is refused by argparse before Qt starts: a named file that does not exist (so a missing config file fails at launch, though one chosen in the GUI is still only logged), a variable with whitespace in it (the box is split on whitespace, so `title=my run` would become two tokens), and a field value with a tab or newline (`_edit_box_keypress_handler` deletes them); for the same reason the variables are joined with spaces, since a newline between them would be deleted and fuse `a=1` and `b=2` into `a=1b=2`. Definition file paths are resolved against the *launch* directory, what a path typed in a shell means, and stored absolute like any other selection (`_set_wr_file`/`_set_wp_file`, shared with the Select buttons). And `_apply_startup_fields()` runs in `__init__` *before* the text fields' signals are connected, so the deferred config parse is the first and only one to see the values — filled afterwards, the user-variables box would start its reparse timer and run a second parse. `tests/test_commander_startup_fields.py` asserts that timer is idle.
- **The layout lives in `commander.ui`**, loaded by `loadUi()` in `YellowDogApp.__init__`, which then connects signals to widgets by name. A renamed or deleted widget therefore fails at construction rather than at use — `tests/test_commander_ui_loads.py` is what catches that.
- **The window is one `QGridLayout` (`main_grid`) so the two columns' top rows line up.** Qt has no cross-layout notion of a row, so while the columns were two independent `QVBoxLayout`s their rows only ever aligned by accident — the separators sat 7px apart and the rows above them 6px and 10px, since the left rows hold a label and a button (h≈19) against the right's `QPlainTextEdit` fields (h=25). Row 0 and row 1 are now the two top rows and row 2 the separators beneath them, all shared; row 3 holds each column's remaining items, in the `QVBoxLayout`s that used to be the columns, and takes the vertical slack. Column 0 is the left panel, column 1 the divider (`line_5`, `rowspan=4`, which is what keeps the vertical rule unbroken), column 2 the right-hand rows, column 3 the logo (`rowspan=2`); `rowstretch="0,0,0,1"`, `columnstretch="0,0,1,0"`. Three things to know before editing this in Designer: the outer margins had to move to the grid, because those `QVBoxLayout`s now cover only row 3 and their own margins would otherwise indent it away from the rows above; their left and right margins had to go too, or the rows and separators in the shared rows reach 5px past everything below them; and the fixed 8px `spacer_above_line_7` is gone, the grid row positioning the separator instead. `tests/test_commander_ui_loads.py` asserts the paired rows share a top and a bottom exactly — which a grid guarantees and no font size affects — so a Designer edit that breaks the shared rows fails rather than merely looking wrong. The columns' *bottom* rows are deliberately not shared: aligning them left too much space above `Browse Results Directory`, detaching it from its panel.
- **Dark Mode restyles the separators by name, so a new one has to be added to the rule.** The native sunken `Line` all but disappears against a dark window, so `_dark_mode_action` paints them itself — a `#555555` background capped by `max-height`/`max-width` — through a selector listing every separator individually. A separator left out keeps the native line and is drawn a pixel thinner than the ones beside it, which is how `line_7` and `line_8` came to look wrong next to `line_4` above them. `tests/test_commander_ui_loads.py` turns Dark Mode on and asserts the horizontal separators are all the same height as each other, never a particular height, so it says nothing about the styled width.
- **The selection lists correct where their style paints a check indicator.** macOS 26 redesigned the system controls, and AppKit gates the redesign on the *main executable's linked SDK*. Where that is the macOS 26 SDK or later, Qt's macOS style draws a checkbox or radio indicator as the new 16x16 control at the painter's origin, ignoring the rect it computed; linked against an earlier SDK the same Qt draws the legacy 18x18 control in the rect. An item view clips each row's painting to that row, so every indicator but the top row's was clipped away: a ten-row confirmation showed one checkbox and nine rows that looked unticked — and untickable — however they were clicked, which is what a dialog allowing a single selection looks like. Only the painting was ever wrong; the ticking under it worked throughout, and the 'N of M selected' count said so. `fix_check_indicator_placement()` puts a `CheckIndicatorPlacement` proxy style on the list, which translates the painter by the rect's top-left before handing the primitive on — the rect's *position* is what is being ignored, so the painter's own transform is all that is left to carry it. **The cause was established causally, not by correlation**, one interpreter at a time with `vtool`, rewriting nothing but the SDK field: 26.5 → 15.5 on a Homebrew Python's `Python.app` fixes it, 15.5 → 26.5 on a uv-managed interpreter breaks it, and Apple's own opt-out (`UIDesignRequiresCompatibility` in the app's `Info.plist`) fixes it too. That matters because the correlations are badly misleading, and this was read wrongly twice before: first as a Qt 6.11.0 regression (the older PyQt6 versions had all been installed under a *different interpreter* — a version bisect across interpreters is worth nothing unless the interpreter is held still), then as a framework-versus-standalone build difference (Homebrew rebuilds against the current SDK; uv's standalone builds target an older one). Every Homebrew build measured misplaces it, 3.10 through 3.14; every uv-managed one places it correctly, 3.10 through 3.15; same PyQt6, same Qt binaries byte for byte, and 6.10.1 and 6.11.0 identical on either. Only the checkbox and radio indicators are affected — push buttons and combo boxes draw in their rect either way — and only an item view, which clips per row, turns that into a functional failure: a standalone `QCheckBox` paints its indicator at its own origin anyway, so Commander's main-window checkboxes are merely 1px high and 2px smaller, and are left alone. Qt records the general problem itself — its 'Qt for macOS - Specific Issues' page says the Widgets and Quick macOS styles "may exhibit drawing artefacts" under Liquid Glass — and names the same two escapes found here: build with Xcode 16, or set `UIDesignRequiresCompatibility`. Both belong to whoever builds the main executable, which for a Python GUI application is whoever built the interpreter, so neither is available to us; correcting the painting is the only lever at this end. So `check_indicator_is_misplaced()` measures it — one indicator painted into a transparent pixmap, and where the ink landed — rather than keying off a version or a platform: nothing available at runtime names the real condition, and the correction must stop installing itself when Qt adapts to the redesign or Apple retires the compatibility path, since over a style that places the indicator correctly it would offset it twice. The style the proxy wraps comes from `platform_style()` rather than from `QProxyStyle`'s own base-less construction, because a base-less proxy wraps a fresh instance of the *desktop* style, not of the style the application is actually using — which on Linux is Fusion under Dark Mode whatever the desktop's is. The correction is parented to the list, since `setStyle()` does not take ownership. The real thing cannot be reproduced in the tests at all: under the offscreen platform Qt's macOS style draws no check indicator anywhere, so `tests/test_commander_check_indicator.py` stands a proxy style in for it, as `MacButtonLayout` does for the platform-viewer button — and it has to install that stand-in twice, as the application's style *and* behind `platform_style()`, or the test passes whether Commander corrects anything or not. The fix itself was verified against the real thing across six interpreters: the correction installs itself on exactly the three that need it, and every row shows its own state on all six.
- **`_align_checkbox_indicators()` indents the checkboxes by the style's own button inset.** The left column's checkboxes and buttons are laid out at the same x, and then the macOS style paints a button's bevel 2px inside its widget — room for the focus ring — and a checkbox's indicator flush, so the checkboxes looked a couple of pixels further left than every button around them. The indent is read from the style (`SE_PushButtonBevel` against `SE_CheckBoxIndicator`), never written as 2, for three reasons that each bit: Dark Mode switches the application style on Linux (`_dark_mode_action` calls `setStyle("Fusion")` there; macOS and Windows go through `setColorScheme` and keep their style), so `changeEvent` recomputes on `StyleChange`; the margins are cleared before measuring, or the second measurement reads the first one's margin and the indent compounds; and it runs from `showEvent`, not `__init__`, because the style resolves the inset against the real platform and reports it flush before the window is shown — measured in `__init__` it is 0 and the indent is never applied at all. The applying direction has no test: offscreen *every* style paints the bevel flush, even the macOS one, so it cannot be reproduced headlessly. It was verified by measuring painted pixels of a real window — buttons at x=22, checkboxes at 20 before and 22 after. Measured per style on macOS: the macOS style insets the bevel by 2, while the `Windows` and `Fusion` styles report it flush and so get no indent at all, which is what keeps the stylesheet — and Qt's caveat about a stylesheet suppressing native theming — out of the picture wherever there is nothing to correct. Qt's own mechanism for this, the `SE_*LayoutItem` rects, does not apply: `WA_LayoutUsesWidgetRect` is already off on both widgets and Qt 6 still lays the checkbox out by its widget rect. What is tested is the clearing direction, which is what a style change depends on. **On Windows the indent is deliberately not applied**: that style paints its button frame inset but reports it flush, so there is nothing to key off, and the resulting 1–2px difference is accepted rather than guessed at. Two routes were tried and are dead ends — a widget cannot measure where it paints by grabbing itself (`grab()` fills its rect opaquely), and the `SE_*LayoutItem` rects, which exist to say where a widget's visual content sits, report flush on Windows and on macOS contradict the style's own painting (claiming 2 where it paints 0, which is itself part of how the misalignment arises).
- **The left column's trailing `verticalSpacer` is load-bearing.** It is the only thing in that column that can grow, and a `QBoxLayout` with nothing able to grow does not leave the surplus at the end — it spreads it evenly *between* the items. Removing it made a taller window push the buttons apart (33px between the first two at 840, 46px at 1200) while every button stayed at 25px, which reads as a layout bug rather than as a missing stretch. Exactly the trap behind `FilePreview`'s stretch-0 spacer, for the same reason. A test resizes the window and asserts the column's row offsets do not change.
- **The window opens at the height its layout asks for.** It used to open 720 tall against a layout whose minimum was 822, so Qt compressed the left column *below its minimum size hint*: every button there wants 25px and was given 18 or 19, unevenly, which is why adjacent buttons sat a pixel off each other. The `geometry` in `commander.ui` is now 840. `minimumSize` stays 720, so the window can still be made small — it just no longer starts that way, and the surplus lands in the column's spacers rather than in the buttons. A test asserts every button is at exactly its `sizeHint()` height, which catches the squeeze and the stretch alike. The same holds sideways, and is the thing to check after renaming a button: a longer label widens the row it sits in, and the button row under the Command Output is what sets the window's minimum width, so `geometry` and `minimumSize` were both moved by the same amount when those labels grew (1064/1053 to 1091/1080). The test compares the window against `minimumSizeHint()` in both directions rather than against numbers — though offscreen fonts are narrower than a real platform's, so the width half of it is a weaker guard than the height half, and a rename is still worth measuring on a real window.
- **`_align_field_labels()` is layout done in code, deliberately.** The left column's three labelled rows (`Extra Options:` twice, `Path:`) sit in three different panel layouts, so nothing lines their fields up — each began where its own label ended, at 110, 110 and 56. The method widens each label to the widest of them, measured at runtime rather than fixed in `commander.ui`, because a width in pixels is a width for one font and this suite runs where fonts are substituted. It has a precedent beside it: `select_config_label.setMargin()`, which is in code because `loadUi()` drops a `QLabel`'s margin. One consequence worth knowing: aligning the labels made the widest row demand more width, which pushed the whole column from 261 to 304 until the two fields' `minimumSize` widths came down to 150. The left column's width is set by its widest button, and `tests/test_commander_selection_labels.py` depends on that, so a field minimum that overruns it widens the column and breaks the button-label elision with it.
- **Bulk destructive actions enumerate before they act.** `_capture_dry_run_json/_summaries/_objects` run the same command with `-D --json` to list what would be affected, then `_confirm_destructive` (entities and objects) or `_choose_objects` (downloads) offers a tick-list, and only the chosen handles are passed back as explicit arguments. The shared primitives are `SelectableRow`, `entity_rows`/`object_rows`, `checked_handles` and `update_selection_state`, in `selection.py`, and `_build_selection_list_widget` on the window.
- **The file dialogs are Qt's own, with a preview pane.** They are `FileDialogs`' (`file_dialogs.py`), which the window holds as `_file_dialogs`. `build_browse_dialog` (the directory buttons) and `select_file` build a non-native `QFileDialog`, call `_add_preview_pane()` and run it through `_run_file_dialog()`; `save_file` builds and runs one the same way but adds no pane, because it names a file that does not exist yet. The selectors accept with **Select** and the browsers with **Open**, which is the honest split: only a browser opens what it is given. The pane is a `FilePreview` added to the dialog's *own* splitter — that is what makes its width draggable, and `_remember_preview_width()` keeps that width on the `FileDialogs` object for the session. The preview exists because leaving the platform's file viewer behind also leaves Quick Look behind; it decides text-versus-binary by decoding the head of the file, never by extension (task output is named whatever the task named it), and it keeps the decoded `QImage` so a widened pane rescales from the original. The text branch is capped three ways: `PREVIEW_READ_BYTES` and `PREVIEW_MAX_LINES` bound what is read and shown, and the elision line names whichever of them bit — stating only what a head-read can know, since a total line count would mean reading the whole file, which is what the byte cap exists to avoid. `PREVIEW_MAX_LINE_CHARS` is the third and is a *performance* cap, not a cosmetic one: `QPlainTextEdit` lays a single line out at superlinear cost, so a 256kB head with no newlines in it (minified JSON) took 110ms to show on a pane that is refilled at every arrow-key press, against 1.4ms once each line is cut. `_thumbnail()` activates the layout before measuring, because a pane only just shown or resized has not had its layout event delivered yet. The pane's two heading lines are pinned to the top and to the height their text needs, with a **stretch-0** spacer below them: a label defaults to taking a share of the spare height and centring its text in it, and a directory — named and kinded, with no body to show — is nothing but spare height, so the two headings ended up a third and two thirds of the way down; a spacer with stretch 1 instead would be an equal claimant with whichever body is on show and halve it.
- **One method sets the file dialogs up, and Commander keeps their preferences.** `_apply_dialog_preferences()` calls `_make_listing_a_names_only_tree()`, sets the view mode (`DIALOG_VIEW_MODE`, `ViewMode.Detail` — the tree, because it is the only one of Qt's two views a hierarchy can be shown in), the sidebar's width and the preview's, and connects `_remember_dialog_preferences()` to `finished`; all three dialogs call it once the pane (if any) is in place. The widths go in a single `setSizes`, stating every pane's but the listing's, and both of those matter because it runs on a dialog that has not been shown: the splitter reports placeholder sizes rather than the widths Qt restored, so a second call throws the first call's away, and a pane left out of the list is squashed to its minimum. That second trap was live for a while — every dialog carrying a preview showed a 90px `Co...` sidebar however wide Qt had it. The placeholders are also useless for measuring how much wider the dialog should be, so each pane says that for itself: the preview counts its whole width, being new, and the sidebar only what it gains over `sizeHint()`, capped at `SIDEBAR_PANE_WIDTH` because a sidebar dragged wider than that is a listing the user chose to shrink.
- **The listing is a names-only hierarchy.** `_make_listing_a_names_only_tree()` turns `rootIsDecorated` and `itemsExpandable` back on — Qt ships the Detail tree flat, though `QFileSystemModel` under it was always hierarchical — so a directory expands in place instead of having to be navigated into and back out of, which is what reading task output three levels down needs. It then hides every column but the name, hides the header with them, and gives the name `ResizeMode.Stretch`: left at its own width the name still elides, now with empty space beside it, which is the worst of both. Applied at build time, not when the tree is shown, so a user switching views mid-dialog finds it set up either way. Two things were verified rather than assumed, because a `QTreeView` with expandable items *can* consume a double-click to expand instead of activating the row: on macOS with a collapsed directory the double-click still navigated and did not expand, with `expandsOnDoubleClick` either way; and a file picked inside an expanded directory comes back with its full path, the selection being the model's rather than the listed directory's. The first has no test — the offscreen platform delivers neither a double-click nor a Return to an item view, and a *stock* dialog does not navigate there either — so it is a real gap, recorded in the method's docstring. The second is covered. A third thing it needs and does not do itself is ordering: `QFileSystemModel` sorts the level it is rooted at and nothing beneath it, so turning expansion on exposed levels arriving in filesystem hash order (`task_005, task_002, task_003`), which neither `sort()` on the model nor the header's sort indicator reorders and which is still unsorted twelve seconds later — so not a race. `NaturalOrderProxy`, installed by `_apply_dialog_preferences()` through `QFileDialog.setProxyModel()` before the listing is set up (it replaces the views' model, and the hidden columns are the view's properties against it), sorts every level as its rows arrive. Its comparison is a `QCollator` in numeric mode rather than the default string compare, because that is what Qt gives the one level it does sort: a plain sort would order every expanded level differently from the directory above it, which is worse than the bug. The tests read a level only once its order has stopped changing, since Qt delivers even the root level unsorted and sorts it from a queued call ~50ms later — read at that moment every one of those cases turns on timing rather than ordering.
- **The dialog preferences are Commander's own** (`dialog_settings()`, under `COMMANDER_SETTINGS_ORGANISATION`), deliberately not the ones Qt keeps under `FileDialog/*`. Qt writes its own whenever one of these dialogs closes, so every machine that has ever opened one carries a value: a default applied only when 'nothing is remembered' was therefore a no-op everywhere but a brand-new profile — and worse, the value sitting there was the 90 left by the squash bug above. Commander's store has no such ambiguity, because only Commander writes it: a value present is a value the user was shown and left, absent means they have set nothing. `_remember_dialog_preferences()` writes on every close for that reason, defaults included. `dialog_settings()` is a function, not a constant, so `conftest`'s `commander_dialog_settings` can point it at an ini file of the test's own — otherwise every GUI test would read and overwrite the developer's real preferences. The preview pane's width stays session-only (`FileDialogs._preview_width`), which is the one dialog preference not in that store.
- **The browse dialog can hand over to the platform's file viewer.** `_add_platform_viewer_button()` puts an `ActionRole` button (`NATIVE_VIEWER_BUTTON_TEXT`, worded per platform) on the dialog's button box; `_switch_to_platform_viewer()` passes `dialog.directory()` — what is on screen, not what it opened at — to `open_with_default_application()` and rejects the dialog, so `_run_file_dialog` reports no chosen file. It exists because the Qt dialog is read-only and deleting things in `results` needs the real file manager. Two details are load-bearing. `setAutoDefault(False)`: focused, an autoDefault button takes the default role from Accept, so Return would mean Finder rather than Open. And the button is moved to index 0 of the box's layout by hand, because each style appends an `ActionRole` button where it likes — macOS after Cancel, Fusion before Open — so left alone it moves about between platforms; it survives as a box member with its role, but a *style change* makes the box relayout from its own button list and undoes the move. The offscreen style used in the tests already puts it first, so `MacButtonLayout` (a `QProxyStyle` returning `MacLayout` for `SH_DialogButtonLayout`) is what makes the placement testable at all — without it the assertion passes whatever the code does.
- **The output window is a view of `_output_entries`, not the store.** It is `OutputPane`'s (`output_pane.py`), which the window holds as `_output` and logs to with `self._output.log()`; the pane owns the entries, the runs and the filter, and the window registers each command with `start_run()` and hands its `QProcess` to `attach()` before connecting its own `finished` handlers, so the last of the output lands before anything reports the process done. Every `log()` call records an `OutputEntry` (its text and the `OutputRun` it came from — a launched command, or `COMMANDER_RUN` for Commander's own messages) and appends it to the widget only if the current filter lets it through; each block it adds is tagged with its entry's index via `QTextBlock.setUserState()`, which is how the right-click menu (`_build_output_menu`) finds the run of the line under the pointer. The filter is **by run, not by the PID text**, because most of a command's output carries no PID — continuation lines, tables, JSON — and the `Executing:` line is printed with Commander's PID before the child has one; the process callbacks and the Executing line pass `run=` for that reason, and a new caller logging on a command's behalf must too. That Executing line is logged with `announcement=True` and belongs to *two* runs, its command's and `COMMANDER_RUN` (`OutputEntry.runs`), so the menu offers both and each view includes it: it is about the command, but the PID a user reads on it is Commander's. Filter membership goes through `OutputEntry.shown_under()`, never a direct `run_id` comparison, or the second membership is lost. The PID shown in the menu and bar is the one the command printed (`printed_pid`, sniffed from its `--pp` prefix) in preference to `QProcess.processId()`, which could differ where a console-script launcher stands between them. Tagging counts blocks with `block_count()`, which must agree with Qt about what starts a block (`\r` alone does) or every later line is misattributed — a test holds the two together. `_filter_output()` rebuilds the widget with `setPlainText()`, and shows or hides the filter bar and activates the layout *before* scrolling, because the bar takes its height from the output window and a view scrolled to its end before losing two rows is no longer at its end. Copy and Save read the widget, so they take what is shown, deliberately; Clear clears the entries too and ends the filter. Tests that `setPlainText()` the widget directly bypass the entries, which is harmless unless they then filter. The menu's **Show Output from Process…** opens `_build_process_dialog()`, Commander's ordinary chooser (the window's `_build_chooser_dialog`, which the pane is handed late-bound, with its All / None, count and accept gating) over `_choosable_runs()` (runs with entries, or still running), ticked from the filter shown, else the right-clicked line's run, else the latest — the `checked` parameter threaded through `_build_chooser_dialog` → `_add_selection_listing` → `_build_selection_list_widget` exists for this, the other choosers starting with every row ticked. The rows come from `OutputRun`'s `user_command_line` (the arguments before `_build_command_args()` decorated them), `started_at` and `outcome` (set by `_record_outcome` on `finished`, or `did not start`), and the listing is widened to its longest row, capped at the main window's width, because its rows are command lines. `_output_filter` is a `frozenset` of run IDs; `filter_description()` names them on the bar, Commander last. Its Return test needs `commander_dialogs.NOTHING`: macOS passes Return from the list to the dialog, which presses the default button by `animateClick()`, ~100ms later, so a driver that rejects straight after the key press wins the race.
- **A dialog list is created with a parent, or it is sized 2px short on macOS.** `_new_dialog_listing()` builds every dialog `QListWidget` as `QListWidget(self)`, although the dialog's layout reparents it straight away, because `_fit_dialog_listing_height()` fixes its height from `frameWidth()` and the macOS style reports 6 for a widget with no parent (a prospective window) against 7 once it is inside one. The confirmation and chooser lists were built unparented until the process chooser exposed it: each showed a scrollbar and clipped its last row (a 58px viewport for three 20px rows). Offscreen reports 7 either way, so no test can see this; it was measured on the real platform, before and after.
- **`_notify()` is the modal notice**: it logs the message and then shows it, so the output window keeps the whole narrative either way, and it degrades to log-only when `--yes` is set (nobody is there to press OK) or while shutting down. `_build_notice_dialog()` is split out so a test can arm the real dialog rather than stub `exec()`, and it forces `PlainText` — a notice carries Windows paths and entity names, which as rich text lose their backslashes and their angle-bracketed parts. Only one caller so far, deliberately: Browse Results Directory with no results directory yet. The other dead-end notices remain log-only, and `tests/test_commander_notices.py` holds that line.
- **`Confirmation.__bool__` raises deliberately.** A confirmation carries both `proceed` and `handles`, and `if self._confirm_destructive(...)` — which is what the natural mistake looks like — would be true even for a refusal. Check `.proceed`.
- **Synchronous helpers block in nested event loops** (`_run_nested`), which keeps the window responsive while a child process runs. That makes re-entrancy possible, so the enumerating actions are guarded by `_operation_in_flight()` and a `_nested_depth` counter (a counter, not a flag: the config parse deferred with `singleShot(0)` runs inside the first loop to spin, so depth 2 is normal). A re-entrant enumeration returning `None` would read as "enumeration failed", which for a destructive action means falling back to the whole scope — hence refusing early.
- **Placeholders come from `yd-variables`.** Discovery is `ConfigDiscovery`'s (`config_discovery.py`), which the window holds as `_discovery` and reads the result from as `_discovery.namespace` and `_discovery.tag`; the window keeps the config-file *selection* (`_config_file`, the watcher, `_working_dir()`), which every command depends on, and tells discovery when it changes. `_parse_yd_config()` runs it (via `_yd_variables_command()`, the seam the tests override) to resolve the namespace and tag for the current config file. Every failure is reported through `_report_discovery_failure()` however quiet the parse was — a quiet parse suppresses the announcement, never the reason it failed — and a *timed-out* one is retried once, after a delay and with a longer budget, because the first `yd-*` of a session on Windows can need longer than the 10s budget to start and nothing else would try again before a restart. The single exception is `_nothing_is_configured()`: with **no** config file selected, `yd-variables` is given `--nc` and has only the environment to work from, and an environment without credentials makes it exit 1 with `Missing configuration data: 'key'` before resolving anything — an error in the output window at startup and on every Deselect, in front of a user who had done nothing. Narrow in both directions: with a file selected that same message means the selected file cannot be used, and with none selected every other failure is still reported, because credentials and namespace/tag in `YD_*` variables with the definition files nominated by hand is a supported way to run Commander. It matches on `MISSING_CONFIG_DATA` from `settings.py` — the CLI has one exit code for everything, so the message is the only signal, and it is the CLI's own definition of it rather than a copy, so the two cannot drift. Two things that fall out of it: `invalidate()` also clears `_last_discovery_failure`, because a suppressed failure never becomes the message the de-duplication compares against and would otherwise mask the same failure recurring after a reselection (only the three config-file paths reach it; the user-variables reparse does not, which is what leaves that de-duplication doing its job); and `_set_config_file(None)` calls `clear()`, which empties `namespace`/`tag` and not just the placeholders showing them, since `_object_path()` builds the default download and delete path out of the tag, so a stale one is a path acted on. Wire new discovery callers through `reparse_placeholders()`, which is the only thing that pairs a parse with the placeholders and with that retry; calling `_parse_yd_config()` directly is how three of the four callers silently had no retry. It is stubbed in the tests (see below), so nothing there spawns a CLI process for it. The one caller that does *not* go straight there is the user-variables box: it reparses 600ms after every keystroke, and every variable is typed through states that are not yet `name=value`, so `_reparse_placeholders_after_edit()` holds the reparse until `variable_is_complete()` accepts every token in the box — otherwise adding `instances=3` reported `Error in variable substitution 'instances'` on the way through, an error the user had not made. It reports nothing while it waits, because at 600ms after a keystroke an unfinished variable and a wrong one are the same text; a genuinely malformed one is reported by the CLI when a command is actually run, and the guard is deliberately not in `_namespace_tag_and_user_vars()`, which those commands share.
- **A selected definition file's path is absolute on purpose.** `_wr_file`/`_wp_file` are stored with `abspath()`, not `relpath()`, because they have two consumers reading them against different bases: they are passed to a child process that runs in the config file's directory (`_working_dir()`), and Show opens them in Commander's own process, whose directory is wherever it was launched from. A path relative to either base is wrong for the other — stored `relpath()`-from-cwd, `yd-submit -r ../demos/bash/x.json` went looking under the config directory and got `No such file or directory`. The config file needs no such care, since its consumers take `_config_dir()`/`_config_basename()` from it rather than passing it on. Note that the command-construction tests are blind to this class of bug when they set `_wr_file` directly and assert the argument verbatim: `tests/test_commander_commands.py` resolves the handed-over path against `_working_dir()` the way the child does, and one case reads the file back through Show, which is what a config-dir-relative 'fix' breaks.
- **A missing tag is not a path.** `_object_path()` returns `None` when the Path field is empty and no tag has been discovered, and the download and delete actions must refuse on it (`NO_OBJECT_PATH`). It used to interpolate the missing tag into the default `f"{tag}*"`, so a failed discovery handed `yd-download`/`yd-delete` the literal `None*` — and with confirmations suppressed, `yd-delete -Ry None*` would have run.
- `commander.py` carries `E402`/`RUF005` per-file ignores in `pyproject.toml`: it was lifted from the standalone `yellow-gui` demo repo, and those are pre-existing findings kept out of the relocation diff. The modules split out of it (`selection.py`, `file_dialogs.py`, `output_pane.py`, `config_discovery.py`, `output_model.py`, `check_indicator.py`, `host.py`, `elision.py`, `command_history.py`) need neither, so none is extended to them.
- **The window's collaborators own their state, and are reached through it.** `FileDialogs` (`_file_dialogs`), `OutputPane` (`_output`) and `ConfigDiscovery` (`_discovery`) are each given what they need — a parent and a font; the output widgets, the window for its layout and width, and the chooser builder; the four fields discovery reads and writes, and seven window hooks — rather than the window, so what they can touch is what they were handed. Tests reach them the same way (`window._output._filter_output`, `monkeypatch.setattr(window._file_dialogs, "save_file", ...)`), patching the instance. Two consequences. A handler a collaborator connects in its own constructor must be patched on *its* class before the window is built, which is what `OWNERS` in `test_commander_button_wiring.py` is for. And a window method a collaborator calls is handed over as a lambda, not a bound method (`build_chooser=lambda ...: self._build_chooser_dialog(...)`): bound at construction, `commander_dialogs.drive_chooser`'s later patch of the window would not reach it. Nothing drives the process chooser that way today, so no test fails without that lambda; it is there so that the driver cannot silently miss. Discovery's are load-bearing now: `test_commander_shutdown.py` replaces `_run_nested` on the window during a real discovery, and with `run_nested` bound early `test_config_parse_timeout_is_bounded` fails. `shutting_down` and `config_selected` read window attributes, so they could only ever be callables.
- **Patch a split-out function where it is defined, and call it through its module where a test must reach it.** `conftest` points `file_dialogs.dialog_settings` at a test ini file, and every caller is `FileDialogs`, in the same module, reading the module global — which the patch replaces. Anything outside `file_dialogs.py` that needs it must call `file_dialogs.dialog_settings()` rather than import the name: imported, it would be a second binding the patch did not reach, and the tests would read and write the developer's real preferences without failing. The check-indicator test patches `check_indicator.platform_style` for the same reason. `monkeypatch.setattr` refuses a missing attribute, so a patch left on `commander` after a move fails loudly rather than going quiet.

### Resource Specification Test Corpus

`tests/resources/` is the single source of resource specifications used by the resource-definition tests (`test_resource_specs.py`, `test_resource_property_coverage.py`, `test_system_resources.py`) — one Jsonnet file per resource type, each with a minimal variant (only required properties) and a maximal one (every settable property), loaded through the CLI's own loader rather than duplicated as separate fixtures. See `tests/resources/README.md` for the minimal/maximal convention and how to add a new resource type.

`tests/resource_models.py` is a write-side coverage gate: it introspects the SDK's own dataclasses for every model the corpus's resource types build (via `create.py`'s `_get_model_object`) and fails, naming the property, when a settable property is set by no specification at all. A property can only be excluded from the gate by a registry entry (`SERVER_ASSIGNED_COVERAGE`, `NOT_SETTABLE`, `NOT_TESTED`) carrying a stated reason — never inferred from the dataclass's own `field.init`, since the SDK structures an `init=False` field from a specification exactly like any other. A live read gate in `test_system_resources.py` then demands every property excluded as platform-assigned either actually come back from a real `yd-show` at least once, or carry a recorded reason why this suite cannot make it come back (most of the waived ones belong to a compute source that never provisions a real instance, so it has no status, no instance summary and no exhaustion to report); an exclusion the platform has started honouring is reported as stale, so a waiver cannot outlive its reason. Consequently, closing a coverage gap the SDK opens (a new property on an existing model) is an edit to one `.jsonnet` file, not to several JSON fixtures.

### Coding Conventions

- Python 3.10+ syntax: use `str | None` (not `Optional[str]`), `match` statements where appropriate
- Type hints on all new functions
- Constants in `settings.py` (UPPERCASE); property name constants prefixed `PROP_`, resource name constants prefixed `RN_`
- Use `print_error()`, `print_info()`, `print_warning()` from `printing.py` — never `print()` directly. Two wrappers over `print_info()` carry a marker from `settings.py`, so the marker is stated once rather than at every call site: `print_debug()` (`DEBUG_MARKER`) for the startup preamble — *every* message printed before a command's own output, so `load_config.py` no longer calls `print_info()` at all — which it also gates on `--debug` and colours `DEBUG_STYLE`; and `print_dry_run()` (`DRY_RUN_MARKER`) for the `--dry-run` messages, which gates nothing and is uncoloured, because every caller is already inside a dry-run branch and the messages are ordinary output. A site that needs the marker without printing it — a conditional prefix, as in `resize.py` — imports the constant instead. The colouring is why `print_info()` takes an optional `style`: it is a Rich *base* style, so the highlighter's own colours for timestamps, quoted strings and YDIDs still apply on top, and `--no-format` ignores it with all other colouring. Reaching for it anywhere else needs a reason — plain `print_info()` is the default
- LRU cache on entity lookup functions in `entity_utils.py`
- Config dataclasses in `config_types.py`; no raw dicts for structured config

### Testing Commander's GUI

Commander's dialogs are tested as dialogs, through `tests/gui_harness.py` (generic Qt helpers) and `tests/commander_dialogs.py` (drivers for Commander's own confirmation and chooser). Three rules, each of which exists because breaking it let a bug reach a user:

- **Never stub `dialog.exec()`.** Use `gui_harness.run_modal()` when the test owns the dialog, or `commander_dialogs.drive_confirmation()` / `drive_chooser()` when production builds and execs it. Both queue the interaction with `QTimer.singleShot(0, ...)` so it lands inside the *real* modal loop, which means a click has to travel the real button-box wiring to have any effect. A stubbed `exec()` cannot tell a working button from an inert one.
- **Assert geometric relationships, never pixel counts.** `gui_harness.visible_rows(listing)` rather than a height in pixels: CI nodes substitute fonts, so absolute measurements do not travel. A list squeezed flat or robbed of its height by a scrollbar still has correct-looking arithmetic — only "how many rows can be seen" catches it.
- **Assert outcomes, not arguments.** Contract tests over `_run_command_in_subprocess` args are useful but blind: every GUI bug that has reached a user lived in a seam those tests stubbed or asserted around.

Constructing a `YellowDogApp` defers `_set_config_file` with `singleShot(0)`, and that runs `yd-variables` in a child process inside whichever event loop spins first — usually a dialog's `exec()`. `conftest`'s autouse `_no_config_discovery` stubs `ConfigDiscovery._parse_yd_config` for any test that uses `qapp`, since none of them are about discovery; the two that test the method itself carry `@pytest.mark.real_config_parse`. Left live it cost 235 CLI invocations and most of the GUI suite's runtime, made the tests depend on an installed `yd-variables`, and let the environment's namespace and tag leak in.

Everything runs under `QT_QPA_PLATFORM=offscreen` with no display, so it works on a headless CI node. Nodes without a usable Qt skip: every Commander test module calls `tests/qt_guard.py`'s `require_qt()` before importing anything that pulls in Qt, and the `qapp` fixture guards again. That guard is deliberately not `pytest.importorskip` — from pytest 9.1 it skips only on `ModuleNotFoundError`, so PyQt6-installed-but-`libGL`-missing (a minimal Linux image) errored instead of skipping. Calling it before the imports is what the `E402` per-file ignores in `pyproject.toml` are for. Modal runs are watchdogged, because a dialog that never closes would hang CI rather than fail it. An autouse `conftest` fixture surfaces assertions raised inside Qt callbacks, which Qt would otherwise print and discard.

Note that `_build_destructive_dialog` returns a dialog whose buttons are *not* wired — `_confirm_destructive` attaches a `clicked` handler afterwards, because it needs to know which button was pressed. Drive it through `_confirm_destructive`, not from the builder. `_build_chooser_dialog` wires its own box and can be driven directly.

## Keeping the Ancillary Files in Step

Documentation here is spread across several files, each with its own audience, and a change that lands in the code but not in them leaves the repo describing something it no longer is. **Before finishing any change, go through this list and update what the change has made wrong or incomplete.** Most changes touch one or two of these; some touch none. Say which ones you updated, or that none needed it.

| File | Update it when |
|---|---|
| `README.md` | User-visible CLI behaviour changes: a new command, flag, property, or a change in what one does. Run `make toc` afterwards — never hand-edit the table of contents |
| `README_CLOUDWIZARD.md` | Cloud Wizard behaviour changes (`make toc_cloudwizard` for its TOC) |
| `PYPI_README.md` | The command list or the headline description changes — it is the PyPI landing page, so it summarises rather than documents |
| `yellowdog_cli/commander/README.md` | Commander's GUI behaviour changes: a new button, dialog, or a change in what an action does |
| `DEVELOPMENT.md` | Anything a developer runs or needs installed changes: make targets, prerequisites, the venv or extras, `setup-ubuntu.sh`, the project layout |
| `tests/README.md` | Test files are added, renamed or removed, or a category, flag, marker or shared fixture changes |
| `CLAUDE.md` (this file) | A new module, pattern or convention arrives, or an existing one is described here and changes |
| `config-template.toml` | A new or changed TOML configuration property — it is the annotated reference for all of them |
| `pyproject.toml` | A new entry point, extra, or package-data file (`include-package-data` is `false`, so an unlisted asset ships broken) |
| `RELEASING.md` | The release process, branch model or PyPI arrangements change |

Two traps worth naming, both of which have bitten:

- A **new test file is invisible** unless it is added to `tests/README.md` — nothing fails, the table just quietly stops being a list of the tests.
- **Docs that describe a mechanism drift silently.** If a paragraph names a function, flag, package or file, check that it still exists and still behaves that way, rather than assuming the prose is fine because the code compiles.
