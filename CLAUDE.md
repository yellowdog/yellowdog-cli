# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

YellowDog CLI (`yellowdog-cli`) is a Python CLI tool suite for managing distributed computing jobs and resources on the YellowDog platform. It provides ~38 `yd-*` commands (e.g., `yd-submit`, `yd-provision`, `yd-list`, `yd-upload`, `yd-download`) installable as a package. It also provides `yd-commander`, a PyQt6 desktop GUI that drives those same commands (see [Commander](#commander)), and `yd-mcp`, an MCP server over them (see [MCP Server](#mcp-server)).

Current version: defined in `yellowdog_cli/_version.py`.

## Commands

```bash
# Install in editable/development mode
make install          # builds, then uv pip install -U -e ".[commander,jsonnet,cloudwizard]"

# Format code (ruff check --fix + ruff format)
make format

# Build distribution
make build            # python -m build

# Run tests
pytest -v                           # standard tests only
pytest -v --run-demos               # include demo integration tests
pytest -v -n 4 --run-demos tests/test_demos.py  # parallel demos (target file to avoid unit tests consuming workers first)
pytest -v -k test_variable          # run a single test file/pattern

# Run tests across all supported Python versions (3.10–3.14) via tox + uv
make tox
tox -e py315          # Python 3.15 pre-release: opt-in, kept out of env_list (see DEVELOPMENT.md)

# Type checking
make pyright

# Update dependencies
make update           # uv pip install -U -e ".[dev,commander,jsonnet,cloudwizard]"
```

### Command Pattern

Most command modules use `@main_wrapper` (requires YellowDog SDK client):

```python
from yellowdog_cli.utils.wrapper import main_wrapper

# Module-level config loading (runs at import time)
CONFIG_XXX = load_config_xxx()

@main_wrapper
def main():
    # Command logic using CLIENT, ARGS_PARSER, CONFIG_COMMON from wrapper
    ...

if __name__ == "__main__":
    main()
```

A small number of standalone commands (`yd-help`, `yd-version`, `yd-format-json`, `yd-jsonnet2json`) need neither credentials nor a config file — they just define a bare `main()` function with no decorator.

`yd-doctor` is the one registry command on neither wrapper: both `@main_wrapper` and `@dataclient_wrapper` exit on a missing or broken configuration before `main()` runs, which is exactly the state `yd-doctor` exists to diagnose, so `doctor.py` builds its own `Context` from `ARGS_PARSER` and runs `utils/doctor_checks.CHECKS` over it instead. PAC belongs to the Proxy row: it reports `HTTPS_PROXY`, or with PAC on resolves the proxy for the API URL (a WARN when none resolves) and keeps it in `HTTPS_PROXY`, so the live checks after it — Reachable included, which no longer resolves PAC itself — use it.

`show.py` splits resolution from printing, and the split is load-bearing: `resolve_details()` returns the object(s) a YDID names (a list, because `--show-token` yields a Configured Worker Pool *and* its token) or `None` having reported why it could not, and `_print_items()` is the only place the JSON array's indentation and separating commas are applied. Threaded through the individual branches instead, they were passed on by ten of the nineteen and forgotten by the other nine, so a multi-ID `yd-show` emitted an array whose elements ran together without commas — unparseable for Compute Requirements, Compute Sources, Nodes, Workers, Work Requirements, Task Groups, Tasks, Image Groups and Images, which is most of what anyone shows. The old tests asserted the arguments handed to `print_yd_object()` and so saw nothing; `tests/test_show_output.py` parses the output instead. An array is emitted whenever more than one object will be printed, which includes more than one ID being asked for even if some of them fail — the shape follows the request, not how much of it succeeded — and `show_ydids()` returns the exit code: 0, `NOT_FOUND` when every failure was a not-found (counted by `_report_not_found()` in a per-run `_TALLY`, since the resolvers report and return `None`), else 1. The resolvers re-raise a `SESSION_FAILURES` failure instead of reporting it; `show_ydids()` then prints what was resolved and raises `ReportedFailure`.

`yd-commander` is the exception to all of this: it uses neither wrapper, loads no config at import, and never touches the SDK, because it runs the other commands as child processes. Its `main()` is in `commander/launcher.py` and stays free of Qt so that the missing-extra message works without PyQt6 installed. See [Commander](#commander).

Data client commands (`yd-upload`, `yd-download`, `yd-delete`/`yd-rm`, `yd-ls`, `yd-copy`) use `@dataclient_wrapper` instead — no SDK client is initialised:

```python
from yellowdog_cli.utils.dataclient_wrapper import dataclient_wrapper

CONFIG_DATA_CLIENT: ConfigDataClient = load_config_data_client()

@dataclient_wrapper
def main():
    # Command logic using ARGS_PARSER and CONFIG_DATA_CLIENT
    ...
```

These commands never contact the Platform API, so they are registered as `CommandKind.DATA_CLIENT` in the command registry, whose common option set omits `--key`, `--secret`, `--url` and `--pac`: `load_config_data_client()` still bypasses `load_config_common()`, which is the sole reader of all four, and no `PlatformClient` is built. The four `ARGS_PARSER` properties are still decorated with `@allow_missing_attribute` and so return `None` rather than raising when unregistered — which is what lets `load_config_common()` keep reading them unconditionally. Passing one of the four to a data client command is an argparse error rather than a silent no-op.

### Command Registry

Every `yd-*` command's options are defined once in `utils/command_registry.py`, as data. `CLIParser` builds argparse from a command's `all_options()` — the kind's common set, then the command's own, in the order argparse will print them — so the option order in a `Command` is load-bearing for `--help`. A shared option is one module constant (`NAMESPACE`, `FOLLOW`, `DRY_RUN`, ...) and a command whose wording differs uses `CONSTANT.variant(help=...)`, which keeps the option's identity; `Command.has()` and `option_named()` both compare by that identity, and `option_named()` is what the README checker relies on to look a flag up. Three options are separate constants rather than `variant()`s, because a `variant()` merges keyword arguments onto the base rather than replacing them and cannot change the `flags` tuple, so it can narrow a keyword's value but never drop one or remove an alias: `DRY_RUN_JSON` (a bare `--json` with no `-J`, unlike the shared `JSON`), `RESIZE_COMPUTE_REQUIREMENT` (a flag with no `type`, unlike `COMPUTE_REQUIREMENT`'s) and `NODE_ACTION_STATUS` (a flag with no `dest`, unlike yd-list's `STATUS`, which appends into `status_filter`) — each keeps its base's first long flag, so identity is preserved. The command is resolved from `sys.argv[0]` by exact lookup after `command_from_argv0()` normalises it (basename, `.py`/`.exe`/`-script` stripped, underscores to hyphens, `yd-` prefixed), so a command name inside the install path no longer matters and no substring ordering does either; an unknown name gets the API common set only, which is what pytest's executable gets. Post-parse checks are `validators` on the commands they apply to. A positional a data client command needs is `nargs="*"` with `Option.tool_required` (`yd-upload`'s `local_paths`, `yd-download`'s `remote_paths`, `yd-copy`'s two paths, checked by `check_copy_args`), so that `--which-rclone` and `--upgrade-rclone` run without one: `check_paths_given` requires it otherwise, and the MCP tools, which offer neither option, mark it required. yd-list's are table-driven: `LIST_NAME_TYPES`, `LIST_STATUS_TYPES`, `LIST_ACTIVE_TYPES`, `LIST_ID_TYPES` and `LIST_SUBSTITUTE_TYPES` say which entity types each filtering option applies to, and `check_list_options` refuses it for any other, so a new entity type, or a filter extended to one, is added to those tables. `requires_namespace_and_tag` is an explicit field rather than derived from having `--namespace`, because `yd-list` has the option and is not one of them. `help.py`'s `main()` renders `COMMANDS` for `yd-help`'s listing, sorted by name — which moved `yd-copy` to its true alphabetical position, the old hand-written table having had it out of place; `yd-rm`, which shares `yd-delete`'s `Command` object, is listed as a synonym for it rather than with the summary twice; A command's extra is read from its summary's trailing `(needs the <extra> extra)`, and `EXTRA_PROBES` names one package per extra that `find_spec()` looks for, never importing it, to say whether it is installed; `--json` gives the extra, `installed` and `synonymOf` as fields. `yd-commander` and `yd-mcp`, entry points with no registry entry, are listed from `help.py`'s own `OTHER_COMMANDS` table, which `tests/test_command_registry.py` holds to the entry points the registry lacks. `tests/test_command_registry.py` holds the registry to `pyproject.toml`'s entry points, and `tests/test_readme_command_list.py` holds the README's Command List to the registry: the Universal and Shared tables' membership and short forms, the preamble's exceptions, and every option bullet under a `### yd-x` heading naming an option that command takes. Its section parser ignores fenced code blocks (`_outside_fences()`), so a `#` shell comment inside an example is never mistaken for a heading or a bullet, and `yd-list`'s options, given in a table rather than as bullets, are checked as table rows. Wording is never checked, and nothing in the README is generated. `tests/test_parser_snapshots.py` holds every command's option *shapes* — each action's kind, flags, `nargs`, `const`, `default`, `type`, `choices` and `required` — to `tests/parser_snapshots.json`, never their wording, and the file is regenerated with `pytest tests/test_parser_snapshots.py --update-parser-snapshots` when a shape change is intended.

### Global State (wrapper.py)

`wrapper.py` initialises two module-level globals used everywhere:
- `CLIENT` — `PlatformClient` instance (YellowDog SDK), built the first time it is asked for (the module `__getattr__`, `_create_client()`, which also applies `set_user_agent()` and stores the client as a real module attribute) — every command that uses it imports it by name, so for them it is built at import as it always was
- `CONFIG_COMMON` — loaded from `config.toml` (or `--config` arg / env vars)

`ARGS_PARSER` is a `CLIParser` instance from `args.py`, also module-level. These three are imported directly by command modules.

The `@main_wrapper` decorator handles: PAC proxy setup (under `--dry-run` too, since most dry runs call the platform), exception catching (permission and credential errors worded by `classify()`, as the exit code is chosen), closing `CLIENT` if it was built (`_close_client()`, which closes whatever the module holds, so a test's mock is closed rather than a real client), and exit codes. The run itself is `command_runner.run_command()`, shared with `@dataclient_wrapper`, so a fix to how a command is run, flushed and exited is made once; a test patching the start-up checks patches them on `command_runner`.

`variables.py` (`yd-variables`) redacts the `key` and `secret` variables, named or not, substituting `REDACTED_VALUE` from `settings.py` (`create.py` uses the same constant for a withheld Keyring password). Those two (`SECRET_VARIABLES`) are the only variables in the table the CLI put there itself — `load_config_common()` adds them alongside `url`, `namespace` and `tag` — so they are the only ones that can be *known* to be credentials. It also redacts every other variable whose name matches `SECRET_VARIABLE_NAME_PATTERN` in `settings.py` (`secret|password|passwd|token|credential|private_key`, case-insensitive, `re.search`), and says so: when at least one was redacted that way, `main()` prints one `print_warning()` line ahead of the JSON giving the count and the pattern and saying everything else is shown in full and `--show-secrets` reports all (so `--quiet` suppresses it with the other warnings). Name-pattern redaction was once considered and rejected: it would catch identifiers, miss badly-named secrets such as `APP_CREDS`, and read as a guarantee the command cannot keep. That objection was to a *silent* heuristic; this one states what it matched and that nothing else was withheld, so it cannot be read as a guarantee — and `key` alone is left out of the pattern so that `APP_KEY_DEMO`, an identifier, is still shown. A value redacted by the pattern is already `REDACTED_VALUE` by the time the undefined-variable check runs, so it carries no reference to check, and only `key` and `secret` are left out of that check by name. All of the redaction applies to a named variable too, with a line saying `key`/`secret` were redacted when they were named, and `--show-secrets` (the same option name `yd-cloudwizard` uses) is the one way round it: naming a variable used to report it whatever it was, which let an MCP tool, which can never pass `--show-secrets`, ask for `secret` by name. `report_variables()` returns a `Report` (the variables, and which were redacted as credentials, by the pattern, or by value), so the rules and the notes counting them are decided in one place. `yd-variables` is the one command with `requires_credentials=False` in the registry (`ARGS_PARSER.credentials_required`), so `wrapper.py` loads `[common]` non-strictly for it and it runs, and reports `key`/`secret` as `null`, without an application key or secret; a named variable never defined is warned of, and a name no variable could have is refused as parsed (`check_variable_names`). And `tests/test_variables_command.py` holds the misses (`APP_KEY_DEMO`, `APP_CREDS`) as well as the matches; its `_run()` drops inherited `YD_VAR_*` variables, which would otherwise join every full report and the note's count. The one extension of that limit is structural, not a name guess: the `{{dataClient.remote}}` and `{{dataClient.<profile>.remote}}` variables are the CLI's own too, and an inline rclone connection string carries its credentials in its parameters, which the rclone parser can identify — so the full report renders those through `rclone_utils.shown_remote()` (name, type and provider kept, `<N parameters redacted>` for the rest; a named remote unchanged), exactly as `yd-doctor`'s profile rows do, under the same rule: lifted by `--show-secrets` alone. `is_remote_variable()` in `variables.py` is the name test, built from the `dataClient` section and `remote` property constants. The same rendering applies to any variable whose *value* is an inline connection string (`rclone_utils.is_inline_remote()`: rclone's `:backend,...` form, or `NAME,...` with a `type` parameter, optionally `rclone:`-prefixed — deliberately strict, since `parse_rclone_config()` reads anything with a comma as a remote and `shown_remote()` would turn `a,b` into `a`), because a user's `remote_with_keys` carries its credentials exactly as `{{dataClient.remote}}` does; for a variable the CLI did not register, `main()` prints a note giving the count (`withheld_remotes()`), as it does for the name pattern. `shown_remote()` keeps an `rclone:` prefix but withholds a trailing `:path` with the last parameter: it cannot be told from the `:port` of a URL-valued parameter such as `endpoint`, and splitting on the last `:` leaked that port in `yd-doctor`'s report.

### Keeping the SDK out of start-up

Importing *anything* from `yellowdog_client` — even `yellowdog_client._version` — runs the package's `__init__`, which imports `PlatformClient` and with it every client, all ~300 model modules and `requests`: about 140ms, most of a command's start. The commands that never use a client — `yd-variables` (Commander's discovery runs it, `--quiet`, on every reparse) and the five data client commands — therefore import no SDK at all, and `tests/test_sdk_free_startup.py` runs each one's real `main()` in a fresh interpreter and fails if `yellowdog_client` was ever imported (with a control case that must load it, so the probe is known to see it). **The rule: a module every command imports never imports the SDK at module level.** That is `version.py` (`sdk_version()` reads the package metadata), `printing.py` (`from __future__ import annotations`, the SDK names under `TYPE_CHECKING`, a local import in each function that uses one at run time — ruff's `TC004` finds those — and the `status_counts_*()` lists built on first use), `items.py` and `misc_utils.py` (type-only), `results.py` and `printing._sdk_json()` (`Json` for an SDK object only, so a list of dicts — a data client command's `--json` result — needs none), `exit_codes.classify()` and `misc_utils.is_http_not_found()` (an SDK or `requests` exception class is checked only if its package is in `sys.modules`, since no instance can exist otherwise), `sdk_models.model_class()` (the one import of `yellowdog_client.model`, reached only for an SDK-backed schema), and `wrapper.py` (`CLIENT` on first access; `pypac` and `user_agent`, which imports `requests`, only where used). A test that patched one of those names on the importing module (`printing.Json`, `wrapper.pac_context_for_url`) now patches it at its source, where the local import looks it up. Two costs remain by design: `yd-variables` without `--quiet` builds the config schema, whose `[workRequirement]` and `[workerPool]` sections need the SDK; and interactive selection (`sorted_objects()`, `print_numbered_object_list()`) imports it for its `isinstance` checks, after the user has been prompted.

### The `--json` Result and Exit Codes

With `--json`, stdout holds one JSON document, the command's result, and the exit code names the kind of failure; the contract, shapes and codes are in the README's *Machine-readable Output and Exit Codes*. `utils/results.py` is the accumulator: a command calls `record()` for each outcome (a dict, or an SDK object, serialised as `yd-list` serialises it) or `record_document()` for a one-object result, and both wrappers call `flush_results()` after `main()` returns and, on an exception, a `SystemExit` or a keyboard interrupt, before exiting — so a failure part-way still reports what was done; the `--debug` branch flushes in a `finally` and still re-raises unclassified. The failure branches set the exit code *before* flushing, and flush through `flush_results_after_failure()`, which reports a flush that fails (an unserialisable record) rather than letting it escape or turn the failure into exit 0. Both wrappers also check `any_failed()` straight after a *successful* `main()` and its flush: a command that caught its own error, recorded it as `failed` and returned normally (e.g. `yd-boost` on a 401) used to exit 0 regardless, so this is checked with or without `--json`, since the records exist either way; it sets `ExitCode.FAILURE` and suppresses the `Done` print, without touching what was already flushed. `yd-cancel`, `yd-shutdown`, `yd-terminate`, `yd-delete`/`yd-rm` and `yd-download` no longer restrict `--json` to `--dry-run` (`command_registry.py`'s `check_json_requires_dry_run` validator is gone): the real, acting path already recorded through `record_action()`/`record_deletion()`/`record_transfer()`, so lifting the parse-time guard was the only change these five needed. The flush does nothing without `--json` (`json_output` is `None` on a command without the option), prints once, and prints `[]` when nothing was recorded. A command that prints its own JSON through `print_json()` gets no flush (`printing.json_document_printed()`): that is the permanent rule, since `yd-show`, `yd-variables` and `yd-doctor` keep printing their own documents, but JSON printed any other way would still get a trailing `[]`. A command that prints its own document *and* records is a mistake, and `flush_results()` raises a `RuntimeError` saying so rather than printing a second document. `results.py` must never import `wrapper.py` or `load_config.py`, which import it. `utils/exit_codes.py`'s `classify()` maps what reaches a wrapper to an `ExitCode` (`settings.py`): typed checks first (the CLI's own `NotFoundError`, an `HTTPError`'s `response.status_code`, the SDK's `NotAuthorisedException`, `InternalServerException` and `ServerErrorException`, `requests` connection errors and timeouts), then the `MissingPermissionException` and `Unauthorized` text checks the wrapper's friendly messages also key on (`MISSING_PERMISSION_TEXT`, `UNAUTHORIZED_TEXT`), then the exception's `__cause__`, else `FAILURE` — so **a failure re-raised with a clearer message must be raised `from` the original**, or it loses its code, and a missing entity is raised as `NotFoundError`, never `KeyError`; a `SystemExit`'s code passes through. `load_config.py`'s and `variable_substitution.py`'s configuration-time exits use `ExitCode.CONFIGURATION`; a command that catches a failure itself exits `FAILURE`, except a `SESSION_FAILURES` one (authentication, connection) that stops an action command: having recorded the failing item and the not-attempted rest, the command raises `exit_codes.ReportedFailure(cause)`, which both wrappers exit on with the cause's code (`classify()` follows `__cause__`) without printing it again. `abort.py`, `boost.py`, `cancel.py`, `shutdown.py`, `nodeaction.py`, `compute_action_common.py`, `start_hold_common.py` and `utils/resource_processing.py` (for `yd-create` and `yd-remove`) do (`nodeaction.py` also raises it for a faulty specification whose faults it has printed, and for a `--follow` that `--timeout` cut short); `create_resources()` and `remove_resources()` otherwise carry on past a failed specification (or ID), printing each failure once, naming the resource (a creator or remover raises rather than printing first), and finish by raising `ReportedFailure` with the failures' shared cause, or a `RuntimeError` for different causes, so they exit by cause like `yd-wait`; the Cloud Wizard, which calls `create_resources()`, still sees it raise, and its `remove_resource_by_id()` still returns `False` on a failure, having reported it. `yd-remove --ids` fetches each resource before confirming its removal (`_removable_by_id()`, a table per YDID type), so an ID that does not exist is `NotFoundError` (exit 6) without a prompt. Its Group, Application and User memberships are made to match a `roles`/`groups` list, so `[]` removes them all, but are left alone without one, and every name in the list is resolved, one that does not exist failing the resource, before anything is changed, since reconciling against a list with a misspelt name would remove the membership it meant. Never raise it `from` anything: `from None` clears the cause the code comes from. Under `--json`, `print_warning()` writes to stderr (`CONSOLE_ERR`, or `sys.stderr` under `--no-format`) rather than being dropped, and `interactive._get_user_input()` writes its prompt to stderr, so stdout still parses. **The rule for new code: a site that reports an outcome with `print_info()` also calls `record()`**, since `--json` silences the one and only the other reaches the script. The twelve action commands (`yd-cancel`, `yd-shutdown`, `yd-terminate`, `yd-start`/`yd-hold` in `start_hold_common.py`, `yd-finish`, `yd-abort`, `yd-resize`, `yd-boost`, and the three `yd-compute-*` in `compute_action_common.py`) do so through `record_action(entity, entity_type, action, outcome, error=None, **extra)`, beside every print of what was done, skipped (declined, filtered, already in that state) or failed; `entity` is an SDK object, an `{id, name}` dict, or a string the command was given (a YDID becomes the `id`, anything else the `name`). An Instance is recorded as `{"id": "<cr_id>.<instance_id>", "name": "<instance_id>"}`, the form those commands accept. `yd-shutdown --terminate` records each Compute Requirement it terminates as a `compute-requirements` record with action `terminate` and an extra `workerPoolId`, its `id` `null` when the pool could not be fetched for it — never the pool's ID under the Compute Requirement's type; a Configured Worker Pool, which has none, is warned of and not recorded. `shutdown.py` follows `compute_action_common.py`'s shape (resolve in the order given, `_Unresolved`, confirm once, act, a `SESSION_FAILURES` failure recording the rest as not attempted) without sharing its code, Worker Pools and Nodes being different targets. `yd-resize` re-raises a failed resize after recording it, so the wrapper still exits non-zero with the record emitted. Their `--json` is `ACTIONS_JSON` in `command_registry.py`, spelled without `-J`. `yd-create` and `yd-remove` record through `record_resource(resource_type, name, id, action, error=None, **extra)` at every created/updated/removed/skipped site, the Image Groups and Images of an Image Family included, and in `create_resources()`/`remove_resources()`'s failure branches, the name coming from `load_resources.resource_display_name()`, read before the creator pops anything from the specification; `yd-create --dry-run --json` records each processed specification with `record()` instead of printing it (`_show_dry_run_specification()`, which takes the resource type and puts `resource` back as the record's first key, since `create_resources()` popped it and a mixed file's array would otherwise be untyped; the printed form still omits it), and records no failures, so its document is the array of specifications, and a Jsonnet dry run under `--json` from a loader that converts several files (`exit_on_dry_run=False`) records a copy of each. `yd-submit`, `yd-provision` and `yd-instantiate` call `record_entity()` straight after the Platform call, and under `--dry-run --json` `record_document()`/`record_document_part()` in place of the print; `record_document_part()` makes the document the one part, or the array of them once batching adds a second. The creators' `--quiet` bare IDs go through `printing.print_quiet_result()`, which prints nothing under `--json`, so `--quiet --json` is the document alone. Those three also carry `check_json_excludes_streaming()` (`command_registry.py`), which refuses `--json` with `--progress` or `--report`: the Rich progress bar and the template report both write to stdout. `--follow` alone reports through `print_info()` and is allowed. A Configured Worker Pool's record carries its `token` and `expiryTime`, as an Application's carries its key, since `--json` silences the prints that show them. The remaining commands: `yd-wait` records `{id, name, status, succeeded}` per ID given, in the order given, and treats an entity not in a terminal state when following ends (its `--timeout`, passed to `follow_ids()`, or a lost stream) as a failure, exiting with the single cause's code (`follow_exit_code()` for a lost stream) or 1 for a Work Requirement failure or mixed causes; `yd-follow`'s `--json` prints each event as a JSON document (`print_event()` keys on the `events_as_json` property in `args.py`, true for that command alone, so an action command's `--follow --json` still prints no events; the `--raw-events` option that duplicated this on `yd-follow` and every command taking `--follow` is gone) and `main()` calls `results_are_streamed()`, so nothing, not even `[]`, follows the events; `check_follow_json_excludes_progress()` refuses it with `--progress`, whose bar consumes the events. The data client records in `dataclient_utils.py`, per file for the three transfers (`record_transfer()`, the listing of a remote directory's files done only when `json_requested()`, since it costs an rclone call) and per item for deletion (`record_deletion()`, with `name` and `isDir` beside `path` and `action`; `deletion_targets()` lists a path or a wildcard's matches once, so `yd-delete` confirms and deletes exactly those, a path already gone recorded `skipped` and a directory without `-R` `failed`, and `delete_item()` deletes one, recording it; `delete.py` refuses the remote's root and the configured bucket, and Commander's delete chooser offers only the `would delete` records). `yd-download`'s records add `match`, the top-level item each file belongs to, because Commander's download chooser offers top-level items and `selection.parse_download_summaries()` groups the per-file records back into them; yd-delete's records are what `parse_object_summaries()` reads, so the old `matched_item_rows()` listing is gone. `yd-ls` records `lsjson_listing()`'s entries in place of printing its table, each with `Listing`, the remote path it was listed under; a path that does not exist, or cannot be reached, is an error (exit 1) while the other paths are still listed, but an empty directory or a wildcard matching nothing (`glob_matches(allow_empty=True)`) is an empty listing. `yd-compare` and `yd-nodeaction` record their tables with `rows_as_objects()`, and pass `override_quiet=not json_requested()` where a message is printed despite `--quiet`, since `override_quiet=True` also prints under `--json`. `yd-version` and `yd-help` are standalone and cannot import `printing.py` (its import parses the command line for a registered command), so they print their documents with `json.dumps(..., cls=CompactJSONEncoder)`.

### Configuration

Config is loaded from (in priority order): CLI args → environment variables → TOML file. Exception: if the config file is explicitly selected with `--config`/`-c`, its contents (including `[common.variables]`) take precedence over environment variables, but not over CLI args (see `config_file_explicitly_selected()` in `misc_utils.py` and `add_substitutions_from_config_file()` in `variable_substitution.py`). Key env vars: `YD_KEY`, `YD_SECRET`, `YD_NAMESPACE`, `YD_TAG`, `YD_URL`. Variables prefixed `YD_VAR_` are available for substitution in specs.

`load_config_common()` records where each `[common]` value came from in `CONFIG_SOURCES` (`command line`, `environment (YD_KEY)`, `config file (<name>)`, `default`, `not set`), and takes `strict=False` to return a partial `ConfigCommon` with `None` for a missing key or secret instead of exiting; `yd-doctor` is the only caller of either. `ConfigCommon.key` and `.secret` are therefore `str | None`, and `wrapper.py` asserts both before building the API key.

Any TOML property can be overridden on the command line with `--property 'section.key=value'` (repeatable). Valid sections: `common`, `dataClient`, `workRequirement`, `workerPool`, `computeRequirement`. Values are JSON-parsed first (handles bool, int, float, list, dict), falling back to plain string — except for the properties listed in `STRING_PROPERTIES` (`property_names.py`), where the supplied text is kept whenever JSON would make it something other than a string, so `--property workRequirement.name=123` is a name and not an integer (`null` still unsets). The registry is keyed on the property name alone, a name being the same type wherever it appears, and `tests/test_property_overrides.py` checks it against the types recorded in that module's comment column. The config loaders type-check a few properties (`check_str`/`check_list` in `load_config.py`), among them the Work Requirement's `name`, `taskGroupName` and `taskName` and the Worker Pool's `name`, and `format_yd_name()` type-checks the name it is handed, so `name = 123` in a TOML *or* a specification file is a reported configuration error rather than an `AttributeError` raised inside the formatter. Overrides are applied after TOML validation in `load_config.py` via `_apply_property_overrides()`, and the schema check that runs as a command starts sees them (see *Specification Schemas*).

File paths follow two rules. A specification file (Work Requirement, Worker Pool, Compute Requirement, resource, Node Action), from the command line or from the configuration file (which `pathname_relative_to_config_file()` rewrites relative to the current directory), is named from the current directory and opened as it is given: the loaders take no `files_directory`. A file a specification refers to — a `taskDataFile`, a CSV file, a `writeFile` content file, a `userDataFile` — is found from the files directory: `--content-path`, else the specification's directory, else the configuration file's (an absolute path is itself), by a plain `os.path.join()` at each site (`provision_utils._read_user_data()` `chdir()`s there instead). A `resolve_filename()` in `variable_substitution.py` used to serve both kinds, guessing from whether a path read from the current directory landed in the files directory that it was a specification, which broke `--content-path` for any specification outside it (and `yd-submit`'s `relpath()` of the specification made even an absolute one fail) and misread a referenced file under a subdirectory named as the specification's; with the guess gone it was only `os.path.join()`, and was removed.

### Variable Substitution

Specs (TOML/JSON/Jsonnet) support `{{variable_name}}` substitution with type tags: `num:`, `bool:`, `array:`, `table:`, `format_name:`. Every value in the substitutions dictionary is a string, so a value arriving as something else has to be rendered as text: `_stringify()` does that, and renders it as **JSON** rather than with `str()`'s Python repr, because the tags read the value back as JSON — `array:` and `table:` with `json_loads()`, `bool:` as the JSON spelling — so a repr's apostrophes meant a TOML `strs = ["a", "b"]` could not be used as an array at all, and `true` was held as `"True"`. Two things it must *not* do, each with a test: a string is passed through untouched, since every value is re-rendered on each resolution pass and one given JSON's quotes would gain another pair every time; and a value with no JSON form falls back to `str()`, which is what keeps TOML's date, time and datetime values (`tomli` returns real `date`/`datetime` objects, which `json_dumps` raises `TypeError` on) rendering as the text they were written as. Three entry points need it, and all three were wrong: `_update_and_resolve_substitutions()`, the `[common.variables]` comprehension in `load_toml_file_with_variable_substitutions()`, and `add_or_update_substitution()` (which `load_config.py` calls for a `--property common.variables.x=...` override, whose value has already been JSON-parsed into a real list, dict, number or boolean). The type tags are `_TYPE_CONVERTERS` in `variable_substitution.py`, each tag with the function converting its value (`_number()`, JSON's syntax or Python's, finite; `_boolean()`, any case, any space around it; `_collection_of()` for `array:` and `table:`, reading JSON, refusing the NaN and infinities `json.loads()` accepts, and only where that fails a Python literal by `ast.literal_eval()` (which evaluates no code), held by `_json_form()` to what JSON could have held: strings for keys, finite numbers, no tuples, sets, bytes or complex numbers, each refused saying why rather than changed; `format_yd_name()`), and `TYPE_TAGS` and the tag regex in `process_variable_substitutions()` are built from its keys, so a tag cannot be recognised without a converter, and `process_typed_variable_substitution()` raises for one it does not know rather than returning `None`. Its errors name the expression as written (`Cannot substitute '{{num:x:=abc}}': 'abc' is not a number`). A typed expression inside a longer string is converted, so checked, and then written as text by `typed_value_as_text()`: as JSON, as `_stringify()` holds a value, but a number as written; it was `str()`, which wrote `True` and Python's `['p', 'q']`. And a typed expression whose name is still undefined once its nested parts are resolved (`{{num:x_{{y}}}}` with no `x_Y`; `_is_whole_expression()`) is passed through with its tag, as an untyped one is, for a later pass or the undefined-variable warning, rather than converted as its own text and reported as `'{{x_Y}}' is not a number`. Default substitutions are defined in `VARIABLE_SUBSTITUTIONS` in `variable_substitution.py`; `{{pid2}}` is `misc_utils.PROCESS_DISCRIMINATOR`, so a hand-written name can be disambiguated the same way a generated one is, and `{{pid}}` is the full PID (`misc_utils.PID`); `{{random}}` and `{{random6}}` are three and six base 36 digits from `misc_utils.random_base36()`, base 36 rather than hexadecimal because it is the widest alphabet a YellowDog name may be built from. Variable names follow one rule, `VARIABLE_NAME_PATTERN` in `settings.py` (a letter, digit or `_`, then letters, digits, `_`, `.` and `-`), checked by `check_variable_name()` at every definition source — the `YD_VAR_*` scan and `-v` parsing at import (which print and exit, the exception trap not yet being in place), `add_or_update_substitution()`, `add_substitutions_without_overwriting()` and `add_substitutions_from_config_file()`, each taking a `source` for the error (the `--property` override and `[dataClient]` profile registration catch it and exit) — and the same pattern builds `_VARIABLE_REFERENCE`, so a `{{...}}` whose name breaks it is text, not a reference: that is what makes the undefined-variable warning and the circular check exact rather than heuristic. The four sources a *user* writes — `YD_VAR_*`, `-v`, `[common.variables]` (in `add_substitutions_from_config_file()`) and the `--property common.variables.<name>` override (in `load_config.py`, ahead of `add_or_update_substitution()`) — call `check_user_variable_name()` instead, which also refuses `RESERVED_VARIABLE_NAMES` (`settings.py`: `namespace`, `tag`, `key`, `secret`, `url`), naming where each is set instead. Those five are registered by `load_config_common()` and `_load_namespace_and_tag()` with `add_substitutions_without_overwriting()`, so a user definition used to win in the table while `CONFIG_COMMON`, which every command acts on, kept the configuration's value — `-v tag=foo` changed `{{tag}}` and not the tag a Work Requirement was named with — and one unset with `{{::}}` was removed from the table and then simply defined again. The CLI's own registration keeps going through `check_variable_name()`, which is why the reserved check is a separate function rather than part of it; `tests/test_variable_names.py` holds both. `.` and `-` may not lead because `{{.ID}}` and `{{- ...}}` are other tools' syntax; an `env:` name is the OS's and gets `ENV_VARIABLE_NAME_PATTERN` (anything but whitespace and the syntax). Default values use `:=` separator. Environment variables via `env:` prefix. Nesting has no depth limit. Syntactic nesting (`{{a_{{b}}}}`) is resolved by recursion within one pass; a substituted value that reveals a further reference needs another pass, so every loader — the three spec loaders and `load_config.py`'s section loaders, via `_resolve_section_variables()` — calls `resolve_variables_insitu()`, which repeats `_substitute_insitu_pass()` until a pass reports no changed paths. Two things make a circular reference an error (`ValueError`, naming the properties) rather than a hang or a silent pass-through: values still changing after `VAR_SUBSTITUTION_MAX_PASSES` (10) passes, which catches mutually- and self-referring `env:` values; and, once settled, an expression that is exactly a defined variable's token (`_unsubstituted_defined_variables()`), since a pass always substitutes a defined variable — this is what catches circular *table* variables, which `_update_and_resolve_substitutions()` resolves at definition to their own token (`p = '{{p}}'`), a value every pass then substitutes back to itself and so looks settled. The check uses the pass's own delimiters (and the Worker Pool ones for `userData`), so Mustache left for the platform is never mistaken for a cycle. An undefined variable is unchanged by the first pass and passes through, and the same walk (`_unsubstituted_references()`, which also looks inside a nested expression such as `{{template_{{x}}}}`) reports it with `print_warning()`, once per expression per process (`_UNDEFINED_VARIABLES_REPORTED`). Three things keep that honest. It is off until `enable_undefined_variable_warnings()`, which `main_wrapper` and `dataclient_wrapper` call as the command starts: the configuration's own passes run at import, before `namespace`, `tag`, `key`, `url` and `dataClient.*` are defined, and would report every one of them. A section resolved at import and never again would therefore go unchecked, which is what the Worker Pool sections are: `load_config_worker_pool()` keeps a copy of each as resolved, before `computeRequirement` is merged into `workerPool` (`_WORKER_POOL_SECTIONS_AS_LOADED`, so a value is listed under the section it was written in, once), and `yd-provision` and `yd-instantiate` pass it to `warn_of_undefined_worker_pool_variables()` as `main()` begins — a check-only walk (`warn_of_undefined_variables()`) sharing the once-only record. Text is substituted the same way: `process_variable_substitutions_in_file_contents()` repeats its pass (`_substitute_file_contents_pass()`) until the text stops changing, under the same cap, and then applies the same circular check (`_undefined_unless_circular()`, shared with the in-situ resolver), naming the `source` its caller passes — the file. It serves User Data, Task Data and `writeFile` content files, which nothing walks afterwards (so a type-tagged expression there is written in this pass, never left for a later one: in quotes as its JSON, quotes and all, anywhere else as text by `typed_value_as_text()`, a number keeping its written form), and the Jsonnet loader's pass over the raw text; for Jsonnet that pass is before evaluation, so it is the only one that can resolve a chain the Jsonnet code computes with, and `load_jsonnet_file_with_variable_substitutions()` hands the substituted text to `_jsonnet.evaluate_snippet()` under the file's own name, with `jpathdir=[os.getcwd()]`, so imports resolve beside the file first and the current directory second, and errors name the file; it once wrote a `VariableSubstitutedJsonnetFile` copy into the current directory for `evaluate_file()`, which resolved imports from there, named the copy (`tmp7bbg02ql:3:6`) in errors, failed in a read-only directory and could leave the substituted copy behind. The pass is `_substitute_jsonnet_pass()` (`jsonnet=True`) rather than the plain text pass: `_JSONNET_LITERAL` lexes the strings (double, single, both verbatim forms, text blocks) and skips the comments, so that an apostrophe in `// don't` opens no string, and each expression, found by position (`misc_utils.find_delimited_expression_spans()`, since one expression can sit in strings needing different escaping), is read through its string's escapes (`_jsonnet_unescaped()`) and its value written back with them (`_jsonnet_escaped()`, which indents a multi-line value in a text block as the block is); outside a string a value is inserted as code, a typed one as its JSON, and a typed one that is a whole string replaces the literal, quotes and all. Each distinct expression is substituted once per pass, which with the scanner's compiled pattern cached per delimiter pair (`_inside_expression_pattern()`) took a 742kB file with 12,000 substitutions from 187ms to 56ms, against 15ms for the plain text pass. One exception in its circular check: the Jsonnet pass leaves a type-tagged expression inside a longer string for the in-situ pass after evaluation to substitute as text, so a leftover type-tagged reference to a defined variable is not taken for a cycle there. A single value is substituted the same way again: `resolve_variables_in_string()` repeats `process_variable_substitutions()` until the value stops changing (a type-tagged result, a non-string and the unset marker are returned as they are), then applies the circular check and the undefined warning, naming its `source`. Every single-value site outside `variable_substitution.py` goes through it — in `load_config.py` via `_resolve_value()`, which exits on the error as `_resolve_section_variables()` does and names each `[common]` and `[dataClient]` value by its property (`key` and `secret` included, so their text is never a message); `resolve_remote_path()` names a path by itself — and `tests/test_variable_subs.py` fails if a bare `process_variable_substitutions()` call appears outside `variable_substitution.py`. It matters beyond chains: a single pass also made the undefined-variable warning call a *defined* variable undefined, because the warning assumes the value it is handed has been fully resolved, and a `--tag` or `YD_TAG` that is a chain generated names from the unresolved token (`envc1_...`), since a command-line or environment value replaces the config file's after the file's own passes. What is substituted other than by a walk checks its own result the same way. The configuration values resolved one string at a time at import — `namespace`, `tag`, `url` and every `{{dataClient.*}}` value, read back from the variable table where they are registered resolved, credentials deliberately excluded — are checked by `warn_of_undefined_config_variables()` (`load_config.py`), which both wrappers call straight after enabling the warnings. File contents substituted as text — User Data files (`provision_utils._read_user_data()`), `yd-nodeaction` `writeFile` content files, Task Data files (`submit_utils._substituted_task_data_file()`) — and the data client paths (`resolve_remote_path()`) each call `warn_of_undefined_variables({source: text})`, the source being the file or the path itself, which is what the warning names. The three file sites pass `per_source=True`, which records the pair (expression, file) in `_UNDEFINED_VARIABLES_REPORTED` rather than the expression alone, so each file of a `userDataFiles`, `contentFiles` or `taskDataFiles` list holding an expression is reported, while one file read for every Task is still reported once; `_read_user_data()` substitutes and checks each file of the list separately for the same reason, rather than the concatenation under all their names. `yd-variables` checks the variables it reports (every one, or those named, less `key` and `secret`) with `warn_of_undefined_variables()`, since the table is resolved at import and so never checked otherwise. Its output follows `yd-show`'s, the other command whose output is always JSON: warnings ahead of the JSON and the wrapper's `Done` after it, on stdout, and `--quiet` for the JSON alone. It used to set `ARGS_PARSER.json_output` itself, so that its JSON came out alone without `--quiet`, but `json_output` means the user asked for JSON output with `--json` and gates `print_warning()` too, so it hid the warnings; routing them to stderr, and then exempting them from the gate, were both tried and dropped in favour of the CLI's ordinary convention. Commander therefore passes `--quiet` in `_yd_variables_command()` — before it did, `main_wrapper`'s own `[common]` check could print onto stdout ahead of the JSON and break discovery's parse — and `test_commander_config_discovery.py` holds it to that, while `test_variables_command.py` runs the same shape of command with a warning due and parses the result. It also explains a variable the `::` syntax removed (`explain_unset_variable()`, every one of them in the full report, via `get_unset_variable_names()`), which would otherwise report `null` exactly as one never defined does. That works from `_DEFINITIONS` in `utils/variable_substitution.py`, each variable's definition as written, because the table cannot say why — the variable is gone from it. `_update_and_resolve_substitutions()` records a merged value as a new definition unless the table already held it (a resolved value, not a definition), and `add_or_update_substitution()` records its own. The same record lets the undefined-variable warning (`_warn_of_undefined()`) say that a reference is to a variable that is *unset*, and why, rather than 'not defined', which sends the reader looking for a typo. The lazy variables `yd-submit` defines per Task Group and Task (`LAZY_VARIABLE_NAMES` in `settings.py`) are never reported, since the loader passes run before they exist. And only an expression shaped like a reference — optional type tag, optional `env:`, then a name — counts (`_VARIABLE_REFERENCE`), so Docker's `{{.ID}}` or a Go template's `{{ .Values.x }}` in a task argument is left alone; a bare word such as Go's `{{end}}` would still be reported, which is why this is a warning and not an error. Every in-situ pass outside `variable_substitution.py` goes through `resolve_variables_insitu()` — the late passes in `submit.py`, `csv_data.py`, `load_resources.py`, `submit_utils.py` and the Cloud Wizard included — and `tests/test_submit_utils.py` fails if a single-pass `process_variable_substitutions_insitu()` call reappears.

The `::` unset suffix (`{{varname::}}`) removes a property entirely when the variable is undefined; if defined, its value is used normally. The bare `{{::}}` always removes the property unconditionally. A *variable* so defined is removed from the table, and is then undefined to everything, so a plain `{{varname}}` reference to it is left unsubstituted and only a `{{varname::}}` one propagates the unset. `_update_and_resolve_substitutions()` removes the unset variables, repeatedly, *before* storing anything it substitutes: it used to remove them after the sweep, by which point every variable resolved in the same sweep had taken in the unset one's `{{::}}` as text and was unset in turn on the next — an unset that spread by plain reference, but only to variables in the same sweep, never to `[common]` values or specifications, which were left unsubstituted. `tests/test_variables_command.py` (`TestUnsetIsNotTransitive`) holds both halves. Both work in TOML, JSON, and Jsonnet — for Jsonnet, `process_variable_substitutions_in_file_contents` leaves unset tokens intact so `process_variable_substitutions_insitu` can remove them after evaluation. A JSON file has no text pass: `load_json_file_with_variable_substitutions()` parses it first and substitutes its values in situ, as the TOML loader does, because substituting the raw text read every value through JSON's escapes and inserted it without them — a default's `[\"x\"]` failed to parse and a Windows path's `\t` became a tab. So a substitution in a JSON file must be inside a string (an unquoted one is reported by the parse error's hint) and in a value: one in a property name, which only the text pass ever reached, is an error (`_substituted_property_names()`). Nested inside another expression, an unset one is replaced by `_UNSET_MARKER` while the outer one resolves, and the outer one is itself unset if the marker survives — that is, if the value was needed, to build a name or as a default that is used. Leaving the inner token in place instead, as it once did, made the outer expression look up a name containing `{{missing::}}` and pass through unresolved.

CSV batch task prototypes use a separate `<<variable_name>>` delimiter system (defined in `csv_data.py`), distinct from `{{`/`}}` to allow both to coexist in the same spec without ambiguity.

### Commander

`yd-commander` is a PyQt6 desktop GUI over the CLI, in `yellowdog_cli/commander/`. It is not a second API client: **every action it takes runs a `yd-*` command as a child process** (`_run_command_in_subprocess`, via `QProcess`), so behaviour, output and configuration precedence are the CLI's. Nothing in the package imports the SDK or `wrapper.py`, and there is no `CLIENT`. `yellowdog_cli/commander/README.md` documents it for users; the notes here are the ones that matter when changing it.

- **PyQt6 is an optional extra** (`pip install "yellowdog-cli[commander]"`). `launcher.py` is deliberately free of Qt and of the heavy CLI imports, so `--help` and the missing-extra message (`check_commander_imports()`) work without it. Only after that guard does it import `commander.py` and call `run_app()`.
- **Launch options only fill the window in.** `launcher.py` parses the config file (positional or `-c`), `-y`, and the options named after the CLI's own — `-n`, `-t`, `--name`, `-P`, `-v`, `--property`, `-r`, `-p` — into a frozen `StartupSettings` (`startup.py`), which `run_app()` hands to `YellowDogApp`; nothing downstream knows a value came from the command line. Three things are deliberate. Everything Commander could not hold as given is refused by argparse before Qt starts: a named file that does not exist (so a missing config file fails at launch, though one chosen in the GUI is still only logged), a variable with whitespace in it (the box is split on whitespace, so `title=my run` would become two tokens), and a field value with a tab or newline (`_edit_box_keypress_handler` deletes them); for the same reason the variables are joined with spaces, since a newline between them would be deleted and fuse `a=1` and `b=2` into `a=1b=2`. Definition file paths are resolved against the *launch* directory, what a path typed in a shell means, and stored absolute like any other selection (`_set_wr_file`/`_set_wp_file`, shared with the Select buttons). And `_apply_startup_fields()` runs in `__init__` *before* the text fields' signals are connected, so the deferred config parse is the first and only one to see the values — filled afterwards, the user-variables box would start its reparse timer and run a second parse. `tests/test_commander_startup_fields.py` asserts that timer is idle.
- **The command box runs three kinds of command three ways.** A `yd-*` command is split with quoting and decorated by `_build_command_args()`; one in `UNDECORATED_YD_COMMANDS` (the registry's `CommandKind.STANDALONE` commands: `yd-version`, `yd-help`, `yd-schema`, `yd-format-json`, `yd-jsonnet2json`, which take none of the added options) is run exactly as typed, and ignores the Properties field; anything else goes to `host.shell_command()` with the text whole. The shell is started by full path — `%ComSpec%`, else `%SystemRoot%\System32\cmd.exe`, else the bare `cmd`; `/bin/sh` elsewhere — because started as the bare `cmd` a Windows machine failed every such command with 'Process failed to start: Access is denied.' while `yd-*` commands ran; `yd-version` used to go to the shell too, since it takes none of the added options, and failed with it. Importing `command_registry` is safe here: it imports only `settings.py` and `glob_utils.py`.
- **The option fields are split with quoting; the variables box is not.** Extra Options (both), Properties and a typed `yd-*` command go through `arguments.split_arguments()`: whitespace separates, single or double quotes group and are removed, and there are no backslash escapes, deliberately, since a shell's would eat Windows paths — so `shlex` is not used. A typed non-`yd-` command is still handed whole to `sh -c`/`cmd /c`. User-Defined Variables stays on `.split()`, which `launcher.py`'s whitespace refusal and `variable_is_complete()` assume. The Properties field (`properties`, in `horizontalLayout_properties`, grid row 4 beneath User-Defined Variables) is passed to every `yd-*` command by `_namespace_tag_and_user_vars()` as `--property=<entry>`, joined so that a value beginning with `-` is never an option, and to discovery, whose debounced reparse waits for every entry to be `property_is_complete()` and the quotes to balance, sharing `_user_vars_reparse_timer`. An unbalanced Properties field makes `_namespace_tag_and_user_vars()` raise `QuotingError`, so every action that runs a `yd-*` command calls `_properties_are_usable()` first and refuses — before any listing, which would otherwise fail and read as 'the listing failed' — and discovery reports it as a discovery failure. A new action that runs a command must make the same call. `--property` at launch is refused unless complete, and is quoted into the field with `quote_argument()`, which refuses a value holding both kinds of quote and a space. `_align_field_labels()` widens `user_variables_label` and `properties_label` to the wider of the two, so the two fields start at one edge.
- **Every control carries a tooltip, written in `commander.ui`.** `tests/test_commander_ui_loads.py` fails for a named button, checkbox or field without one — the output window alone is exempt, since a tooltip there would pop up over whatever is being read — and for one over two lines of 80 characters, because plain-text tooltips do not wrap and anything longer belongs in the Help. They are one-line summaries of what the README says, so a change to what an action does may need both. The two definition-file Select buttons show the selected file's full path as their tooltip instead, and `_show_selection_on_button()` restores the original (`_select_wr_default_tooltip`/`_select_wp_default_tooltip`, read from the widget at construction) on deselection rather than clearing it.
- **The layout lives in `commander.ui`**, loaded by `loadUi()` in `YellowDogApp.__init__`, which then connects signals to widgets by name. A renamed or deleted widget therefore fails at construction rather than at use — `tests/test_commander_ui_loads.py` is what catches that.

- **The selection lists correct where their style paints a check indicator.** macOS 26 redesigned the system controls, and AppKit gates the redesign on the *main executable's linked SDK*. Where that is the macOS 26 SDK or later, Qt's macOS style draws a checkbox or radio indicator as the new 16x16 control at the painter's origin, ignoring the rect it computed; linked against an earlier SDK the same Qt draws the legacy 18x18 control in the rect. An item view clips each row's painting to that row, so every indicator but the top row's was clipped away: a ten-row confirmation showed one checkbox and nine rows that looked unticked — and untickable — however they were clicked, which is what a dialog allowing a single selection looks like. Only the painting was ever wrong; the ticking under it worked throughout, and the 'N of M selected' count said so. `fix_check_indicator_placement()` puts a `CheckIndicatorPlacement` proxy style on the list, which translates the painter by the rect's top-left before handing the primitive on — the rect's *position* is what is being ignored, so the painter's own transform is all that is left to carry it. **The cause was established causally, not by correlation**, one interpreter at a time with `vtool`, rewriting nothing but the SDK field: 26.5 → 15.5 on a Homebrew Python's `Python.app` fixes it, 15.5 → 26.5 on a uv-managed interpreter breaks it, and Apple's own opt-out (`UIDesignRequiresCompatibility` in the app's `Info.plist`) fixes it too. That matters because the correlations are badly misleading, and this was read wrongly twice before: first as a Qt 6.11.0 regression (the older PyQt6 versions had all been installed under a *different interpreter* — a version bisect across interpreters is worth nothing unless the interpreter is held still), then as a framework-versus-standalone build difference (Homebrew rebuilds against the current SDK; uv's standalone builds target an older one). Every Homebrew build measured misplaces it, 3.10 through 3.14; every uv-managed one places it correctly, 3.10 through 3.15; same PyQt6, same Qt binaries byte for byte, and 6.10.1 and 6.11.0 identical on either. Only the checkbox and radio indicators are affected — push buttons and combo boxes draw in their rect either way — and only an item view, which clips per row, turns that into a functional failure: a standalone `QCheckBox` paints its indicator at its own origin anyway, so Commander's main-window checkboxes are merely 1px high and 2px smaller, and are left alone. Qt records the general problem itself — its 'Qt for macOS - Specific Issues' page says the Widgets and Quick macOS styles "may exhibit drawing artefacts" under Liquid Glass — and names the same two escapes found here: build with Xcode 16, or set `UIDesignRequiresCompatibility`. Both belong to whoever builds the main executable, which for a Python GUI application is whoever built the interpreter, so neither is available to us; correcting the painting is the only lever at this end. So `check_indicator_is_misplaced()` measures it — one indicator painted into a transparent pixmap, and where the ink landed — rather than keying off a version or a platform: nothing available at runtime names the real condition, and the correction must stop installing itself when Qt adapts to the redesign or Apple retires the compatibility path, since over a style that places the indicator correctly it would offset it twice. The style the proxy wraps comes from `platform_style()` rather than from `QProxyStyle`'s own base-less construction, because a base-less proxy wraps a fresh instance of the *desktop* style, not of the style the application is actually using — which on Linux is Fusion under Dark Mode whatever the desktop's is. The correction is parented to the list, since `setStyle()` does not take ownership. The real thing cannot be reproduced in the tests at all: under the offscreen platform Qt's macOS style draws no check indicator anywhere, so `tests/test_commander_check_indicator.py` stands a proxy style in for it, as `MacButtonLayout` does for the platform-viewer button — and it has to install that stand-in twice, as the application's style *and* behind `platform_style()`, or the test passes whether Commander corrects anything or not. The fix itself was verified against the real thing across six interpreters: the correction installs itself on exactly the three that need it, and every row shows its own state on all six.
- **`_align_checkbox_indicators()` indents the checkboxes by the style's own button inset.** The left column's checkboxes and buttons are laid out at the same x, and then the macOS style paints a button's bevel 2px inside its widget — room for the focus ring — and a checkbox's indicator flush, so the checkboxes looked a couple of pixels further left than every button around them. The indent is read from the style (`SE_PushButtonBevel` against `SE_CheckBoxIndicator`), never written as 2, for three reasons that each bit: Dark Mode switches the application style on Linux (`_dark_mode_action` calls `setStyle("Fusion")` there; macOS and Windows go through `setColorScheme` and keep their style), so `changeEvent` recomputes on `StyleChange`; the margins are cleared before measuring, or the second measurement reads the first one's margin and the indent compounds; and it runs from `showEvent`, not `__init__`, because the style resolves the inset against the real platform and reports it flush before the window is shown — measured in `__init__` it is 0 and the indent is never applied at all. The applying direction has no test: offscreen *every* style paints the bevel flush, even the macOS one, so it cannot be reproduced headlessly. Measured per style on macOS: the macOS style insets the bevel by 2, while the `Windows` and `Fusion` styles report it flush and so get no indent at all, which is what keeps the stylesheet — and Qt's caveat about a stylesheet suppressing native theming — out of the picture wherever there is nothing to correct. What is tested is the clearing direction, which is what a style change depends on. **On Windows the indent is deliberately not applied**: that style paints its button frame inset but reports it flush, so there is nothing to key off, and the resulting 1–2px difference is accepted rather than guessed at. Two routes were tried and are dead ends — a widget cannot measure where it paints by grabbing itself (`grab()` fills its rect opaquely), and the `SE_*LayoutItem` rects, which exist to say where a widget's visual content sits, report flush on Windows and on macOS contradict the style's own painting (claiming 2 where it paints 0, which is itself part of how the misalignment arises).

- **The file dialogs are Qt's own, with a preview pane.** They are `FileDialogs`' (`file_dialogs.py`), which the window holds as `_file_dialogs`. `build_browse_dialog` (the directory buttons) and `select_file` build a non-native `QFileDialog`, call `_add_preview_pane()` and run it through `_run_file_dialog()`; `save_file` builds and runs one the same way but adds no pane, because it names a file that does not exist yet. The selectors accept with **Select** and the browsers with **Open**, which is the honest split: only a browser opens what it is given. The preview exists because leaving the platform's file viewer behind also leaves Quick Look behind; it decides text-versus-binary by decoding the head of the file, never by extension (task output is named whatever the task named it), and it keeps the decoded `QImage` so a widened pane rescales from the original. The text branch is capped three ways: `PREVIEW_READ_BYTES` and `PREVIEW_MAX_LINES` bound what is read and shown, and the elision line names whichever of them bit — stating only what a head-read can know, since a total line count would mean reading the whole file, which is what the byte cap exists to avoid. `PREVIEW_MAX_LINE_CHARS` is the third and is a *performance* cap, not a cosmetic one: `QPlainTextEdit` lays a single line out at superlinear cost, so a 256kB head with no newlines in it (minified JSON) took 110ms to show on a pane that is refilled at every arrow-key press, against 1.4ms once each line is cut. `_thumbnail()` activates the layout before measuring, because a pane only just shown or resized has not had its layout event delivered yet. - **The output window is a view of `_output_entries`, not the store.** It is `OutputPane`'s (`output_pane.py`), which the window holds as `_output` and logs to with `self._output.log()`; the pane owns the entries, the runs and the filter, and the window registers each command with `start_run()` and hands its `QProcess` to `attach()` before connecting its own `finished` handlers, so the last of the output lands before anything reports the process done. Every `log()` call records an `OutputEntry` (its text and the `OutputRun` it came from — a launched command, or `COMMANDER_RUN` for Commander's own messages) and appends it to the widget only if the current filter lets it through; each block it adds is tagged with its entry's index via `QTextBlock.setUserState()`, which is how the right-click menu (`_build_output_menu`) finds the run of the line under the pointer. The filter is **by run, not by the PID text**, because most of a command's output carries no PID — continuation lines, tables, JSON — and the `Executing:` line is printed with Commander's PID before the child has one; the process callbacks and the Executing line pass `run=` for that reason, and a new caller logging on a command's behalf must too. The rows come from `OutputRun`'s `user_command_line` (the arguments before `_build_command_args()` decorated them), `started_at` and `outcome` (set by `_record_outcome` on `finished`, or `did not start`), and the listing is widened to its longest row, capped at the main window's width, because its rows are command lines. `_output_filter` is a `frozenset` of run IDs; `filter_description()` names them on the bar, Commander last. Its Return test needs `commander_dialogs.NOTHING`: macOS passes Return from the list to the dialog, which presses the default button by `animateClick()`, ~100ms later, so a driver that rejects straight after the key press wins the race.
- **A dialog list is created with a parent, or it is sized 2px short on macOS.** `_new_dialog_listing()` builds every dialog `QListWidget` as `QListWidget(self)`, although the dialog's layout reparents it straight away, because `_fit_dialog_listing_height()` fixes its height from `frameWidth()` and the macOS style reports 6 for a widget with no parent (a prospective window) against 7 once it is inside one. The confirmation and chooser lists were built unparented until the process chooser exposed it: each showed a scrollbar and clipped its last row (a 58px viewport for three 20px rows). Offscreen reports 7 either way, so no test can see this; it was measured on the real platform, before and after.
- **The Help window is the package's own `README.md`**, so the guide on GitHub and the one in the application are a single file and the latter matches the installed version; `pyproject.toml` lists it as package data for that reason, and `tests/test_commander_help.py` checks the declaration, since with `include-package-data = false` a missed file is simply absent from the wheel. `HelpDialog` (`help_viewer.py`) is modeless and the window keeps one (`_help_dialog`), raising it again so the reader keeps their place; the Help button, F1 and the platform's `HelpContents` key all open it. Qt's Markdown importer needs four corrections, all in `build_help_document()`: headings get no anchor names, so each is given the one GitHub derives from its text (`heading_anchor()`) — which is what the README's `[...](#section)` links are written against, and a test fails if any of them has no heading to land on, so renaming a heading means fixing the links to it; fenced code blocks come out unshaded and headings with no space around them; every list item is spaced like a paragraph, which spread the README's table of contents over two screens, so an item that is nothing but a link to a section (`section_link_item()`) is drawn tight, with a disc rather than the hollow bullet `*` gets, while prose lists keep their spacing; and the screenshot shows at natural size, cut off, so it is dropped. The table of contents is `gh-md-toc`'s, generated by `make toc_commander` with `--skip-header`, since an entry for the page's own title would push every real section down a level; like any section link, a stale entry fails the link test. The document is *set* on the browser rather than loaded, which leaves it no source for history to return to, so `setSource(QUrl("#"))` gives it one — without it Back never enables. The Help button sits in the bottom row because the utility row (`horizontalLayout_4`) is the widest in its column and so sets the window's minimum width — measured on macOS it is 717px in a 717px column, nothing to spare — and a button there would widen that minimum.
- **`_notify()` is the modal notice**: it logs the message and then shows it, so the output window keeps the whole narrative either way, and it degrades to log-only when `--yes` is set (nobody is there to press OK) or while shutting down. `_build_notice_dialog()` is split out so a test can arm the real dialog rather than stub `exec()`, and it forces `PlainText` — a notice carries Windows paths and entity names, which as rich text lose their backslashes and their angle-bracketed parts. Only one caller so far, deliberately: Browse Results Directory with no results directory yet. The other dead-end notices remain log-only, and `tests/test_commander_notices.py` holds that line.
- **`Confirmation.__bool__` raises deliberately.** A confirmation carries both `proceed` and `handles`, and `if self._confirm_destructive(...)` — which is what the natural mistake looks like — would be true even for a refusal. Check `.proceed`.
- **Synchronous helpers block in nested event loops** (`_run_nested`), which keeps the window responsive while a child process runs. That makes re-entrancy possible, so the enumerating actions are guarded by `_operation_in_flight()` and a `_nested_depth` counter (a counter, not a flag: the config parse deferred with `singleShot(0)` runs inside the first loop to spin, so depth 2 is normal). A re-entrant enumeration returning `None` would read as "enumeration failed", which for a destructive action means falling back to the whole scope — hence refusing early.
- **Placeholders come from `yd-variables`.** Discovery is `ConfigDiscovery`'s (`config_discovery.py`), which the window holds as `_discovery` and reads the result from as `_discovery.namespace` and `_discovery.tag`; the window keeps the config-file *selection* (`_config_file`, the watcher, `_working_dir()`), which every command depends on, and tells discovery when it changes. `_parse_yd_config()` runs it (via `_yd_variables_command()`, the seam the tests override, which passes `--quiet` because `yd-variables` prints its variable warnings on stdout ahead of the JSON) to resolve the namespace and tag for the current config file. Every failure is reported through `_report_discovery_failure()` however quiet the parse was — a quiet parse suppresses the announcement, never the reason it failed — and a *timed-out* one is retried once, after a delay and with a longer budget, because the first `yd-*` of a session on Windows can need longer than the 10s budget to start and nothing else would try again before a restart. There is no exception for 'nothing configured': `yd-variables` needs no credentials, so with no config file and none in the environment it reports the defaults (the `_nothing_is_configured()` special case that suppressed its `Missing configuration data: 'key'` exit is gone). Two things to know: `invalidate()` also clears `_last_discovery_failure`, so a configuration file selected again reports its failure again rather than having it taken for a repeat (only the three config-file paths reach it; the user-variables reparse does not, which is what leaves that de-duplication doing its job); and `_set_config_file(None)` calls `clear()`, which empties `namespace`/`tag` and not just the placeholders showing them, since `_object_path()` builds the default download and delete path out of the tag, so a stale one is a path acted on. Wire new discovery callers through `reparse_placeholders()`, which is the only thing that pairs a parse with the placeholders and with that retry; calling `_parse_yd_config()` directly is how three of the four callers silently had no retry. It is stubbed in the tests (see below), so nothing there spawns a CLI process for it. The one caller that does *not* go straight there is the user-variables box: it reparses 600ms after every keystroke, and every variable is typed through states that are not yet `name=value`, so `_reparse_placeholders_after_edit()` holds the reparse until `variable_is_complete()` accepts every token in the box — otherwise adding `instances=3` reported `Error in variable substitution 'instances'` on the way through, an error the user had not made. It reports nothing while it waits, because at 600ms after a keystroke an unfinished variable and a wrong one are the same text; a genuinely malformed one is reported by the CLI when a command is actually run, and the guard is deliberately not in `_namespace_tag_and_user_vars()`, which those commands share.
- **A selected definition file's path is absolute on purpose.** `_wr_file`/`_wp_file` are stored with `abspath()`, not `relpath()`, because they have two consumers reading them against different bases: they are passed to a child process that runs in the config file's directory (`_working_dir()`), and Show opens them in Commander's own process, whose directory is wherever it was launched from. A path relative to either base is wrong for the other — stored `relpath()`-from-cwd, `yd-submit -r ../demos/bash/x.json` went looking under the config directory and got `No such file or directory`. The config file needs no such care, since its consumers take `_config_dir()`/`_config_basename()` from it rather than passing it on. Note that the command-construction tests are blind to this class of bug when they set `_wr_file` directly and assert the argument verbatim: `tests/test_commander_commands.py` resolves the handed-over path against `_working_dir()` the way the child does, and one case reads the file back through Show, which is what a config-dir-relative 'fix' breaks.
- **A missing tag is not a path.** `_object_path()` returns `None` when the Path field is empty and no tag has been discovered, and the download and delete actions must refuse on it (`NO_OBJECT_PATH`). It used to interpolate the missing tag into the default `f"{tag}*"`, so a failed discovery handed `yd-download`/`yd-delete` the literal `None*` — and with confirmations suppressed, `yd-delete -Ry None*` would have run.
- `commander.py` carries `E402`/`RUF005` per-file ignores in `pyproject.toml`: it was lifted from the standalone `yellow-gui` demo repo, and those are pre-existing findings kept out of the relocation diff. The modules split out of it (`selection.py`, `file_dialogs.py`, `output_pane.py`, `config_discovery.py`, `output_model.py`, `check_indicator.py`, `host.py`, `elision.py`, `command_history.py`, `help_viewer.py`) need neither, so none is extended to them.
- **The window's collaborators own their state, and are reached through it.** `FileDialogs` (`_file_dialogs`), `OutputPane` (`_output`) and `ConfigDiscovery` (`_discovery`) are each given what they need — a parent and a font; the output widgets, the window for its layout and width, and the chooser builder; the four fields discovery reads and writes, and seven window hooks — rather than the window, so what they can touch is what they were handed. Tests reach them the same way (`window._output._filter_output`, `monkeypatch.setattr(window._file_dialogs, "save_file", ...)`), patching the instance. Two consequences. A handler a collaborator connects in its own constructor must be patched on *its* class before the window is built, which is what `OWNERS` in `test_commander_button_wiring.py` is for. And a window method a collaborator calls is handed over as a lambda, not a bound method (`build_chooser=lambda ...: self._build_chooser_dialog(...)`): bound at construction, `commander_dialogs.drive_chooser`'s later patch of the window would not reach it. Nothing drives the process chooser that way today, so no test fails without that lambda; it is there so that the driver cannot silently miss. Discovery's are load-bearing now: `test_commander_shutdown.py` replaces `_run_nested` on the window during a real discovery, and with `run_nested` bound early `test_config_parse_timeout_is_bounded` fails. `shutting_down` and `config_selected` read window attributes, so they could only ever be callables.
- **Patch a split-out function where it is defined, and call it through its module where a test must reach it.** `conftest` points `file_dialogs.dialog_settings` at a test ini file, and every caller is `FileDialogs`, in the same module, reading the module global — which the patch replaces. Anything outside `file_dialogs.py` that needs it must call `file_dialogs.dialog_settings()` rather than import the name: imported, it would be a second binding the patch did not reach, and the tests would read and write the developer's real preferences without failing. The check-indicator test patches `check_indicator.platform_style` for the same reason. `monkeypatch.setattr` refuses a missing attribute, so a patch left on `commander` after a move fails loudly rather than going quiet.

### MCP Server

`yd-mcp` is an MCP server over the CLI, in `yellowdog_cli/mcp/`, offered by the optional `mcp` extra (`mcp>=2.2`). It is a thin peer of Commander: **every tool call runs a `yd-*` command as a child process with `--json`**, exactly as Commander runs a command in response to a button, so that behaviour, configuration precedence, output shapes and exit codes are the CLI's by construction rather than a second implementation of them. Nothing in the package imports the SDK, `wrapper.py`, `args.py` or `printing.py`: `args.py` parses the command line at import for a registered command, and `yd-mcp` is not one, and `printing.py`'s output goes to a terminal a stdio server does not have. `tools.py` and `runner.py` import nothing from the `mcp` package either, so the tool catalogue and the child-process runner are tested without the extra installed; `server.py` is the one module that imports `mcp`, and `launcher.py` imports it only after `check_mcp_imports()` (`utils/check_imports.py`) passes, so `--help` and the missing-extra message work without it, as Commander's do without Qt.

The tool catalogue (`tools.py`) is built from the command registry, not hand-written: `build_tools()` makes one `ToolSpec` per command whose `ToolKind` (`command_registry.py`) is not `NONE` — `READ_ONLY`, `ACTING` or `DESTRUCTIVE`, carried to the client as `readOnlyHint`/`destructiveHint` — from `all_options()` less `MCP_EXCLUDED_OPTIONS`, mapped mechanically to JSON Schema (`_property_schema()`, `_item_schema()`). **A new command states its `ToolKind` when it is added to the registry**, since the field has no default; **a new option is placed on purpose**, either given a schema entry or added to `MCP_EXCLUDED_OPTIONS`, and `tests/test_mcp_tools.py` holds every option of every tool command to one or the other. `yd-rm` shares `yd-delete`'s `Command` and so gets no tool of its own, exactly as it shares its command; `yd-cloudwizard`, `yd-format-json`, `yd-jsonnet2json` and `yd-help` are `ToolKind.NONE` and so absent from the catalogue.

`fixed_args()` prepends what every tool call needs ahead of its own arguments, gated per command on the option actually being present: `-c <file>`/`--nc`, `--nf`, `--json` (added even for `yd-version`, whose parser is its own and not in the registry), `--quiet` for `SELF_PRINTING_COMMANDS` (`yd-show` and `yd-variables`, which print their own document through `print_json()` with no `--json` option, so without it the wrapper's `Done` follows the document and `Run.document` is `None`, as Commander's `_yd_variables_command()` found), `--yes`, then the launch-time `-n`/`-t`/`-v`, so a tool's own `namespace`/`tag`/`variable` argument comes later on the command line and wins. `command_argv()` runs the command as `python -m yellowdog_cli.<module>` under the server's own interpreter, not the `yd-*` console scripts, since a desktop client launches the server with a minimal `PATH` that may not hold them. `to_argv()` emits every value-taking option as one `--long-flag=value` entry (`_joined()`; an `append` option repeats it, a boolean stays its bare flag), and **that form is load-bearing for security, not style**: as two entries, a value that looks like a flag (`namespace="--show-secrets"`) is taken by argparse as that flag on a `nargs="?"` option such as `--namespace` or `--tag`, which switched on exactly the options `MCP_EXCLUDED_OPTIONS` withholds — `yd_variables` reported the secret in full — so never tidy it back into `[flag, value]`; for the same reason `_property_schema()` refuses a non-positional option with `nargs` of `*` or `+`, whose values one entry could not carry. It emits `--` ahead of the positionals, so a positional starting with `-` (a glob, a remote path) is never read as an option. The four specification-taking tools (`yd_submit`, `yd_provision`, `yd_instantiate`, `yd_create`, and `yd_remove` alongside them) accept a path or the specification inline; an inline one is written as JSON to a uniquely named `.yd-mcp-*.json` file in the working directory, created exclusively and readable by the owner only (`tempfile.NamedTemporaryFile`, so O_EXCL and 0600: a predictable name written with `write_text()` followed a symlink pre-placed there and was world-readable) — the config file's directory, so relative `taskDataFile`/`userDataFile` references resolve as they would from a file the user wrote there — and removed after the run whatever its outcome.

`runner.run()` runs one command line with `subprocess.run` (`stdin=DEVNULL`, so an unanswered prompt fails fast rather than hanging) and a `timeout_seconds` bound (every tool has one, default 300, `yd_follow`'s 60); a `TimeoutExpired` is reported as a stopped `Run` carrying what the child had already written, not raised, and output is decoded with `errors="replace"` on both paths, since a strict decode raised `UnicodeDecodeError` out of `call_tool()` and the SDK answered a stray byte with a JSON-RPC internal error. `server.py`'s `_result_of()` turns a `Run` into a `CallToolResult`: an exit 0, a stopped run, or an exit 1 whose document holds a record with `outcome`/`action` of `failed` (the CLI's own per-item rule, `results.any_failed()`) is a success, `structuredContent` being `{"result", "exitCode", "stopped"}` (plus `"stderr"` when stopped); every other non-zero exit, or no parseable document at all, is `isError` with `{"result", "exitCode", "stderr"}` and, as text, the command's stderr followed by the document as compact JSON when there is one (`_error_text()`: `yd_doctor`'s failing checks and `yd_wait`'s failed Work Requirement exit 1 with the document alone, and said only 'exited 1 with no output' before); an unknown tool name, an argument `_validate()` rejects, or any other exception raised inside `call_tool()` (its last-resort `except Exception`, which logs the traceback to stderr) is a tool error too, with `exitCode` 2, never a protocol-level error, so the agent sees the message and can retry. Stdout is the transport (`stdio_server()`), so nothing the server prints for itself may go there; it logs its own start and, per call, the full command line and the child's exit code to stderr at `INFO`, which is why the fixed `-v` arguments, and a call's own `variable` argument, make a secret-holding variable visible in the server's own log. On POSIX the first SIGINT or SIGTERM ends the process at once (`_stop_on_signal()`, an `anyio.open_signal_receiver()` task beside `server.run()`): it logs `stopped` and calls `os._exit(0)` because cancelling the task group cannot finish — the SDK's stdin reader blocks in `readline()` in an anyio worker thread that a cancel waits for and interpreter exit joins, as does a tool call in progress — which is why one Ctrl-C used to be absorbed and a second one printed a traceback. A command still running is left to finish on its own. On Windows, which has no signal receiver, `run_server()` catches `KeyboardInterrupt` instead.

Tests are `tests/test_mcp_tools.py`, `tests/test_mcp_runner.py`, `tests/test_mcp_launcher.py` (all Qt-free, SDK-free and `mcp`-free) and `tests/test_mcp_server.py`, which drives the real `Server` through the SDK's own `ClientSession` over in-memory streams and is skipped without the extra (`tests/mcp_guard.py`'s `require_mcp()`, in the style of `qt_guard.py`'s `require_qt()`). `yellowdog_cli/mcp/README.md`, shipped as package data, documents the server for its users; `tests/test_mcp_readme.py` holds it to declaring every tool and keeping its table of contents current.

Phase 2 (a `streamable-http` transport, per-session credentials) is left open rather than built: `run()` already takes an `environment` parameter that phase 1 fills with the server's own `os.environ` and phase 2 would fill per session instead, and no tool exposes `--key`, `--secret`, `--url` or `--config`, so a session's credentials can only ever come from that parameter.

### Specification Schemas

`utils/spec_properties.py` records, as data, every specification property the CLI itself defines rather than the SDK: the Work Requirement properties and their levels, and the shells the Worker Pool, Compute Requirement, resource and Node Action files put around their SDK models. The rule: a Work Requirement property is added to `WORK_REQUIREMENT_PROPERTIES` *and* given a row in `README.md`'s Work Requirement Property Dictionary, with the same levels marked, and `make schema_descriptions` is run — `tests/test_spec_properties.py` fails on a row with no property, a property with no row, a level that disagrees, a duplicate row, or a `spec_data/descriptions.json` that is not a fresh extraction. A dictionary property's description is the README row's and nothing else (`description=None` in the registry), so the customer-facing table is the single source; a nested fragment's properties (the task data inputs and outputs, a Group's roles) and every shell property carry their own `description` in the registry, since no README row describes them. The dictionary is the reference for levels unless a loader contradicts it. `property_names.py`'s type comments stay as documentation, and a test holds them to the registry's fragment types.

`utils/spec_schema.py` builds each family's schema when asked, never from a stored copy, so a newer SDK is described the moment it is installed. What *is* stored is the compiled validator (`utils/schema_cache.py`): fastjsonschema's code generation and Python's compile of the result are nearly all of the check's cost (the Resources family's code is 1.3MB of source, ~130ms on Apple silicon and several times that on an older machine), while building the schema is a few ms and checking a document a fraction of one, so the cache is keyed on a digest of the schema as built each run and cannot outlive the SDK that shaped it. It lives under the system's temporary directory deliberately, so that nothing the CLI leaves needs finding and removing: macOS and Linux age out or clear their temporary directories, and Windows' is cleared by Storage Sense or Disk Clean-up, which is less certain but bounded at one file per stem. The SDK side is `annotation_schema()`'s mapping table (`str`, `int`, `float`, `bool`, an `Enum`, `timedelta` as an ISO 8601 duration, `datetime` as `date-time`, `List`/`Set`, `Dict` with an enum key as `propertyNames`, `Optional` admitting null — a `null` added to the `type` or `enum`, or for a `$ref` or combinator `if` null `else` the schema — a dataclass as a `$ref`, a generic dataclass such as `Selection[T]` expanded inline with `T` substituted, a polymorphic base dispatched on its discriminator by `_polymorphic_dispatch()`, the `_dispatch()` shape, over `$ref`s to its members); **the rule is fail-loud**: an annotation outside the table raises `SchemaGenerationError` naming the model and field, and nothing falls through to an open schema, so a new SDK type is fixed by a row in the table rather than silently accepted. A polymorphic base's members are found as the SDK's deserialiser finds them (its leaf subclasses with a `type`/`action`/`errorType` discriminator), and `POLYMORPHIC_FAMILIES` is held to that by a test; a member's discriminator is the value its class declares, plus the short class name for the four families whose discriminator `create.py` reads and strips itself (`CLI_READ_DISCRIMINATORS`). The CLI's own departures from the SDK are named tables in the module, each with its reason: `FIELD_OVERRIDES` (the Allowance dates, read by dateparser), `SUPPLIED_BY_CONFIGURATION` (the usage properties the TOML file fills in a Worker Pool or Compute Requirement file), `NODE_ACTION_NOT_PASSED` (`action` and `nodeIdFilter`, which `yd-nodeaction` never passes, dropped in that family only: a Worker Pool file's `nodeEvents` is posted as written), `MEMBER_SHELL` (a compute source's `userDataFile(s)`), `CLI_REQUIRED` (`namespace` on the Compute Source Template, Compute Requirement Template and Configured Worker Pool, which `create.py` indexes with no default; the corpus's minimal variants that omit it are `resource_live.MISSING_NAMESPACE_FAILURE_NAMES`, and the corpus test asserts exactly those fail, on `namespace`). Three shapes are deliberate. The `{{variable}}` wrapping is `if` a variable `else` the schema, not an `anyOf`, and a resource or node action is dispatched on its `resource`/`type` by `if`/`then` rather than a `oneOf`, as a nested polymorphic member (a Compute Source Template's `source`, a Worker Pool's node actions) is on its discriminator and the Compute Requirement root is on whether `requirementTemplateUsage` is present, and an optional model admits null by `if` null `else` its `$ref` (a `{{variable}}` in a dispatch key matches no case and leaves the object unchecked, which cannot be helped), both because `fastjsonschema` reports an `anyOf` or `oneOf` failure as `cannot be validated by any definition` at the wrapper, where an `else` or `then` failure is the schema's own message with its path — and the repair, having no path inside a combinator, would blank the whole member and lose its other violations. And `build_schema()` returns a deep copy, because `fastjsonschema` rewrites every `$ref` it compiles in place, against the `$id`: a `$ref` dict shared between families sent the second family's compile to fetch the first family's `$id` over the network.

`schema.py` (`yd-schema`) is the one place a schema is turned into a file, and it does that at run time too, never from a copy shipped with the package: `--write <dir>` calls `build_schema()` for every `Family` and writes `<family>.schema.json` alongside an `index.json` naming the CLI and SDK versions that produced them — the index last, so a write failing part-way leaves none (or the old one) for `--check` to find, and an `OSError` is an error naming the path and exit 1, as `--check`'s unreadable index is — `--check <dir>` compares those two versions against `index.json`, then builds each family (a few ms each; fastjsonschema's compile, the expensive part, is not needed) and compares it with the file written, so a file edited, missing or left by another run is not reported up to date on the index's word alone; a printed family (`printing.print_json_text()`, the text as given, no colouring or wrapping) is byte for byte what `--write` writes (`schema_text()`), each file written atomically; the SDK's version comes from `version.sdk_version()`, the package metadata, so `--list` and `yd-schema config` import no SDK (`--check` does, since it builds every family), `--list` names the families, and a bare `<family>` prints that one schema to stdout. Nothing SDK-derived ships in the wheel: `pyproject.toml`'s package data for `yellowdog_cli.spec_data` is `descriptions.json` alone, the CLI's own property text extracted from the README, because a schema built from a bundled SDK snapshot would silently describe whatever SDK the wheel happened to be built against rather than the one actually installed — the same reasoning as `utils/spec_schema.py` building on demand rather than at import. `yd-schema` needs no configuration and no credentials, so like `doctor.py` it is a registry command running straight off `ARGS_PARSER`, on neither wrapper.

`utils/spec_validation.py` checks a specification at run time. **The hook rule**: a loader that reads a specification family calls `check_specification()` (or, for `yd-create`'s several files, `strip_schema_key()`, `warn_of_violations()` and `validate_all_and_exit()`) on the document once it is loaded — after the loader's variable substitution, Jsonnet evaluation, TOML conversion or CSV task expansion, so an unresolved `{{x}}` passes where the schema admits one and an `{{::}}`-unset property is already gone — and before anything uses it; the hooks are in `submit.py` (after the JSON/Jsonnet/TOML branches, before `validate_properties()`), `provision.py` and `nodeaction.py` (after their JSON/Jsonnet branches), `instantiate.py` (before `requirementTemplateUsage` is unwrapped) and `load_resources.load_resource_specifications()` (per file, after the in-situ pass and before the source-directory stamp, for creation only: the schema is what `yd-create` accepts, and `yd-remove` reads only names). An ordinary run warns and goes on — **and is never refused by the schema itself**: `warn_of_violations()` catches a `SchemaGenerationError` or fastjsonschema's `JsonSchemaDefinitionException` from building or compiling the schema (a future SDK field the mapping cannot describe), prints one warning that the file went unchecked, naming the cause and `yd-schema <family>`, and returns no violations, so an SDK upgrade cannot stop every run until a CLI release, while `--validate` and `yd-schema` stay fail-loud and name the model and field; `--validate` (`VALIDATE` in the registry, on those five commands, `ARGS_PARSER.validate`) prints the violations as errors, records `{source, path, message}` for `--json` (whose document is therefore the array, `[]` when valid), and exits 1, or 0 with a line saying the file is valid; wherever it cannot check a document — no specification file (including `yd-submit`'s CSV-only run, whose document the CLI builds from the TOML configuration with task-level prototype properties no file may carry, and `yd-nodeaction` without `--actions`), `yd-submit --json-raw` (Platform JSON, not a specification) and `yd-nodeaction --status` — `--validate` is refused with an error, so it never exits 0 without having checked anything. `$schema` (`SCHEMA_KEY` in `property_names.py`, in `ALL_KEYS`) is stripped by the hook, since a Worker Pool file is posted to the Platform as written and a resource's unknown key would be warned of by `_get_model_object()`. `fastjsonschema` stops at the first failure, so `validate_specification()` repairs each failure out of a copy of the document — deleting the properties an object must not contain, adding the ones it must, satisfying a one-of-these-keys `anyOf` (`ONE_OF_REQUIRED`) by adding its first alternative and a not-these-together `not` (a writeFile's content sources) by dropping the last key, each named in its own words (`must contain one of name, username, id`, `must not have both content and contentFile`, and for the properties deleted or added `unknown property 'nope'` and `missing required properties 'a', 'b'`, sorted) rather than fastjsonschema's, whose Python reprs (`must not contain {'nope'} properties`, a set in unstable order) never reach a user, replacing any other failing value with a `{{variable}}` token, which the wrapping admits wherever a value stands — and validates again, until it passes or the failure is the document's own, stopping at `MAX_VIOLATIONS` with a final `...and more` violation; fastjsonschema's path is its rendered name split on `.`, so `_locate()` joins parts back together to follow a key that contains one; the split is on `[` and `]` too, and a key containing either cannot be followed, so the repair loop stops there, after reporting that violation — documented in the module docstring rather than fixed. The tests hand every command's `ARGS_PARSER` mock `validate=False` (`test_json_output.py`'s `_DEFAULTS` included): a `MagicMock`'s unset `validate` is truthy.

The configuration file is the sixth family, `config`, and is checked in two parts. At import `load_config.py`'s `validate_properties()` runs exactly as it always has — before the `--property` overrides, `[dataClient]` profiles stripped, every key held to `ALL_KEYS` — and is still the only error: an unknown or deprecated key exits 3. Everything the schema adds is a warning, printed as a command starts by `warn_of_config_violations()`, which `main_wrapper` calls with `ALL_CONFIG_SECTIONS` and `dataclient_wrapper` with `DATA_CLIENT_CONFIG_SECTIONS` (the sections each kind reads; the subset also saves compiling the SDK-backed `[workRequirement]`), and `validate_config()` compiles the schema over only those of them the file actually has (`sections & frozenset(working)`, after its own key checks, which still use the full set to name an unknown section), so a file without `[workRequirement]` never compiles its SDK definitions — 36ms against 8ms for the rest on Apple silicon, before `schema_cache.py` keeps either, straight after `warn_of_undefined_config_variables()`. Never at import: `yd-doctor` imports `load_config` inside its checks, and warnings printed then would land in its table. It checks `_CONFIG_AS_WRITTEN`, a deep copy of `CONFIG_TOML` taken straight after the overrides and before any section loader pops or merges anything (`importCommon`, `[computeRequirement]` into `[workerPool]`), so a violation is named under the section it was written in and an unknown `--property` key, which `validate_properties()` never sees, is reported; it is `None` without a file (`--nc`, none found), and the `importCommon` file is not checked. `validate_config()` checks each section's top-level keys itself before the schema — a key in `ALL_KEYS` is `'<key>' is not read in this section`, anything else `unknown property` — because the schema's closed objects would call a misplaced key unknown. The rule: **a new configuration property goes in `CONFIG_SECTIONS` (for `[workRequirement]`, a dictionary property with the TOML level) and in `config-template.toml`, or `tests/test_config_schema.py` fails**; its fragment follows what the loader *accepts*, so a property the loader casts with `int()`/`float()` (`INT_CAST`/`FLOAT_CAST`) admits exactly what the cast takes — any number, a bool, and a string of digits with `_` separators, plus for `float()` a fraction, an exponent, `inf`/`infinity`/`nan` — as a type list with a `pattern`, never an `anyOf`, whose failure fastjsonschema reports as `cannot be validated by any definition`, and `validate_config()` rewords both of its failures (`_worded()`, by the property's fragment) as `must be an integer`/`must be a number`. A top-level key that is not a table is `'<key>' is not in a section`, a table that is no section `unknown section`. `warn_of_config_violations()` also catches any other exception from the check as one warning (re-raised under `--debug`), since the check is advisory and must never stop a command that would otherwise run. A key read but undocumented is caught too: `test_every_key_the_loaders_read_is_in_its_section` scans `load_config.py` for each `<x>_section.get(CONSTANT)` and `[CONSTANT]`, which is how `[workRequirement]`'s `workerTag`, a fallback with no dictionary row, came to be a registry entry of its own. `validate_config()` drops `None` values before checking, since TOML has none and one can only be a `--property section.key=null` unset. The SDK is imported only when a schema needs a model: `sdk_models.model_class()` is the one place `yellowdog_client.model` is imported, so the `[common]` and `[dataClient]` schemas, and the data client commands that check only those, load no SDK. Once `version.py` and the shared utilities stopped importing it (see *Keeping the SDK out of start-up*), leaving this import eager would have been the last thing loading it for them. `warn_of_config_violations()` also returns at once when `printing.warnings_suppressed()` (`--quiet`, `--count-only`: `print_warning()`'s own rule) and not `--debug`, since it only warns and building a schema with an SDK-backed section imports the SDK — which Commander's `yd-variables --quiet` would otherwise pay on every discovery. `conftest`'s autouse `_no_config_snapshot` sets the snapshot to `None` for every test, since the test process loads whatever `config.toml` the checkout holds at import.

### Resource Specification Test Corpus

`tests/resources/` is the single source of resource specifications used by the resource-definition tests (`test_resource_specs.py`, `test_resource_property_coverage.py`, `test_system_resources.py`) — one Jsonnet file per resource type, each with a minimal variant (only required properties) and a maximal one (every settable property), loaded through the CLI's own loader rather than duplicated as separate fixtures. See `tests/resources/README.md` for the minimal/maximal convention and how to add a new resource type.

`tests/resource_models.py` is a write-side coverage gate: it introspects the SDK's own dataclasses for every model the corpus's resource types build (via `create.py`'s `_get_model_object`) and fails, naming the property, when a settable property is set by no specification at all. A property can only be excluded from the gate by a registry entry (`SERVER_ASSIGNED_COVERAGE`, `NOT_SETTABLE`, `NOT_TESTED`) carrying a stated reason. Those registries, `MODEL_FOR_RESOURCE` and `settable_properties()` live in `yellowdog_cli/utils/sdk_models.py`, shared with the specification schemas, and `resource_models.py` re-exports them under their old names (the same objects, so a test mutating one changes what the gate reads); `build_models()`, `comparable()` and the nested-model walk stay in the tests, being the gate's alone. An exclusion is never inferred from the dataclass's own `field.init`, since the SDK structures an `init=False` field from a specification exactly like any other. A live read gate in `test_system_resources.py` then demands every property excluded as platform-assigned either actually come back from a real `yd-show` at least once, or carry a recorded reason why this suite cannot make it come back (most of the waived ones belong to a compute source that never provisions a real instance, so it has no status, no instance summary and no exhaustion to report); an exclusion the platform has started honouring is reported as stale, so a waiver cannot outlive its reason. Consequently, closing a coverage gap the SDK opens (a new property on an existing model) is an edit to one `.jsonnet` file, not to several JSON fixtures.

### Coding Conventions

- Python 3.10+ syntax: use `str | None` (not `Optional[str]`), `match` statements where appropriate
- Every text file is opened with `encoding="utf-8"` (`open()`, `Path.read_text()`, `Path.write_text()`): without it Python uses the locale's encoding, cp1252 on Windows, and a UTF-8 specification or script holding a non-ASCII character fails to decode or arrives mangled. `tests/test_file_encoding.py` walks the package's source and fails on a text-mode call that names none
- Type hints on all new functions
- Constants in `settings.py` (UPPERCASE); property name constants prefixed `PROP_`, resource name constants prefixed `RN_`
- Use `print_error()`, `print_info()`, `print_warning()` from `printing.py` — never `print()` directly. Every Rich console print passes `soft_wrap=True`, since `print_string()` has already wrapped a message to `LOG_WIDTH` (`terminal_width()`, `DEFAULT_LOG_WIDTH` without a terminal or for one reporting 0 columns, where `fill()` raised) and a table is not wrapped at all, while Rich, at 80 columns whenever the output is not a terminal, wrapped every line again and broke tables, `yd-ls` paths and messages written to a pipe or a file; `print_event()` reads an event's fields through `_field()`/`_counts()`, since the Platform leaves a summary null and an exception there ended the stream being followed. Every Rich console the CLI builds has `emoji=False` (and `ConsoleWithInputBackspaceFixed.input()` defaults to the console's setting rather than Rich's `emoji=True`), because Rich turns `:x:` into an emoji and the CLI prints user text: `{{num:x:=1}}` came out as `{{num❌=1}}`. A new console must do the same. Two wrappers over `print_info()` carry a marker from `settings.py`, so the marker is stated once rather than at every call site: `print_debug()` (`DEBUG_MARKER`) for the startup preamble — *every* message printed before a command's own output, so `load_config.py` no longer calls `print_info()` at all — which it also gates on `--debug` and colours `DEBUG_STYLE`; and `print_dry_run()` (`DRY_RUN_MARKER`) for the `--dry-run` messages, which gates nothing and is uncoloured, because every caller is already inside a dry-run branch and the messages are ordinary output. `print_error()` and `print_warning()` likewise prepend `ERROR_MARKER` and `WARNING_MARKER`, so a warning goes through `print_warning()` rather than spelling its prefix, and anything printing an error without `printing.py` — Commander, `yd-jsonnet2json` — uses `ERROR_MARKER`, never a literal. A site that needs the marker without printing it — a conditional prefix, as in `resize.py` — imports the constant instead. The colouring is why `print_info()` takes an optional `style`: it is a Rich *base* style, so the highlighter's own colours for timestamps, quoted strings and YDIDs still apply on top, and `--no-format` ignores it with all other colouring. Reaching for it anywhere else needs a reason — plain `print_info()` is the default
- LRU cache on entity lookup functions in `entity_utils.py`
- Config dataclasses in `config_types.py`; no raw dicts for structured config

### Testing Commander's GUI

Commander's dialogs are tested as dialogs, through `tests/gui_harness.py` (generic Qt helpers) and `tests/commander_dialogs.py` (drivers for Commander's own confirmation and chooser). Three rules, each of which exists because breaking it let a bug reach a user:

- **Never stub `dialog.exec()`.** Use `gui_harness.run_modal()` when the test owns the dialog, or `commander_dialogs.drive_confirmation()` / `drive_chooser()` when production builds and execs it. Both queue the interaction with `QTimer.singleShot(0, ...)` so it lands inside the *real* modal loop, which means a click has to travel the real button-box wiring to have any effect. A stubbed `exec()` cannot tell a working button from an inert one.
- **Assert geometric relationships, never pixel counts.** `gui_harness.visible_rows(listing)` rather than a height in pixels: CI nodes substitute fonts, so absolute measurements do not travel. A list squeezed flat or robbed of its height by a scrollbar still has correct-looking arithmetic — only "how many rows can be seen" catches it.
- **Assert outcomes, not arguments.** Contract tests over `_run_command_in_subprocess` args are useful but blind: every GUI bug that has reached a user lived in a seam those tests stubbed or asserted around.

Constructing a `YellowDogApp` defers `_set_config_file` with `singleShot(0)`, and that runs `yd-variables` in a child process inside whichever event loop spins first — usually a dialog's `exec()`. `conftest`'s autouse `_no_config_discovery` stubs `ConfigDiscovery._parse_yd_config` for any test that uses `qapp`, since none of them are about discovery; the two that test the method itself carry `@pytest.mark.real_config_parse`. Left live it cost 235 CLI invocations and most of the GUI suite's runtime, made the tests depend on an installed `yd-variables`, and let the environment's namespace and tag leak in.

Everything runs under `QT_QPA_PLATFORM=offscreen` with no display, so it works on a headless CI node. Nodes without a usable Qt skip: every Commander test module calls `tests/qt_guard.py`'s `require_qt()` before importing anything that pulls in Qt, and the `qapp` fixture guards again. That guard is deliberately not `pytest.importorskip` — from pytest 9.1 it skips only on `ModuleNotFoundError`, so PyQt6-installed-but-`libGL`-missing (a minimal Linux image) errored instead of skipping. Calling it before the imports is what the `E402` per-file ignores in `pyproject.toml` are for. Modal runs are watchdogged, because a dialog that never closes would hang CI rather than fail it. An autouse `conftest` fixture surfaces assertions raised inside Qt callbacks, which Qt would otherwise print and discard.

Note that `_build_destructive_dialog` returns a dialog whose buttons are *not* wired — `_confirm_destructive` attaches a `clicked` handler afterwards, because it needs to know which button was pressed. Drive it through `_confirm_destructive`, not from the builder. `_build_chooser_dialog` wires its own box and can be driven directly.

## Keeping the Ancillary Files in Step

Documentation here is spread across several files, each with its own audience, and a change that lands in the code but not in them leaves the repo describing something it no longer is. **Before finishing any change, go through this list and update what the change has made wrong or incomplete.** Most changes touch one or two of these; some touch none. Say which ones you updated, or that none needed it.

| File | Update it when |
|---|---|
| `README.md` | User-visible CLI behaviour changes: a new command, flag, property, or a change in what one does. Run `make toc` afterwards — never hand-edit the table of contents |
| `README_CLOUDWIZARD.md` | Cloud Wizard behaviour changes (`make toc_cloudwizard` for its TOC) |
| `PYPI_README.md` | The command list or the headline description changes — it is the PyPI landing page, so it summarises rather than documents |
| `yellowdog_cli/commander/README.md` | Commander's GUI behaviour changes: a new button, dialog, or a change in what an action does (`make toc_commander` for its TOC, which the Help window shows too) |
| `DEVELOPMENT.md` | Anything a developer runs or needs installed changes: make targets, prerequisites, the venv or extras, `setup-ubuntu.sh`, the project layout |
| `tests/README.md` | Test files are added, renamed or removed, or a category, flag, marker or shared fixture changes |
| `CLAUDE.md` (this file) | A new module, pattern or convention arrives, or an existing one is described here and changes |
| `config-template.toml` | A new or changed TOML configuration property — it is the annotated reference for all of them |
| `pyproject.toml` | A new entry point, extra, or package-data file (`include-package-data` is `false`, so an unlisted asset ships broken) |
| `RELEASING.md` | The release process, branch model or PyPI arrangements change |

Two traps worth naming, both of which have bitten:

- A **new test file is invisible** unless it is added to `tests/README.md` — nothing fails, the table just quietly stops being a list of the tests.
- **Docs that describe a mechanism drift silently.** If a paragraph names a function, flag, package or file, check that it still exists and still behaves that way, rather than assuming the prose is fine because the code compiles.
